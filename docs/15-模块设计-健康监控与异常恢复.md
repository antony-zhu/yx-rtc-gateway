## 2. 设计目标

1. 设备出现局部故障时优先降级运行，不轻易重启整机。
2. `dev_mgr_task` 卡死、FreeRTOS 栈溢出、关键内部内存耗尽等系统级故障必须触发受控重启或硬件看门狗兜底。
3. 脚本异常不得拖垮设备管理平面。
4. 网络、HTTP、MQTT 长期失败不得阻塞脚本本地业务。
5. `datafs`、`logfs` 故障不得影响联网、MQTT、配置更新、OTA 和状态上报。
6. 故障摘要不能只依赖 `logfs`，必须有 NVS 或 RAM 中的最小摘要。
7. 重启前尽量保存重启原因、故障模块、运行时间和可信 UTC。
8. 防止脚本异常或启动阶段异常造成无限重启。
9. 看门狗喂养必须由健康监控模块统一决策，用户脚本不能直接控制硬件看门狗。
10. 发布版本不得在故障、日志、崩溃摘要中输出密码、token、密钥和派生材料。

## 3. 模块边界

建议目录：

```text
main/
  supervisor/
    gw_health_monitor.c
    gw_watchdog.c
    gw_fault_recorder.c
    gw_reboot_manager.c
    gw_boot_guard.c
```

职责拆分：

| 子模块 | 主要职责 |
| --- | --- |
| `gw_health_monitor` | 任务心跳、健康通道、栈高水位、heap/PSRAM 阈值和周期检查 |
| `gw_watchdog` | ESP-IDF task watchdog、硬件看门狗、软看门狗通道和喂狗决策 |
| `gw_fault_recorder` | 最小故障摘要、重启原因、故障计数和诊断快照 |
| `gw_reboot_manager` | 受控重启、脚本停止、NVS 刷新、状态上报和最终 `esp_restart()` |
| `gw_boot_guard` | 启动风暴检测、脚本禁用保护和受限启动策略 |

健康监控模块不负责：

1. 不申请、获取或改写设备管理 MQTT 凭据。
2. 不解析 MQTT 业务方法。
3. 不直接写配置区文件。
4. 不直接进入 Python VM。
5. 不自动恢复出厂。

## 4. 故障等级

故障按影响范围分级：

| 等级 | 含义 | 默认动作 |
| --- | --- | --- |
| `info` | 可观测事件，不影响运行 | 记录日志或诊断计数 |
| `warn` | 可恢复异常或资源风险 | 上报状态，继续运行 |
| `degraded` | 局部能力降级 | 关闭或降级对应能力，保留设备管理平面 |
| `recoverable_error` | 当前任务失败但系统可继续 | 结束当前任务，保留旧状态并应答失败 |
| `fatal` | 系统级故障，不能安全继续 | 记录摘要后受控重启 |
| `panic` | 无法进入受控流程 | 依赖 ESP-IDF panic 或硬件看门狗 |

等级判定原则：

1. 能只影响脚本的故障，不升级为设备管理故障。
2. 能只影响日志的故障，不升级为设备管理故障。
3. 能保留旧配置或旧固件的失败，不升级为系统级故障。
4. 可能破坏 NVS、配置生效区、OTA 分区或关键任务调度的故障，按 `fatal` 处理。
5. 无法确认系统仍可调度时，由硬件看门狗兜底。

## 5. 健康对象

健康监控对象分为核心对象和非核心对象。

核心对象：

| 对象 | 健康含义 | 异常动作 |
| --- | --- | --- |
| `dev_mgr_task` | 设备管理主状态机仍在调度 | 超时后记录 `dev_mgr_hang` 并重启 |
| `script_task` | 脚本运行时按状态报告健康 | 按脚本异常策略处理 |
| `storage_core` | NVS 和关键配置状态可读 | 进入受限运行或重启 |
| `watchdog` | 健康监控自身可运行 | 异常由硬件看门狗兜底 |

非核心对象：

| 对象 | 健康含义 | 异常动作 |
| --- | --- | --- |
| `log_task` | 日志队列和后台清理仍在调度 | 降级本地日志，不重启 |
| `net_worker` | 网络恢复流程没有卡死 | 重启网络流程，不重启设备 |
| `mqtt_worker` | MQTT client 事件循环没有卡死 | 重建 `dev_mqtt` client |
| `http_worker` | 系统 HTTP worker 没有卡死 | 取消当前 HTTP 任务并应答失败 |
| `ota_worker` | OTA 写入流程有进展 | 中止 OTA，保留当前固件 |
| `time_worker` | 授时任务没有卡死 | 标记时间不可信，等待下次授时 |
| `script_mqtt` | 脚本 MQTT client 状态 | 只影响脚本业务 |
| `script_http` | 脚本 HTTP 请求状态 | 只影响脚本业务 |

对象启停规则：

1. 对象未启动时，不参与健康判定。
2. 对象处于主动停止状态时，不参与超时判定。
3. 对象进入长耗时操作时，必须报告阶段和进度，而不是直接延长所有看门狗时间。
4. `script_task` 被配置更新、OTA、恢复出厂或重启流程主动停止时，脚本健康通道应进入 `stopping` 或 `disabled`，不按卡死处理。

## 6. 看门狗分层

看门狗分三层：

| 层级 | 名称 | 作用 |
| --- | --- | --- |
| 第一层 | 软看门狗 | 由 `gw_health_monitor` 检查任务心跳、阶段超时和脚本健康 |
| 第二层 | ESP-IDF task watchdog | 检测关键 FreeRTOS 任务长时间不让出 CPU |
| 第三层 | 硬件看门狗 | 在系统调度失效或监控模块失效时强制重启 |

喂狗原则：

1. 用户脚本不得直接喂硬件看门狗或 task watchdog。
2. 普通 worker 不直接喂硬件看门狗，只向健康监控模块上报心跳和进度。
3. 硬件看门狗由健康监控模块统一喂养。
4. 当关键健康通道超时且无法受控恢复时，健康监控模块停止喂对应看门狗或发起受控重启。
5. 看门狗喂养不依赖可信 UTC，使用系统 tick 计时。

脚本异常默认策略 `restart_by_watchdog` 的含义：

1. `restart_by_watchdog` 使用脚本软看门狗通道，不允许用户脚本直接控制硬件看门狗。
2. 线程 1 收到 `SCRIPT_EXCEPTION` 后，记录脚本异常摘要并停止刷新脚本健康通道。
3. 脚本软看门狗过期后，由 `gw_reboot_manager` 发起受控重启。
4. 如果受控重启流程自身卡死，硬件看门狗兜底重启。

## 7. 默认健康参数

健康检查默认参数：

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| `health.scan_interval_ms` | 1000 | 健康监控扫描周期 |
| `health.fault_summary_min_interval_ms` | 5000 | 同类故障摘要最小写入间隔 |
| `health.stack_check_interval_sec` | 60 | 栈高水位检查周期 |
| `health.heap_check_interval_sec` | 60 | heap 和 PSRAM 检查周期 |
| `health.boot_guard_window_sec` | 600 | 启动风暴统计窗口 |
| `health.boot_guard_max_reboots` | 3 | 窗口内允许的异常重启次数 |
| `health.script_crash_max_reboots` | 3 | 脚本导致重启的保护阈值 |

任务健康默认参数：

| 对象 | 心跳周期 | 超时 | 超时动作 |
| --- | ---: | ---: | --- |
| `dev_mgr_task` | 1 秒 | 10 秒 | 记录并重启 |
| `script_task` | 5 秒 | 30 秒 | 按脚本异常策略 |
| `log_task` | 10 秒 | 60 秒 | 降级本地日志 |
| `net_worker` | 阶段进度 | 120 秒 | 重启网络流程 |
| `mqtt_worker` | 10 秒 | 60 秒 | 重建 MQTT client |
| `http_worker` | 阶段进度 | 60 秒 | 取消当前系统 HTTP 任务 |
| `ota_worker` | 阶段进度 | 120 秒 | 中止 OTA 并上报失败 |
| `time_worker` | 30 秒 | 120 秒 | 标记授时失败 |

说明：

1. `http_worker` 超时不是 HTTP 总超时；HTTP 请求仍只使用连接超时和应答间隔超时。
2. 流式 HTTP 传输只要持续收到数据或阶段有进展，就不算 worker 卡死。
3. OTA 写 Flash、配置文件写入、日志清理等非 HTTP 阶段必须定期报告进展。
4. 上述参数为固件默认值，可以作为设备参数配置，但发布版本应设置合理上下限。

## 8. 栈和内存监控

任务栈固定使用内部 RAM。

| 对象 | 告警阈值 | 处理 |
| --- | ---: | --- |
| `dev_mgr_task` 剩余栈 | 4 KB | 记录 warn 并上报状态 |
| `script_task` 剩余栈 | 8 KB | 记录 warn 并上报脚本风险 |
| `log_task` 剩余栈 | 2 KB | 记录 warn，必要时降级日志能力 |
| worker 剩余栈 | 2 KB | 记录 warn，后续调大栈或拆分流程 |

内存监控建议：

| 资源 | 告警阈值 | 处理 |
| --- | ---: | --- |
| 内部 heap | 64 KB | 上报资源风险，限制非必要系统分配 |
| 内部 heap | 32 KB | 拒绝非关键任务，必要时受控重启 |
| PSRAM | 512 KB | 上报脚本资源风险 |
| PSRAM | 128 KB | 脚本大缓冲申请失败，脚本进入异常流程 |

规则：

1. Python VM heap、Python 对象、脚本大缓冲和脚本业务动态内存必须使用 PSRAM。
2. 脚本 PSRAM 不足不得回退占用内部 RAM 大块内存。
3. 内部 heap 低水位是系统级风险，应优先停止新建非关键 worker。
4. FreeRTOS 栈溢出视为 `fatal`，记录 `fault_task` 后重启；如无法记录，则由 panic 或硬件看门狗处理。

## 9. 故障摘要

由于 `logfs` 可能不可用，最小故障摘要必须保存在 NVS 或 RAM 中。

NVS 建议字段：

| 字段 | 说明 |
| --- | --- |
| `stats.boot_count` | 累计启动次数 |
| `stats.last_reset_reason` | ESP-IDF 读取到的上次复位原因 |
| `stats.last_reboot_reason` | 固件主动请求重启的原因 |
| `stats.last_fault_module` | 最近故障模块 |
| `stats.last_fault_reason` | 最近故障原因 |
| `stats.last_fault_uptime_ms` | 最近故障发生时运行时长 |
| `stats.last_fault_utc_ms` | 最近故障 UTC，UTC 不可信时为 0 |
| `stats.fault_count` | 累计故障计数 |
| `stats.boot_guard_count` | 当前启动风暴窗口内异常重启次数 |
| `stats.script_crash_count` | 当前窗口内脚本导致重启次数 |

记录规则：

1. 关键故障发生时先写 RAM 摘要，再尝试写 NVS。
2. 不因为 NVS 写入失败阻塞 panic 或重启流程。
3. 同类高频故障按 `health.fault_summary_min_interval_ms` 限频写入。
4. `logfs` 可用时，故障摘要同时投递日志。
5. 故障摘要不得包含 MQTT 密码、设备管理 MQTT 出厂密码、URL token、NVS 加密密钥和用户敏感字段。

故障原因建议命名：

| 原因 | 说明 |
| --- | --- |
| `dev_mgr_hang` | 设备管理主任务心跳超时 |
| `script_exception` | Python 脚本异常 |
| `script_watchdog_timeout` | 脚本健康通道超时 |
| `script_stop_timeout` | 系统任务要求脚本停止但超时 |
| `stack_overflow` | FreeRTOS 栈溢出 |
| `internal_heap_low` | 内部 heap 低于关键阈值 |
| `psram_low` | PSRAM 低于脚本关键阈值 |
| `cfgfs_invalid` | 配置分区无有效配置 |
| `nvs_error` | NVS 初始化或读写异常 |
| `ota_boot_failed` | OTA 后启动失败 |
| `boot_loop_guard` | 启动风暴保护触发 |

## 10. 启动风暴保护

启动风暴指设备在短时间内反复重启，导致无法稳定上线或无法接收平台修复指令。

启动成功判定：

1. 基础初始化完成。
2. `dev_mgr_task` 已运行并持续健康超过 120 秒。
3. 设备没有在该窗口内再次发生 `fatal` 或 watchdog 重启。

启动风暴默认规则：

| 场景 | 处理 |
| --- | --- |
| 10 分钟内异常重启达到 3 次 | 进入受限启动保护 |
| 10 分钟内脚本导致重启达到 3 次 | 本次启动禁用脚本自动运行 |
| OTA 后启动失败 | 由 ESP-IDF OTA 安全机制处理，仅用于启动失败恢复 |
| 配置双区都无效 | 不无限重启，保持设备管理平面等待整包配置修复 |

受限启动保护：

1. 不自动清除 `device_id`、`product_id`、`group_id`、MAC 和出厂必要参数。
2. 不自动恢复出厂。
3. 优先启动网络、`dev_mqtt` 和状态上报。
4. 可以临时跳过脚本自动启动，并上报 `script_status=disabled_by_fault`。
5. 可以跳过非必要能力，例如实时日志、脚本 MQTT、脚本 HTTP 和 WebSocket。
6. 平台下发新的配置包后，按配置更新流程修复。

脚本保护解除：

1. 成功应用新的配置包后清除脚本异常窗口计数。
2. 设备稳定运行超过启动风暴窗口后清除脚本异常窗口计数。
3. 恢复出厂后清除相关计数，但仍保留 `device_id`、`product_id` 和 `group_id`。

## 11. 局部恢复策略

网络和通信：

| 异常 | 恢复动作 |
| --- | --- |
| 4G 联网失败 | 退避重试，不重启设备 |
| 网络断开 | 重新联网，恢复后重连 `dev_mqtt` |
| DNS 失败 | 按 HTTP 或 MQTT 重试策略处理 |
| MQTT 鉴权失败 | 保留 MQTT 信息，进入 `auth_failed` 状态并按重连/维护策略处理，不自动重新注册 |
| MQTT worker 卡死 | 重建 MQTT client，必要时重启 worker |
| HTTP worker 卡死 | 取消当前系统 HTTP 任务并应答失败 |

存储和文件系统：

| 异常 | 恢复动作 |
| --- | --- |
| NVS 单字段主副本之一损坏 | 使用有效副本并择机修复 |
| NVS 关键字段主副本都损坏 | 使用默认值或进入受限运行 |
| `cfgfs` 挂载失败 | 重试 3 次后格式化并重新挂载；仍失败则进入受限运行 |
| `cfgfs` 当前区无效 | 扫描双区，选择有效区 |
| `cfgfs` 双区都无效 | 保持管理平面，等待整包配置更新 |
| `datafs` 挂载失败 | 重试 3 次后格式化并重新挂载；仍失败则脚本文件 API 返回失败，不重启 |
| `logfs` 挂载失败 | 重试 3 次后格式化并重新挂载；仍失败则降级本地日志，不重启 |
| `logfs` 写满 | 后台清理到不高于 50%，不阻塞线程 1 和线程 2 |

脚本：

| 异常 | 恢复动作 |
| --- | --- |
| Python 顶层异常 | 上报 `SCRIPT_EXCEPTION`，按策略处理 |
| 脚本 event loop 卡住 | 脚本软看门狗超时，按策略处理 |
| PSRAM 分配失败 | 脚本 API 抛异常或脚本异常，不占用内部 RAM |
| 脚本停止超时 | 记录 `script_stop_timeout`，系统任务继续 |
| 脚本导致重启风暴 | 禁用脚本自动运行，保留管理通道 |

配置和 OTA：

| 异常 | 恢复动作 |
| --- | --- |
| 配置下载失败 | 删除临时文件，保留旧配置 |
| 配置校验失败 | 不切换生效区，保留旧配置 |
| OTA 下载失败 | 保留当前固件 |
| OTA 写入失败 | abort OTA，保留当前固件 |
| OTA 后启动失败 | 由 ESP-IDF OTA 安全机制回退上一可启动固件 |

## 12. 受控重启流程

以下场景允许请求受控重启：

1. OTA 成功。
2. 配置更新成功。
3. 平台下发 `device.reboot`。
4. 脚本异常策略要求重启。
5. 关键任务心跳超时。
6. FreeRTOS 栈溢出或内部 heap 进入危险状态。

受控重启步骤：

```text
gw_reboot_request(reason)
  -> 设置主状态 rebooting
  -> 记录 fault/reboot 摘要
  -> 如 UTC 可信，写入 last_trusted_utc
  -> 尝试上报重启原因
  -> 请求 script_task 停止，最多等待 5 秒
  -> 取消可取消的 HTTP、日志上传和脚本网络请求
  -> 刷新关键 NVS 状态
  -> 投递最后一条本地日志
  -> 短延迟后 esp_restart()
```

重启约束：

1. 重启请求由 `gw_reboot_manager` 串行处理。
2. 已经处于 `rebooting` 时，新的重启请求只更新更高优先级原因，不重复执行流程。
3. 重启前不等待 `logfs` 必须写入成功。
4. 重启前不等待网络必须恢复。
5. 如果受控重启流程卡死，硬件看门狗兜底。

重启原因优先级：

| 优先级 | 原因 |
| ---: | --- |
| 1 | `stack_overflow`、`panic`、`dev_mgr_hang` |
| 2 | `internal_heap_low`、`watchdog_timeout` |
| 3 | `ota_success`、`config_success` |
| 4 | `device_reboot_request`、`factory_reset` |
| 5 | `script_exception`、`script_watchdog_timeout` |

数字越小优先级越高。

## 13. 恢复出厂边界

恢复出厂不是普通异常恢复动作。

固定规则：

1. 设备不得因为网络失败、MQTT 失败、脚本异常、`datafs` 写满、`logfs` 写满或配置下载失败而自动恢复出厂。
2. 远程恢复出厂必须来自 MQTT 方法 `device.factory_reset`，且携带 `confirm=true` 和非空 `reason`。
3. 恢复出厂必须保留 MAC、当前 `device_id`、`product_id`、`group_id` 和出厂必要参数。
4. 恢复出厂可以清除 MQTT 信息、运行参数、配置双区、`datafs`、`logfs`、OTA 临时状态、运行统计和 `last_trusted_utc`。
5. 恢复出厂完成后重启。

健康监控模块只负责：

1. 识别恢复出厂流程是否卡死。
2. 记录恢复出厂失败或超时摘要。
3. 必要时通过重启恢复设备管理能力。

## 14. 状态和诊断上报

健康监控状态建议：

| 字段 | 说明 |
| --- | --- |
| `health.status` | `ok`、`warn`、`degraded`、`fatal_pending` |
| `health.last_fault_module` | 最近故障模块 |
| `health.last_fault_reason` | 最近故障原因 |
| `health.last_fault_uptime_ms` | 最近故障发生时运行时长 |
| `health.last_reboot_reason` | 最近一次固件主动重启原因 |
| `health.boot_guard_active` | 是否处于启动风暴保护 |
| `health.script_disabled_by_fault` | 是否因脚本异常风暴禁用脚本 |
| `health.dev_mgr_stack_free` | `dev_mgr_task` 剩余栈 |
| `health.script_stack_free` | `script_task` 剩余栈 |
| `health.internal_heap_free` | 内部 heap 剩余 |
| `health.psram_free` | PSRAM 剩余 |

上报原则：

1. 状态心跳只携带摘要，不携带大堆栈。
2. 脚本异常堆栈按脚本异常协议上报，超长截断。
3. 故障详细日志通过 `log.query` 查询，超过 8192 字节使用 HTTP POST。
4. `logfs` 不可用时，仍应能通过状态或属性看到最近故障摘要。
5. UTC 不可信时，故障 UTC 填 `0`，但 `uptime_ms` 必须可用。

## 16. 测试建议

1. `dev_mgr_task` 人为停止心跳后能记录故障并重启。
2. `script_task` 顶层异常能进入 `restart_by_watchdog`。
3. 脚本连续异常导致重启达到阈值后，本次启动禁用脚本并保留 `dev_mqtt`。
4. `logfs` 挂载失败时，故障摘要仍可通过状态查询看到。
5. `datafs` 写满时脚本写失败，但线程 1 继续联网和 MQTT 心跳。
6. `cfgfs` 双区无效时设备不无限重启，保持管理通道等待配置修复。
7. 内部 heap 低水位时拒绝非关键任务。
8. PSRAM 低水位时脚本进入异常，不占用内部 RAM 大缓冲。
9. OTA 写入阶段卡住时中止 OTA 并保留当前固件。
10. 受控重启前能保存 `last_trusted_utc`、重启原因和故障摘要。
11. 受控重启流程卡死时硬件看门狗能兜底。
12. Release 版本故障摘要和日志中不出现密码、token 和密钥。

## 17. 实现顺序

1. 实现 `gw_fault_recorder`，先打通 RAM 摘要和 NVS 最小故障字段。
2. 实现 `gw_health_monitor`，注册核心任务和非核心任务健康对象。
3. 接入 `dev_mgr_task`、`script_task`、`log_task` 心跳。
4. 接入栈高水位、内部 heap 和 PSRAM 检查。
5. 实现脚本软看门狗和 `restart_by_watchdog`。
6. 实现 `gw_reboot_manager` 受控重启流程。
7. 实现 `gw_boot_guard` 启动风暴保护。
8. 接入网络、MQTT、HTTP、OTA、配置和时间 worker 的阶段进度。
9. 接入状态/属性上报和日志诊断。
10. 补齐重启、脚本异常、分区异常、内存不足和敏感信息测试。
