# 测试流程

## 1. 文档定位

本文档定义 `ESP32S3R8N16` 网关项目的测试流程。测试按以下三部分组织：

1. 设备端单独测试。
2. 设备和平台联调。
3. 平台基础测试。

测试重心放在设备端。平台侧只要求满足设备接入、命令下发、配置同步和结果查看等基础能力，不做复杂权限、页面细节和后台管理流程的深度专项测试。

相关文档：

| --- | --- |
| `00-ESP32S3R8N16网关固件工程模块设计.md` | 固件模块、任务模型和异常隔离 |
| `01-ESP32S3R8N16网关设备运行设计.md` | 设备启动、联网、配置、OTA 和异常策略 |

| `tests/device-joint/README.md` | 真设备联调脚本说明 |

## 2. 总体测试顺序

建议按以下顺序推进：

```text
设备端单独测试
  |
  v
设备和平台联调
  |
  v
平台基础测试
```

执行原则：

1. 先确认设备自身启动、联网、MQTT、协议应答和配置下载能力正常。
2. 再接入平台，验证平台下发和设备回执闭环。
3. 最后做平台基础冒烟，确保平台不阻塞设备测试。
4. 出现问题时优先定位在当前层级，不直接跳到完整平台流程排查。

## 3. 第一部分：设备端单独测试

### 3.1 测试目标

设备端单独测试用于验证固件自身能力，不依赖完整平台业务流程。

重点验证：

1. 设备能稳定启动。
2. 文件系统、任务和日志基础能力正常。
3. 设备能联网并接入 MQTT。
4. 设备能按协议收发 `down_raw` 和 `up_raw`。
5. 查询、设置、重启、配置更新等核心方法可执行。
6. 异常场景不会导致死机、异常重启或旧配置丢失。

### 3.2 前置条件

设备条件：

| 项目 | 要求 |
| --- | --- |
| 硬件 | ESP32S3R8N16 网关设备 |
| 网络 | 4G/SIM 或当前固件支持的联网方式可用 |
| MQTT 参数 | 已通过出厂或维护流程写入设备 NVS |
| 串口 | 可查看设备启动和运行日志 |
| 固件 | 已烧录待测版本 |

协议参数：

| 项目 | 值 |
| --- | --- |
| `device_id` | 设备 MAC 大写十六进制字符串 |
| `group_id` | `yx_gw` |
| 设备订阅下行 | `/yx_gw/YxzhNode${device_id}/thing/model/down_raw` |
| 设备发布上行 | `/yx_gw/YxzhNode${device_id}/thing/model/up_raw` |

PC 测试目录：

```powershell
cd D:\codex\yx-gateway-1\tests\device-joint
$dev = "设备MAC大写十六进制"
```

### 3.3 固件构建和烧录

```powershell
cd D:\codex\yx-gateway-1\embedded
idf.py build
idf.py -p COM9 flash
```

验收标准：

1. 固件编译成功。
2. 烧录成功。
3. 设备启动后串口无持续异常重启。
4. Release 日志中不输出 MQTT 密码、token、NVS 加密材料和完整敏感 URL。

### 3.4 启动与基础能力测试

检查设备启动日志：

| 测试项 | 预期结果 |
| --- | --- |
| 芯片信息 | 能打印芯片型号、Flash、PSRAM 等基础信息 |
| 设备身份 | 能输出 MAC、`device_id`、`product_id` |
| 固件版本 | 能输出 `major.minor.patch` 格式版本 |
| 分区挂载 | `cfgfs`、`datafs`、`logfs` 挂载成功或按策略降级 |
| 核心任务 | `dev_mgr_task`、`script_task`、`log_task` 创建成功 |
| 看门狗 | 无看门狗复位、栈溢出和任务卡死 |

异常检查：

1. `datafs` 或 `logfs` 异常不得影响设备管理通道。
2. `cfgfs` 异常时设备应保留 MQTT、状态上报和整包配置修复能力。
3. 设备不得因为日志写入失败而重启。

### 3.5 网络和 MQTT 接入测试

先检查设备注册或凭据链路：

```powershell
.\device-joint-test.ps1 -Phase register-device -DeviceId $dev
.\device-joint-test.ps1 -Phase register-server -DeviceId $dev
```

监听设备上行：

```powershell
.\device-joint-test.ps1 -Phase mqtt-listen -DeviceId $dev -Duration 0 -VerboseMqtt
```

验收标准：

1. 设备完成联网。
2. 设备使用本地 MQTT 凭据连接 Broker。
3. 设备成功订阅 `down_raw`。
4. PC 能看到设备发布到 `up_raw`。
5. 首批上报至少包含 `device.login.report`，建议同时检查 `heartbeat.report` 和 `property.report`。
6. Topic 必须是 `/yx_gw/YxzhNode${device_id}/thing/model/...`，不得回退到旧 Topic。

### 3.6 协议命令测试

查询类命令：

```powershell
.\device-joint-test.ps1 -Phase cmd-status -DeviceId $dev -VerboseMqtt
.\device-joint-test.ps1 -Phase cmd-task -DeviceId $dev -VerboseMqtt
.\device-joint-test.ps1 -Phase cmd-property -DeviceId $dev -VerboseMqtt
```

设置类命令：

```powershell
.\device-joint-test.ps1 -Phase cmd-heartbeat -DeviceId $dev -HeartbeatIntervalSec 60 -VerboseMqtt
.\device-joint-test.ps1 -Phase cmd-script-config -DeviceId $dev -ExceptionAction restart_by_watchdog -VerboseMqtt
```

重启命令：

```powershell
.\device-joint-test.ps1 -Phase cmd-reboot -DeviceId $dev -RebootDelaySec 3 -RebootReason joint_test -VerboseMqtt
```

验收标准：

| 测试项 | 预期结果 |
| --- | --- |
| 下行接收 | 设备在 `down_raw` 收到对应 `method` |
| 上行应答 | 设备在 `up_raw` 返回 `{method}.reply` |
| 请求匹配 | 回执 `request_id` 与下发完全一致 |
| 查询类 | `device.status.get`、`task.current.get`、`property.get` 可并行处理 |
| 设置类 | `property.set` 只允许白名单属性 |
| 重启 | 设备先返回 `accepted`，再按延迟重启 |

### 3.7 配置包下载测试

生成 smoke 配置包：

```powershell
.\device-joint-test.ps1 -Phase config-package -DeviceId $dev -Sequence 1
```

启动临时 HTTP 文件服务：

```powershell
.\device-joint-test.ps1 -Phase serve-package -DeviceId $dev -Sequence 1 -HttpPort 18080
```

另开终端下发配置更新：

```powershell
$pkg = "D:\codex\yx-gateway-1\tests\device-joint\packages\$dev\1"
$url = "http://<PC_IP>:18080"
.\device-joint-test.ps1 -Phase cmd-config-update -DeviceId $dev -Sequence 1 -PackageDir $pkg -PackageBaseUrl $url -VerboseMqtt
```

注意：

1. `<PC_IP>` 必须是设备网络可访问的地址。
2. 不允许使用 `127.0.0.1` 或仅 PC 本机可访问的地址作为配置包 URL。

验收标准：

| 测试项 | 预期结果 |
| --- | --- |
| 指令接收 | 设备收到 `config.update` |
| 接收应答 | 设备返回 `config.update.reply`，`message=accepted` |
| 文件下载 | 下载 `manifest.jsonl` 和其中描述的全部文件，至少包含 `config.json`、`main.py` |
| 文件校验 | size 和 sha256 校验通过 |
| 配置切换 | 写入非生效区，校验后切换当前配置区 |
| 最终应答 | 使用同一 `request_id` 返回 `success` |
| 重启 | 配置成功后设备受控重启 |

### 3.8 YMZL/CH37X 硬件读取验证

测试目标：

1. 验证脚本侧 `ch37x` 模块可以启动 CH37X host。
2. 验证真实硬件可枚举并持续读取原始字节。
3. 验证 `ymzl.py` 流式解析器可以从分片字节流中解析完整 YMZL/GS200 帧。

参考配置包源：

```text
tests/device-joint/package-sources/ymzl-hw-read/
```

验收标准：

| 测试项 | 预期结果 |
| --- | --- |
| CH37X 枚举 | 日志出现 `ready=True`，并显示 `vid=0x1A86 pid=0x5523` |
| 原始数据 | `rx` 持续递增，`drop=0` |
| 帧解析 | 日志出现 `ymzl_hw_frame`，`cmd=0x12`，`ext=cmd12` |
| 管理面 | 测试脚本运行时 `device.status.get` 仍可返回，`script_status=running` |
| 日志噪声 | 默认 `log_raw=false`，仅周期记录状态和抽样帧 |

### 3.9 设备异常专项测试

必须覆盖以下异常：

| 场景 | 输入或操作 | 预期结果 |
| --- | --- | --- |
| 非法 JSON | 下发无法解析的 JSON | 返回 `400 invalid_json` 或记录解析失败 |
| 缺少必填字段 | 缺少 `version`、`method` 或 `request_id` | 返回 `400 missing_field` |
| 字段类型错误 | 字符串、整数、对象类型不符合协议 | 返回 `400 invalid_field` |
| Payload 超限 | MQTT Payload 超过 8192 字节 | 拒绝处理，不执行业务 |
| 重复请求 | 重复使用相同 `request_id` | 返回 `425 duplicate_request_id` |
| 设备忙 | 配置更新中下发新的非查询类任务 | 返回 `423 device_busy` |
| 配置版本未递增 | `seq_id <= 当前 seq_id` | 拒绝更新，不下载文件 |
| Manifest 非法 | JSONL 格式错误或缺少描述行 | 返回失败，旧配置继续运行 |
| 缺少核心文件 | 缺少 `config.json` 或 `main.py` | 返回失败，旧配置继续运行 |
| SHA-256 错误 | 文件内容与 sha256 不一致 | 返回失败，旧配置继续运行 |
| HTTP 下载失败 | URL 不可访问或超时 | 返回失败，旧配置继续运行 |
| MQTT 断开 | 断开网络或 Broker | 设备自动重连，脚本线程不被阻塞 |
| `datafs` 写满 | 脚本持续写文件 | 写操作失败，设备管理通道正常 |
| `logfs` 写满 | 产生大量日志 | 触发清理或降级，不影响 MQTT |
| UTC 不可信 | RTC 时间无效且未授时 | 协议应答 `timestamp=0` |

### 3.9 设备长稳测试

建议执行：

| 类型 | 时长 | 检查内容 |
| --- | ---: | --- |
| 短稳 | 2 小时 | 心跳、MQTT 在线、命令下发、日志无异常 |
| 长稳 | 24 小时 | MQTT 重连次数、heap/PSRAM、栈高水位、日志滚动 |
| 恢复 | 按需 | 断网、重启 Broker、设备重启后能恢复上线 |

通过标准：

1. 无异常重启。
2. 无看门狗复位。
3. MQTT 可自动恢复。
4. 心跳持续上报。
5. 资源水位无明显持续泄漏。

## 4. 第二部分：设备和平台联调

### 4.1 测试目标

设备和平台联调用于验证最小业务闭环：

1. 平台能识别设备上线。
2. 平台能下发服务命令。
3. 设备能按协议执行并回执。
4. 平台能根据 `request_id` 更新任务状态。
5. 平台能生成配置包，设备能下载并回执。

平台权限、租户管理、复杂页面交互不作为本阶段重点。

### 4.2 前置条件

1. 设备端单独测试已通过。
2. 平台后端、数据库、MQTT Broker 可用。
3. 平台已预注册设备，`device_id` 为设备 MAC 大写十六进制。
4. 设备已绑定到测试组。
5. 后台配置包地址必须是设备可访问的地址，不能是 `127.0.0.1`。

### 4.3 设备上线联调

操作步骤：

1. 平台预注册设备。
2. 租户端将设备绑定到测试组。
3. 设备上电并连接 MQTT。
4. 设备发布 `device.login.report`。
5. 平台设备列表查看设备状态。

验收标准：

| 测试项 | 预期结果 |
| --- | --- |
| 设备状态 | 平台显示在线 |
| 心跳 | 平台能看到最近心跳时间 |
| 属性 | 平台能看到固件版本、配置 sequence、网络状态 |
| Topic | 平台订阅的是设备 `up_raw` 精确 Topic |

### 4.4 平台服务命令联调

在平台侧下发：

1. 状态查询：`device.status.get`
2. 当前任务查询：`task.current.get`
3. 属性查询：`property.get`
4. 属性设置：`property.set`
5. 重启：`device.reboot`

验收标准：

| 测试项 | 预期结果 |
| --- | --- |
| 下发 Topic | 平台发布到设备 `down_raw` |
| 设备执行 | 设备按 `method` 执行业务 |
| 设备回执 | 设备发布 `{method}.reply` 到 `up_raw` |
| 请求匹配 | 平台任务 `request_id` 与设备回执一致 |
| 任务状态 | 成功时变为 `succeeded`，失败时变为 `failed` |

### 4.5 平台配置同步联调

操作步骤：

1. 平台脚本配置页保存草稿。
2. 执行“保存并同步测试组”。
3. 平台生成配置包。
4. 平台下发 `config.update`。
5. 设备下载并校验配置包。
6. 设备返回 `accepted` 和最终结果。
7. 平台同步批次和设备任务更新状态。

验收标准：

| 测试项 | 预期结果 |
| --- | --- |
| 配置包 | 包含 `manifest.jsonl`、`config.json`、`main.py` |
| 下发 | 设备收到 `config.update` |
| 受理回执 | 设备返回 `accepted` |
| 最终回执 | 成功返回 `success`，失败返回 `failed` 和原因 |
| 后台任务 | 根据设备最终回执更新任务状态 |
| 配置状态 | 设备当前配置 sequence 更新 |

### 4.6 联调失败场景

| 场景 | 预期结果 |
| --- | --- |
| 设备离线时下发命令 | 平台任务保持等待、超时或失败，不得误判成功 |
| 设备返回 `failed` | 平台任务变为 `failed` |
| 设备回执缺少合法 `stage` | 平台任务变为 `failed`，记录 `invalid_reply_stage` |
| 设备返回 `version_not_increased` | 平台记录失败原因 |
| 设备回执 `request_id` 不一致 | 平台不得匹配到错误任务 |
| 配置包 URL 设备不可访问 | 设备返回下载失败，平台任务失败 |

## 7. 问题定位建议

| 现象 | 优先检查 |
| --- | --- |
| 设备不上线 | 设备 MQTT 凭据、网络状态、`up_raw` Topic |
| 平台看不到在线 | 设备是否已预注册，设备是否发送 `device.login.report` |
| 命令一直 pending | 设备是否收到 `down_raw`，回执 `request_id` 是否一致 |
| 配置下载失败 | `manifest_url` 是否设备可访问，不能使用 `127.0.0.1` |
| 设备配置失败 | `seq_id`、manifest 格式、size、sha256、核心文件是否完整 |
| 设备频繁重启 | 串口重启原因、看门狗、脚本异常策略、栈高水位 |
| MQTT 连接成功但订阅失败 | Topic ACL 是否放开 `/yx_gw/YxzhNode${device_id}/thing/model/down_raw` |
| 日志异常增多 | `logfs` 使用率、日志清理、敏感信息脱敏 |
