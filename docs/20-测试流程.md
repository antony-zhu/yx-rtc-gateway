# 测试流程

## 1. 范围和原则

本流程覆盖当前仓库中的两部分：

1. `embedded`：ESP32-S3 网关固件、4G、IO、CH37X、MQTT 和定时任务。
2. `app`：通过 BLE 配置网关定时任务的 Flutter Android APP。

固件默认只构建 4G 版本。除非明确要求以太网测试，否则不要构建或烧录以太网版本。仓库已经删除 MicroPython，测试中不再检查 `main.py`、`script_task`、Python 模块或脚本配置包。

## 2. 默认 4G 固件构建

在已激活 ESP-IDF 5.5 环境的 PowerShell 中执行：

```powershell
cd D:\codex\yx_gateway\embedded
idf.py --no-ccache -B build-4g -D GW_NETWORK_TARGET=4G build
```

验收标准：

1. `yx_gateway.bin`、`bootloader.bin` 和分区表生成成功。
2. `generated/gw_network_build.h` 中 `GW_NETWORK_TARGET_4G=1`、`GW_NETWORK_TARGET_ETHERNET=0`。
3. `compile_commands.json` 中有且只有 `gw_4g_ecm.c`，没有 `gw_ethernet.c`。
4. 固件大小不超过 3 MiB 应用分区。

可用以下 PowerShell 检查驱动源码选择：

```powershell
$commands = Get-Content -Raw build-4g\compile_commands.json | ConvertFrom-Json
($commands | Where-Object { $_.file -like '*gw_4g_ecm.c' }).Count
($commands | Where-Object { $_.file -like '*gw_ethernet.c' }).Count
```

只有明确要求以太网固件或以太网专项测试时，才使用独立目录：

```powershell
idf.py --no-ccache -B build-ethernet -D GW_NETWORK_TARGET=ETHERNET build
```

## 3. COM9 烧录和运行冒烟

确认 COM9 是目标设备，且没有其他串口工具占用：

```powershell
Get-PnpDevice -Class Ports -PresentOnly | Select-Object FriendlyName, Status
```

保留设备 NVS 凭据，正常烧录时不要执行 `erase-flash`：

```powershell
cd D:\codex\yx_gateway\embedded
idf.py --no-ccache -B build-4g -p COM9 flash
idf.py --no-ccache -B build-4g -p COM9 monitor
```

启动日志至少应满足：

| 模块 | 预期结果 |
| --- | --- |
| 芯片和内存 | ESP32-S3、16 MiB Flash、8 MiB PSRAM 初始化成功 |
| 板级驱动 | RS485 和 GPIO40/41/42 初始化成功 |
| 存储 | NVS 身份可读，`cfgfs`、`datafs`、`logfs` 挂载成功 |
| 时间 | 外部 RTC 可检测；定时任务执行服务保持暂停，NVS 任务表不加载 |
| BLE | 广播名称和 `device_id` 正确，配置服务启动 |
| CH37X | 枚举 `VID=0x1A86 PID=0x5523` 并进入 READY |
| 4G | SIM、驻网、ECM 拨号、DHCP 成功，日志出现 `4g ready` |
| MQTT | 注册成功并出现 `business MQTT online`；业务上行 QoS0、下行订阅 QoS1 |

至少观察两个相邻的 `dongle_mqtt: status` 周期。通过标准：

1. `mqtt=online` 保持不变。
2. `published` 持续递增。
3. `queue_drop=0`、`mqtt_err=0`、`down_drop=0`、`tx_err=0`、`raw_drop=0`。
4. 无 panic、看门狗复位、栈溢出和反复重启。

## 4. MQTT 和 Cron 定时任务

业务 MQTT Topic 为：

| 方向 | Topic |
| --- | --- |
| 平台下发 | `yx_gw/YxzhNode<EFUSE_MAC>/thing/model/down_raw` |
| 设备上报 | `yx_gw/YxzhNode<EFUSE_MAC>/thing/model/up_raw` |

其中 `EFUSE_MAC` 为 ESP32 eFuse MAC 的 12 位大写十六进制文本；当前生产构建暂停
Cron 执行服务，相关增删改查和到期动作测试需在明确启用调度器后执行。

完整报文见 `24-Cron定时任务MQTT协议.md`。建议按以下顺序验证：

1. `command.capabilities`：确认固件白名单命令和版本。
2. `schedule.upsert`：创建一个未来分钟执行的 Cron 任务。
3. `schedule.get`：核对 `task_id`、`revision`、Cron 和命令参数。
4. `schedule.list`：核对任务表版本和任务摘要。
5. （启用调度器时）等待到期：确认收到一次且仅一次 `schedule.fired`。
6. `schedule.enable`：停用、重新启用并核对版本递增。
7. `schedule.delete`：删除任务并确认再次查询返回不存在。

协议专项至少覆盖：

| 场景 | 预期结果 |
| --- | --- |
| 非法 Cron | 保存阶段拒绝，不创建任务 |
| 未知命令或版本 | 保存阶段拒绝，不在到期时才失败 |
| revision 冲突 | 返回版本冲突，原任务不变 |
| 重复 `request_id` | 一小时保护期内不重复执行变更 |
| 请求缓存已满 | 返回设备忙，不提前淘汰仍在保护期内的请求 |
| 16 个任务同一分钟到期 | 所有动作最终进入执行队列，不因队列容量丢失 |
| UTC 不可信 | Cron 不执行，恢复可信时间后重新对账 |
| 重启或校时跨过计划点 | 不补执行已经错过的 Cron |

外部 MQTT 测试客户端不得复用设备正在使用的 `client_id`，否则 Broker 会踢掉设备连接，造成假故障。

## 5. 4G 和 IO 恢复专项

| 场景 | 操作 | 预期结果 |
| --- | --- | --- |
| 4G 断链 | 断开天线、SIM 网络或模组链路后恢复 | supervisor 进入退避重拨，最终恢复 MQTT |
| 事件队列拥塞时断链 | 制造高优先级事件突发并触发断网 | 周期状态对账仍能启动恢复，不永久停在 disconnected |
| ECM 拨号失败 | 让 `AT+MDIALUP?` 始终未连接 | 不得进入 READY，按失败流程重试 |
| CH37X 数据上行 | 接入 `VID=1A86 PID=5523` 设备并持续发数据 | `uplink` 和 `published` 递增，丢弃和发送错误为 0 |
| RS485 | 按目标波特率收发已知帧 | 无串帧、超时和波特率切换异常 |
| RTC | 冷启动、断电再启动、网络校时 | 时间有效，调度器边界对账符合预期 |
| 指示灯 | MQTT、任务和错误状态切换 | GPIO40/41/42 极性和状态正确 |

## 6. Flutter APP 检查

```powershell
cd D:\codex\yx_gateway\app
flutter analyze
flutter test
flutter build apk --debug
```

验收标准：

1. 静态分析无错误。
2. BLE 分片、事务队列、设备扫描、仓库状态、幂等键和任务页面测试全部通过。
3. Debug APK 成功生成在 `build\app\outputs\flutter-apk\app-debug.apk`。
4. 真机可扫描 `YX-xxxx`，连接后能读取任务、同步时间并完成任务增删改。

## 7. 当前自动化测试边界

Flutter APP 已有自动化测试。固件当前还没有第一方 Unity 或主机单元测试工程，因此 Cron 边界、NVS 掉电窗口、断网恢复、16 任务同分钟和 IO 并发仍需以构建、静态审查和实机专项覆盖。

后续补固件自动化测试时，优先顺序为：

1. Cron 解析边界、DOM/DOW OR 语义、星期 7、时区和跳时。
2. 16 任务同分钟到期以及 1 秒级阻塞命令。
3. NVS 重启恢复、写失败和断电窗口。
4. MQTT 定时任务增删改查、重复请求、版本冲突和丢应答重传。
5. CH37X 回调注销、stop/start/disconnect 并发和 RS485 事务。

每轮测试至少记录固件版本、设备 MAC、构建目标、串口、MQTT 在线时长、发布计数、错误计数和未覆盖项。
