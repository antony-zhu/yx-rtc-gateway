## 2. 总体原则

1. 模块之间只通过明确接口、事件队列、状态快照和请求上下文交互。
2. `dev_mgr_task` 是设备管理平面的主控任务，负责状态机推进和业务编排。
3. `script_task` 是唯一允许进入 MicroPython VM 的任务。
4. MQTT 回调、HTTP 回调、timer callback、驱动回调和 ISR 不得直接执行长耗时业务。
5. C 层不得从非 `script_task` 上下文直接调用 Python。
6. 所有长耗时操作必须投递到 worker，由 worker 再通过事件返回结果。
7. 所有跨模块结果统一使用 `gw_result_t` 表达。
8. 所有协议时间戳统一使用 UTC 毫秒；UTC 不可信时填 `0`。
9. 所有超时、重试、队列清理、健康扫描统一使用单调运行时间，不依赖 UTC。
10. 系统模块接口不得暴露 MQTT 密码、NVS 加密材料、ESP-IDF 私有 handle 或 Python 对象指针。

## 3. 接口分层

模块接口按四类定义：

| 类型 | 说明 | 典型使用 |
| --- | --- | --- |
| 同步查询接口 | 只读、短耗时、无阻塞或短锁 | 查询状态、参数、资源余量 |
| 异步请求接口 | 提交请求后立即返回，结果通过事件返回 | 联网、HTTP 下载、OTA、配置更新 |
| 事件通知接口 | 模块把状态变化或结果投递给拥有者 | 网络就绪、MQTT 断开、脚本异常 |
| 状态快照接口 | 保存当前事实，允许被状态聚合模块读取 | `network_status`、`mqtt_status`、`script_status` |

固定约束：

1. 回调只允许更新状态快照、复制必要数据、投递事件或唤醒任务。
2. 查询接口不得触发联网、下载、Flash 写入、Python 执行等副作用。
3. 请求接口必须明确请求上下文、取消方式和结果事件。
4. 状态快照是当前事实，不代表每一次状态迁移都被完整保存。
5. 一次性输入必须进入消息队列，不能只放在状态快照里。

## 4. 统一结果结构

跨模块结果统一使用 `gw_result_t`，协议应答、日志记录、诊断字段都从该结构派生。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 处理结果码；模块内部成功统一为 `0` |
| `reason_code` | string | 稳定英文短码，对应 `17` 中的 reason_code |
| `http_status` | integer | HTTP 状态码；未收到 HTTP 响应时为 `0` |
| `server_code` | integer | 服务端 JSON `code`；没有应用层 code 时为 `0` |
| `esp_err` | integer | ESP-IDF 错误码；无 ESP 错误时为 `0` |
| `detail` | string | 简短诊断摘要，不包含敏感信息 |

结果规则：

1. `code=0` 表示模块内部成功；发布到 MQTT 时按协议映射为对应业务 code。
2. `reason_code` 必须使用稳定短码，不使用中文、不拼接动态内容。
3. `detail` 只用于诊断，不作为平台业务判断的唯一依据。
4. HTTP 失败必须尽量填充 `http_status`、`server_code` 和 `reason_code`。
5. 不得在 `detail` 中包含密码、token、签名、密钥、完整带敏感 query 的 URL。

## 5. 请求上下文

由 MQTT 触发或跨 worker 执行的请求必须携带请求上下文。

| 字段 | 说明 |
| --- | --- |
| `request_id` | 平台请求 ID；非平台请求可为空 |
| `method` | 平台方法名或内部请求名 |
| `source` | 请求来源，例如 `protocol`、`scheduler`、`script_api` |
| `reply_topic` | 平台应答 Topic；非平台请求为空 |
| `started_uptime_ms` | 本地单调开始时间 |
| `started_utc_ms` | UTC 可信时为毫秒时间戳，否则为 `0` |
| `cancel_token` | 取消标记或任务句柄 |
| `flags` | 请求标志，例如 `mqtt_triggered`、`scheduled`、`need_reboot` |

规则：

1. 凡是 MQTT 指令触发且需要 HTTP/HTTPS 的操作，都必须保留同一个 `request_id` 到最终 MQTT 应答。
2. 固件不执行 HTTP 注册；MQTT 信息缺失只更新本地状态和诊断。
3. 查询类请求可以并行；非查询类请求必须经过 `gw_protocol_manager` 的互斥任务保护。
4. 同一时间运行中的 `request_id` 永远不能重复。
5. 最近 32 个平台 `request_id` 记录由协议模块统一维护，已完成记录 1 小时后清理。

## 6. 事件模型

系统内部事件统一使用 `GW_EVT_*` 命名。事件只描述“发生了什么”，不在事件名中塞入处理策略。

事件包建议字段：

| 字段 | 说明 |
| --- | --- |
| `event_id` | 事件枚举，例如 `GW_EVT_NET_READY` |
| `source` | 事件来源模块 |
| `target` | 目标模块或任务 |
| `priority` | `critical`、`high`、`normal`、`low` |
| `request_id` | 关联平台请求，没有则为空 |
| `method` | 关联方法，没有则为空 |
| `uptime_ms` | 本地单调时间 |
| `timestamp` | UTC 可信时为毫秒时间戳，否则为 `0` |
| `result` | `gw_result_t`，成功事件也可携带 |
| `payload_type` | 小型结构、buffer 引用或无 payload |
| `payload` | 可选负载指针，不允许指向栈内存 |
| `payload_len` | 负载长度 |
| `release_cb` | 负载释放函数；无动态负载时为空 |

事件所有权：

1. 事件投递成功后，带 `release_cb` 的 payload 所有权转移给接收方。
2. 事件投递失败时，发送方必须释放 payload 或执行本模块满队列策略。
3. 大 payload 不得直接复制进 `dev_mgr_event_queue` 的事件结构，应使用 buffer 引用。
4. 指向 Python 对象、ESP-IDF 私有上下文、临时栈内存的指针不得作为事件 payload。
5. 接收方处理完成后必须调用 `release_cb` 或按约定释放资源。

## 7. 队列定义和满队列策略

固定队列建议：

| 队列 | 默认容量 | 生产者 | 消费者 | 满队列策略 |
| --- | ---: | --- | --- | --- |
| `dev_mgr_event_queue` | 32 | worker、MQTT、time、script、log、health | `dev_mgr_task` | 核心事件置 pending 标志并唤醒，普通事件可合并 |
| `gw_mqtt_client_cmd_queue` | 每 client 16 | `dev_mqtt` 管理侧、脚本 API | `gw_mqtt_client` worker | 返回队列满错误 |
| `script_event_queue` | 每对象 32 | C service、MQTT、HTTP、WS、外设 | `script_task` | 数据事件 `drop_new` 并计数，状态事件合并 |
| `log_queue` | 64 | 所有模块 | `log_task` | 非阻塞投递，按等级丢弃并计数 |
| `health_report_queue` | 16 | worker、核心任务 | `gw_health_monitor` | 状态类合并，fatal 事件置 pending 标志 |

核心事件不得静默丢弃：

| 类型 | 处理 |
| --- | --- |
| `critical` | 队列满时设置模块 pending 标志，直接通知目标任务，记录故障摘要 |
| `high` | 尽量入队；失败时更新状态快照并记录 dropped 计数 |
| `normal` | 允许合并同类状态事件 |
| `low` | 允许丢弃，但必须增加 dropped 计数 |

说明：

1. 队列满不能导致调用方长期阻塞。
2. 状态类事件可合并，因为状态快照保存当前事实。
3. 消息类事件不可只合并，丢弃时必须增加 dropped/overflow 计数。
4. `dev_mgr_task` 收到 pending 标志后，应主动重新读取相关模块状态快照。
5. 满队列本身是可诊断事件，应进入日志或诊断字段。

## 9. MQTT 事件到 Python 的规则

脚本 MQTT 事件路径固定为：

```text
esp-mqtt callback
  -> gw_mqtt_client
  -> script_mqtt_adapter
  -> script_mqtt C 状态快照 / C 消息队列
  -> waker
  -> script_task
  -> Python mqtt.recv()/poll() 或 mqtt callback
```

规则：

1. `dev_mqtt` 事件只进入设备管理平面，不进入 Python。
2. 脚本 MQTT 最多 4 个 client；每个 client 使用独立 handle、状态快照、消息队列和 DATA 分片组包状态。
3. ESP-MQTT callback 不得直接调用 Python callback。
4. MQTT DATA 分片必须在 C 层组包成完整消息后再进入脚本事件队列。
5. 脚本 MQTT 完整消息最大 8192 字节。
6. 脚本侧 `recv()` / `poll()` 返回的是脚本业务 MQTT 事件，不包含平台 `/yx_gw/YxzhNode${device_id}/thing/model/...` 协议事件。
7. 队列满时，脚本 MQTT 数据事件按 `drop_new` 处理并增加 dropped 计数。
8. `mqtt.on()` 注册的 Python callback 只由 MicroPython scheduler/waker 在 `script_task` 上下文调用，callback 异常必须捕获并打印或上报，不允许穿透到 ESP-MQTT callback。

脚本 MQTT 事件对象建议：

| 字段 | 说明 |
| --- | --- |
| `handle` | 事件所属脚本 MQTT client handle |
| `name` | client 诊断名称 |
| `type` | `data`、`connected`、`disconnected`、`subscribed`、`published`、`error` |
| `topic` | MQTT Topic；非数据事件可为空 |
| `payload` | `bytes`；仅 `data` 事件存在 |
| `payload_len` | Payload 长度 |
| `msg_id` | MQTT 消息 ID 或发布/订阅确认 ID |
| `timestamp_ms` | UTC 可信时为毫秒时间戳，否则为 `0` |
| `reason` | 错误或诊断原因 |

## 10. C 与 Python 通用事件

Python 侧公开 API 统一采用：

```python
status = obj.status()
evt = obj.poll()
stats = obj.stats()
```

通用事件类型：

| 类型 | 来源 | 说明 |
| --- | --- | --- |
| `mqtt.data` | `script_mqtt` | 用户业务 MQTT 收到消息 |
| `mqtt.status` | `script_mqtt` | 脚本 MQTT 状态变化 |
| `http.done` | `script_http` | 脚本异步 HTTP 完成 |
| `ws.data` | `script_ws` | WebSocket 收到数据 |
| `board.input` | driver adapter | 外设输入或业务帧 |
| `system.status` | system adapter | 网络、UTC 或系统状态摘要变化 |
| `runtime.stop_requested` | `gw_script_manager` | 线程 1 请求脚本退出 |

Python 侧规则：

1. waker 只表示“可能有状态或消息可读”，不表示事件数量。
2. `poll()` 无消息时返回 `None`。
3. 单轮 drain 默认 `max_batch=5`。
4. 用户 callback 异常必须被 Python 包装层捕获，并上报脚本异常。
5. 脚本退出时必须清理所有 C 队列、waker、callback 和异步请求。

## 11. 模块对外接口约定

### 11.1 设备管理主控

| 接口 | 类型 | 说明 |
| --- | --- | --- |
| `gw_supervisor_start()` | 异步启动 | 创建 `dev_mgr_task` 并进入主状态机 |
| `gw_supervisor_post_event(evt)` | 事件通知 | 向 `dev_mgr_task` 投递事件 |
| `gw_supervisor_get_state(out)` | 同步查询 | 获取主状态、任务状态和诊断摘要 |
| `gw_supervisor_request_reboot(reason)` | 异步请求 | 发起受控重启 |
| `gw_supervisor_request_factory_reset(ctx)` | 异步请求 | 发起恢复出厂 |

约束：

1. 只有 `gw_supervisor` 可以最终决定设备主状态。
2. 其他模块不得直接修改 `status`、`task_status` 等主状态字段。
3. 受控重启必须经过 `gw_reboot_manager`，不得在普通 worker 中直接 `esp_restart()`。

### 11.2 存储与文件系统

| 接口 | 类型 | 说明 |
| --- | --- | --- |
| `storage_init()` | 同步初始化 | 初始化 NVS 和系统参数加密 |
| `fs_mount_all()` | 同步初始化 | 挂载 `cfgfs`、`datafs`、`logfs` |
| `fs_get_info(partition, out)` | 同步查询 | 查询分区容量和使用量 |
| `nvs_secure_get(namespace, key, out)` | 同步查询 | 加密读取系统参数 |
| `nvs_secure_set(namespace, key, value)` | 同步写入 | 加密写入系统参数 |
| `fs_resolve_data_path(user_path, out)` | 同步查询 | 把脚本路径规范化到 `datafs:/` |

约束：

1. 用户脚本参数不进系统 NVS，应放在 `config.json` 或 `datafs:/`。
2. `device_id` 和 `product_id` 恢复出厂时保留。
3. `datafs:/` 和 `logfs:/` 故障不得影响设备管理平面。

### 11.3 网络和 HTTP

| 接口 | 类型 | 说明 |
| --- | --- | --- |
| `gw_net_start(profile)` | 异步请求 | 启动默认 4G 联网 |
| `gw_net_stop(reason)` | 异步请求 | 停止网络 |
| `gw_net_get_status(out)` | 同步查询 | 获取网络状态快照 |
| `gw_net_get_modem_info(out)` | 同步查询 | 获取 4G 模组缓存信息，如 IMEI、ICCID、SIM、信号和注册状态 |
| `gw_http_download_start(req)` | 异步请求 | 配置或 OTA 下载 |
| `gw_http_upload_start(req)` | 异步请求 | 日志或文件 HTTP POST 上传 |
| `gw_http_cancel(cancel_token)` | 异步请求 | 取消 HTTP 请求 |

约束：

1. HTTP 连接超时默认 10 秒，应答间隔超时默认 3 秒，不定义总超时。
2. MQTT 触发的 HTTP 操作必须通过同一个 `request_id` 回应最终结果。
3. 脚本 HTTP 不得用于配置更新、OTA 或系统日志上传。
4. 4G public profile 固定为 `4g`；USB ECM、CDC、AT interface 和 endpoint 修正属于网络模块内部实现。
5. 4G 启动阶段 AT 通道由系统独占，脚本只能读取缓存状态或通过后续受控 API 发起允许的查询。

### 11.4 MQTT 基础封装

| 接口 | 类型 | 说明 |

约束：

## 12. 执行上下文限制

| 上下文 | 允许 | 禁止 |
| --- | --- | --- |
| ESP-IDF callback | 复制小数据、更新状态、投递事件 | HTTP 下载、Flash 写入、Python 调用、长阻塞 |
| MQTT callback | 组包、长度检查、投递 MQTT 事件 | 协议执行、配置更新、OTA、Python callback |
| HTTP callback | 刷新应答间隔计时、写流式数据、报告进度 | 发布 MQTT 最终应答、执行 Python |
| timer callback | 投递调度事件 | 执行联网、下载、清理、日志扫描 |
| worker task | 执行长耗时操作、阶段上报 | 直接修改主状态、直接进入 Python |
| `dev_mgr_task` | 状态机推进、任务编排、协议应答调度 | 长时间阻塞、Flash 大文件写入 |
| `script_task` | MicroPython VM、Python 事件循环 | 执行设备管理 OTA、直接改系统 NVS |

## 13. MQTT 应答与事件结果关系

MQTT 应答由协议模块统一生成，业务模块只返回 `gw_result_t` 和必要数据。

固定规则：

1. 接收应答和最终应答必须使用同一个 `request_id`。
2. 进度上报必须保留同一个 `request_id`。
3. MQTT 触发 HTTP 操作的最终成功或失败必须通过 MQTT 返回。
4. 查询类方法如果能直接生成结果，不需要进入 worker。
5. 查询结果预计超过 8192 字节时，必须要求平台提供 URL 并走 HTTP POST。
6. 发布 MQTT 应答失败时，不重试到无限；记录日志和诊断，由 MQTT 重连流程处理。

业务模块返回结果到 MQTT 的映射：

| 模块结果 | MQTT code | message / reason_code |
| --- | ---: | --- |
| 成功 | `0` | `ok` |
| 参数非法 | `400` | `invalid_field` 或更具体原因 |
| 方法不支持 | `404` | `method_not_found` |
| 版本未递增 | `409` | `version_not_increased` |
| 设备忙 | `423` | `device_busy` |
| 重复 `request_id` | `425` | `duplicate_request_id` |
| Payload 过大 | `413` | `payload_too_large` |
| 存储空间不足 | `507` | `storage_full` |
| 内部错误 | `500` | `internal_error` |

## 14. 实现检查项

实现模块时至少检查：

1. 是否在错误上下文中直接调用了 Python。
2. 是否在 callback 或 timer 中执行了长耗时操作。
3. 是否有无界队列、无界 buffer 或无限重试。
4. 队列满是否有明确策略和计数。
5. 跨 worker payload 是否有清晰所有权和释放路径。
6. MQTT 触发 HTTP 操作是否保留同一个 `request_id`。
7. UTC 不可信时是否填 `timestamp=0`，并使用 uptime 做超时。
8. 敏感信息是否被脱敏或禁止输出。
9. `datafs:/`、`logfs:/` 故障是否不会拖垮设备管理平面。
10. 脚本侧大缓冲是否使用 PSRAM，任务栈是否仍在内部 RAM。
