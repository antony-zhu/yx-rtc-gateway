# 模块设计 - 设备管理主流程

## 1. 文档定位

本文档细化 `ESP32S3R8N16` 网关固件中的设备管理主流程，也就是运行设计文档中所说的“线程 1”。这里的线程 1 不是单一阻塞线程，而是设备管理平面：由 `dev_mgr_task` 作为主控任务，按需要拉起网络、MQTT、HTTP、OTA、授时等辅助任务。

本文档重点定义设备从开机到上线、配置检查、OTA、运行心跳、平台指令处理、异常降级和重启协调的主状态机。

## 2. 设计目标

1. 线程 1 负责设备管理，不阻塞线程 2 的脚本启动和运行。
2. 默认使用 4G 联网，APN 默认空字符串。
3. MQTT 连接信息必须由出厂/产测流程写入 NVS。
4. 固件有有效 MQTT 信息时直接连接 `dev_mqtt`；缺失时进入 `mqtt_status=not_configured`，不自动 HTTP 注册。
5. `dev_mqtt` 在线后立即上报状态、属性、配置版本和存储资源。
6. 上线后检查 OTA 和配置更新；OTA 优先于配置更新。
7. 定时 OTA 和定时配置更新必须依赖可信 UTC。
8. MQTT 指令统一经过协议模块校验、去重、互斥和分发。
9. 由 MQTT 发起且需要 HTTP 的操作，必须使用同一个 `request_id` 返回最终结果。
10. 网络重连、MQTT 重连、授时失败均不得阻塞脚本。
11. 需要 OTA、配置更新、恢复出厂或重启时，由线程 1 统一协调脚本停止。

## 3. 模块边界

建议目录：

```text
main/
  gw/
    gw_supervisor.c
    gw_net_manager.c
    gw_mqtt_manager.c
    gw_protocol_manager.c
    gw_config_manager.c
    gw_script_manager.c
    gw_state.c
```

建议职责拆分：

| 子模块 | 主要职责 |
| --- | --- |
| `gw_supervisor` | 设备管理主状态机、启动顺序、运行循环、异常降级 |
| `gw_state` | 设备状态、网络状态、MQTT 状态、脚本状态、任务状态聚合 |
| `gw_net_manager` | 默认 4G 联网、网络重连、网络状态事件 |
| `gw_mqtt_manager` | 基于 `gw_mqtt_client` 创建和管理 `dev_mqtt` 连接、订阅、发布、重连 |
| `gw_protocol_manager` | MQTT 下行校验、`request_id` 去重、指令分发、应答 |
| `gw_config_manager` | 配置版本检查、整包配置更新、配置区切换 |
| `gw_script_manager` | 与 `script_task` 协同启动、停止、异常通知 |
| `time_manager` | RTC/UTC 可信判断、授时、调度时间判断 |
| `ota_manager` | OTA 接收、下载、校验、升级和进度上报 |

设备管理主流程不负责：

1. 不直接实现 AES 加密和 LittleFS 路径解析。
2. 不直接执行 Python 代码。
3. 不在 MQTT 回调中执行 HTTP 下载、OTA 写 Flash、配置写文件等长耗时操作。
4. 不缓存离线 MQTT 上报。
5. 不因为 `datafs` 或 `logfs` 故障停止设备管理能力。

## 4. 任务模型

固定核心任务：

| 任务 | 栈大小 | 内存来源 | 职责 |
| --- | ---: | --- | --- |
| `dev_mgr_task` | 24 KB | 内部 RAM | 设备管理主状态机 |
| `script_task` | 64 KB | 内部 RAM | Python 脚本运行 |
| `log_task` | 8 KB | 内部 RAM | 日志写入和清理 |

线程 1 可管理的辅助任务：

| 辅助任务 | 建议栈 | 说明 |
| --- | ---: | --- |
| `net_worker` | 8 KB | 4G 联网、断线检测、网络重连 |
| `mqtt_worker` | 8 KB | MQTT 连接、订阅、收包、重连 |
| `http_worker` | 12 KB | MQTT 触发的 HTTP 下载、上传 |
| `ota_worker` | 12 KB | OTA 下载、校验、写入 ESP-IDF OTA 分区 |
| `time_worker` | 6 KB | RTC、4G、MQTT、HTTPS、SNTP 授时 |

任务约束：

1. 所有任务栈使用内部 RAM。
2. Python VM heap、脚本对象和脚本大缓冲使用 PSRAM。
3. `dev_mgr_task` 只做状态机推进和任务调度，不执行长时间阻塞操作。
4. 辅助任务通过队列、事件组或消息邮箱与 `dev_mgr_task` 通信。
5. MQTT 回调只投递事件，不直接执行业务。
6. 日志写入只投递到 `log_task`，不得在设备管理任务中扫描或清理 `logfs`。
7. 辅助任务栈大小为建议初值，后续应根据栈高水位和实际库调用深度调整。

## 5. 核心状态机

设备管理主状态建议如下：

| 状态 | 说明 |
| --- | --- |
| `booting` | 设备刚启动，基础模块初始化中 |
| `local_loading` | 读取 NVS、配置双区、RTC、运行参数 |
| `net_starting` | 正在启动默认网络 |
| `mqtt_not_configured` | 缺少出厂 MQTT 连接信息，无法连接 `dev_mqtt` |
| `mqtt_connecting` | 正在连接 `dev_mqtt` |
| `online` | 管理通道在线，正常运行 |
| `config_checking` | 正在检查或等待配置更新 |
| `config_updating` | 正在整包更新配置 |
| `ota_checking` | 正在检查或等待 OTA |
| `ota_upgrading` | 正在 OTA 升级 |
| `degraded` | 受限运行，仍保留管理能力 |
| `rebooting` | 正在协调重启 |
| `factory_resetting` | 正在恢复出厂 |

状态转换主线：

```text
booting
  -> local_loading
  -> net_starting
  -> mqtt_connecting 或 mqtt_not_configured
  -> online
  -> config_checking / ota_checking
  -> online
  -> 运行循环
```

降级主线：

```text
cfgfs 异常
  -> degraded
  -> 保留联网、MQTT、状态上报、整包配置修复能力

datafs 异常
  -> online 或 degraded
  -> 脚本文件 API 失败，不影响设备管理

logfs 异常
  -> online
  -> 关闭本地持久化日志，不影响设备管理
```

## 6. 启动流程

`app_main` 建议启动顺序：

1. 初始化基础硬件、Flash、NVS。
2. 初始化 NVS 加密存储。
3. 挂载 `cfgfs`、`datafs`、`logfs`。
4. 读取出厂参数和运行参数。
5. 读取 `last_trusted_utc`，校验 RTC 是否可信。
6. 扫描配置双区，确定当前生效区。
7. 校验当前生效区 `manifest.jsonl`、`config.json`、`main.py`。
8. 初始化日志任务。
9. 创建 `dev_mgr_task`。
10. 创建 `script_task`。
11. 两个核心任务并行运行。

启动约束：

1. `script_task` 不等待联网或 MQTT 连接成功。
2. 如果当前配置有效，脚本可基于本地 `main.py` 先运行。
3. 如果当前配置无效，但存在上一份有效脚本或出厂默认脚本，可按脚本策略运行。
4. 如果没有可运行脚本，`script_status` 上报为 `stopped` 或 `error`，线程 1 仍继续联网和配置修复。
5. `cfgfs` 双区无效时，线程 1 进入受限运行，等待平台整包配置更新。

## 7. dev_mgr_task 主循环

`dev_mgr_task` 主循环建议采用事件驱动：

```text
while true:
  等待事件或定时器
  处理网络事件
  处理 MQTT 连接事件
  处理 MQTT 下行事件
  处理授时事件
  处理配置/OTA 事件
  处理脚本事件
  更新状态机
  必要时上报状态或属性
```

事件来源：

| 事件 | 来源 | 说明 |
| --- | --- | --- |
| `NET_READY` | `net_worker` | 网络可用 |
| `NET_LOST` | `net_worker` | 网络断开 |
| `MQTT_CONNECTED` | `mqtt_worker` | `dev_mqtt` 已连接 |
| `MQTT_DISCONNECTED` | `mqtt_worker` | `dev_mqtt` 断开 |
| `MQTT_AUTH_FAILED` | `mqtt_worker` | MQTT 鉴权失败 |
| `MQTT_DOWNLINK` | `mqtt_worker` | 收到平台下行 |
| `TIME_TRUSTED` | `time_worker` | UTC 已可信 |
| `CONFIG_DONE` | `http_worker/config` | 配置更新完成 |
| `OTA_DONE` | `ota_worker` | OTA 完成 |
| `SCRIPT_EXCEPTION` | `script_task` | 脚本异常 |
| `SCRIPT_EXITED` | `script_task` | 脚本退出 |
| `LOG_FAULT` | `log_task` | 日志存储异常 |

事件处理要求：

1. 单次事件处理应尽快返回。
2. 会阻塞的操作投递到对应 worker。
3. 状态变化后按需通过 `up_raw` 上报 `device.login.report`、`device.offline.report` 或 `heartbeat.report`。
4. 查询类 MQTT 指令可以直接生成应答，但不得阻塞正在执行的互斥任务。

## 8. 网络与 MQTT 参数流程

### 8.1 网络启动

默认策略：

1. 默认联网方式为 4G。
2. 当前 4G 底层实现为 USB ECM，public profile 仍固定使用 `4g`。
3. APN 默认空字符串。
4. 联网失败按退避重试。
5. 网络失败不得阻塞 `script_task`。

流程：

```text
dev_mgr_task
  -> net_start(profile=4g)
  -> 等待 NET_READY 或 NET_FAILED
  -> NET_READY 后进入 MQTT 参数检查
  -> NET_FAILED 后保持重试并上报 network_status
```

网络状态：

| 场景 | `network_status` |
| --- | --- |
| 未启动或断开 | `disconnected` |
| 正在联网 | `connecting` |
| 已获取 IP | `connected` |
| 信号差或频繁断线 | `degraded` |

4G USB ECM 落地约束：

1. `dev_mgr_task` 只发起 `gw_net_start(GW_NET_PROFILE_4G)`，不直接执行 USB Host、AT 命令或 ECM 拨号。
2. `net_worker` 负责 4G GPIO 初始化、USB Host、CDC/ECM 组件、AT 查询、ECM 数据模式和 IP 获取。
3. 4G 启动阶段 AT 通道由系统独占，脚本不允许抢占。
4. 4G ready 后缓存 IMEI、ICCID、SIM、信号和注册状态，供属性上报和脚本受控查询使用。
5. USB 断开、ECM lost IP、AT 通道关闭或 IP 等待超时都必须转换为 `NET_LOST` 或 `NET_FAILED` 事件。
6. `net_worker` 失败后释放本轮 USB/ECM/AT 资源，再由线程 1 的重试策略决定下一轮启动时间。
7. `script_task` 不等待 `net_worker` 完成；即使 4G 长时间无法联网，本地脚本仍按本地配置运行。

### 8.2 MQTT 信息检查

启动后读取 NVS 中的 MQTT 连接信息：

| 情况 | 处理 |
| --- | --- |
| 无 MQTT 信息 | `mqtt_status=not_configured`，等待出厂/维护工具写入 |
| MQTT 信息完整 | 直接连接 `dev_mqtt` |
| MQTT 信息解密失败 | `mqtt_status=not_configured`，不得清除 `device_id` |
| MQTT 鉴权失败 | `mqtt_status=auth_failed`，保留本地 MQTT 信息，等待后台修正或维护重写 |

### 8.3 出厂 MQTT 信息缺失

HTTP 注册不属于固件运行时流程。缺少 MQTT 信息时，固件只做本地状态记录：

1. `status=offline`。
2. `mqtt_status=not_configured`。
3. `health_status=warn`。
4. 本地日志记录缺失字段或解密错误原因，不打印密码。
5. 不发起 HTTP GET、不重试注册、不清除 `device_id`。

## 9. dev_mqtt 管理流程

`dev_mqtt` 必须使用 `gw_mqtt_client` 通用 MQTT 封装层创建。线程 1 不直接调用 ESP-IDF MQTT；脚本侧 MQTT 也使用同一封装层，但使用独立的脚本 client 实例。

连接参数：

| 参数 | 默认值 |
| --- | --- |
| QoS | 1 |
| Clean Session | 1 |
| Retain | 0 |
| Last Will | 不启用 |
| 离线缓存 | 不启用 |
| 单条 Payload | 8192 字节 |
| 连接超时 | 10 秒 |

连接成功后订阅：

```text
/yx_gw/YxzhNode${device_id}/thing/model/down_raw
```

订阅必须以 Broker 返回 `SUBACK` 为准。本地提交订阅请求成功不代表设备管理通道已经可用；如果任一下行 Topic 订阅后被服务端断开，应保持 `mqtt_status=disconnected`，记录 Topic/ACL 诊断日志，并等待重连或服务端修正权限。

连接成功后立即执行：

1. 通过 `up_raw` 上报状态，表示设备在线。
2. 通过 `up_raw` 上报完整基础属性。
3. 上报当前配置流水号和 `manifest_sha256`。
4. 触发一次授时。
5. 进入 OTA 和配置检查流程。

与脚本 MQTT 的关系：

1. `dev_mqtt` 和脚本 MQTT 共享 `gw_mqtt_client` 底层封装，不共享凭据、Topic、回调和生命周期。
2. 脚本不能获得 `dev_mqtt` 的 handle。
3. 脚本 MQTT 断开、鉴权失败或重连失败不改变 `mqtt_status`。
4. `mqtt_status` 只表示 `dev_mqtt` 状态。
5. 网络断开会同时影响两类 MQTT client，但恢复后按各自重连策略处理。

断线策略：

1. MQTT 断开后，`mqtt_status` 变为 `reconnecting`。
2. 设备按退避策略重连。
3. 不缓存离线 MQTT 上报。
4. 断线期间平台命令不可达，脚本继续运行。
5. 鉴权失败时保留本地 MQTT 信息，等待后台修正账号或维护工具重写。

Last Will：

1. 设备管理 MQTT 默认启用 Last Will。
2. 遗嘱消息发布到 `up_raw`。
3. 遗嘱方法为 `device.offline.report`，内容表示 `status=offline`。

## 10. 上线、心跳与属性上报

上线后必须上报：

| 类型 | Topic | 内容 |
| --- | --- | --- |
| 登录 | `up_raw` / `device.login.report` | 设备上线、网络状态、MQTT 状态、脚本状态、任务状态 |
| 心跳 | `up_raw` / `heartbeat.report` | 在线状态、网络状态、MQTT 状态、脚本状态、任务状态 |
| 属性 | `up_raw` / `property.report` | 固件版本、配置版本、网络参数、资源状态、存储状态 |
| 配置状态 | `up_raw` 属性上报或配置应答 | `config.sequence`、`config.manifest_sha256` |

心跳规则：

1. 默认启用心跳。
2. 默认心跳间隔 60 秒。
3. 平台允许下发的最小心跳间隔 10 秒。
4. 心跳通过 `up_raw` 中的 `heartbeat.report` 上报。
5. 心跳不携带大块日志和大块属性。
6. 普通心跳成功不触发 `last_trusted_utc` NVS 写入。

状态字段由 `gw_state` 聚合：

| 字段 | 来源 |
| --- | --- |
| `status` | `gw_supervisor` 主状态 |
| `network_status` | `gw_net_manager` |
| `mqtt_status` | `gw_mqtt_manager` |
| `script_status` | `gw_script_manager` |
| `task_status` | `gw_protocol_manager` 或当前互斥任务 |

## 11. 授时流程

UTC 用途：

1. OTA 和配置的定时执行。
2. 日志 `ts`。
3. 状态、属性和进度上报时间戳。
4. HTTPS 证书时间校验。

可信来源：

| 来源 | 说明 |
| --- | --- |
| RTC | 带电池 RTC，校验通过后可作为可信来源 |
| 4G 网络时间 | 模组或运营商时间 |
| MQTT 授时 | 平台下发或连接后对时 |
| HTTPS 时间 | 可完成证书时间校验时使用 |
| NTP/SNTP | 网络可用时周期同步 |

可信判断：

1. 年份必须在 2026 到 2046 年之间。
2. RTC 时间不得早于 `last_trusted_utc - 300000` 毫秒。
3. `last_trusted_utc` 保存在加密 NVS，不设置过期时间。
4. 没有可信 UTC 时，协议时间戳填 `0`。
5. 没有可信 UTC 时，立即执行类指令仍可执行。
6. 没有可信 UTC 时，定时 OTA 和定时配置更新进入等待授时状态。

`last_trusted_utc` 写入：

1. 首次获得可信 UTC 时立即写入。
2. 当前可信 UTC 比 NVS 值大超过 24 小时时写入。
3. OTA、配置切换或正常重启前，如 UTC 可信，应写入一次。
4. 当前可信 UTC 小于等于 NVS 值时不写入，并记录时间倒退异常。

## 12. 配置与 OTA 编排

上线后的检查顺序：

1. 上报当前固件版本、配置流水号和 `manifest_sha256`。
2. 等待平台判断或主动触发检查。
3. 如果同时需要 OTA 和配置更新，优先执行 OTA。
4. OTA 成功后重启。
5. 配置更新成功后重启。
6. 失败时保留当前固件或旧配置运行。

OTA 编排：

| 步骤 | 说明 |
| --- | --- |
| 接收 `ota.upgrade` | 校验 `request_id`、版本、URL、SHA-256 |
| 判断版本 | 目标版本必须高于当前版本 |
| 判断时间 | `scheduled_at` 存在时必须等 UTC 可信并到达时间 |
| 接受任务 | 返回接收应答 |
| 停止脚本 | 通知 `script_task` 停止，最长等待 5 秒 |
| 下载固件 | HTTP/HTTPS 由 URL 决定 |
| 校验固件 | 大小、SHA-256、ESP-IDF OTA 校验 |
| 写入分区 | 写入 OTA 分区 |
| 上报结果 | 成功或失败均携带同一 `request_id` |
| 重启 | 成功后重启进入新固件 |

配置更新编排：

| 步骤 | 说明 |
| --- | --- |
| 接收 `config.update` | 校验 `request_id`、`sequence`、manifest URL |
| 判断流水号 | `sequence` 必须大于当前 `config.sequence` |
| 接受任务 | 返回接收应答 |
| 写非生效区 | 下载并校验完整配置包 |
| 停止脚本 | 目标区完整校验通过后，切槽前通知脚本释放资源 |
| 切换生效区 | 写 NVS 当前配置区、流水号和 `manifest_sha256` |
| 上报结果 | 成功或失败均携带同一 `request_id` |
| 重启 | 成功后重启，使新脚本和配置生效 |

## 13. MQTT 指令处理

MQTT 下行入口统一由 `gw_protocol_manager` 处理。

处理步骤：

1. 校验 Topic 是否属于固定组 `yx_gw` 和当前 `device_id` 生成的 `YxzhNode${device_id}`；设备初始化时使用硬件 MAC 十六进制大写字符串作为 `device_id`。
2. 校验 Payload 不超过 8192 字节。
3. 解析 JSON。
4. 校验 `version`、`method`、`request_id`。
5. 检查 `request_id` 是否重复。
6. 判断指令是否为查询类。
7. 非查询类尝试占用互斥任务。
8. 分发到对应模块。
9. 生成接受应答、进度上报或最终应答。

查询类指令：

| 方法 | 说明 |
| --- | --- |
| `device.status.get` | 查询当前设备状态 |
| `task.current.get` | 查询当前互斥任务 |
| `property.get` | 查询设备属性 |
| `log.query` | 查询日志，可触发 HTTP POST 上传 |
| `schema.get` | 查询 Schema |

非查询类指令：

| 方法 | 说明 |
| --- | --- |
| `property.set` | 设置运行参数 |
| `config.update` | 整包配置更新 |
| `ota.upgrade` | OTA 升级 |
| `device.reboot` | 设备重启 |
| `device.factory_reset` | 恢复出厂 |

当前版本不在 MQTT 协议中定义远程脚本启动、停止和重启方法。脚本停止和重启只作为配置更新、OTA、恢复出厂、系统重启和脚本异常策略中的内部协同动作；如后续需要远程脚本控制，应先更新 MQTT 协议文档。

## 14. 互斥任务和 request_id

互斥规则：

1. 同一时间只允许一个非查询类任务运行。
2. 正在执行 OTA、配置更新、重启、恢复出厂、属性设置或脚本异常策略配置时，新的非查询类指令返回 `device_busy`。
3. 查询类指令允许并行。
4. 查询类指令不得阻塞正在运行的互斥任务。

`request_id` 规则：

1. 设备保存最近 32 个平台下发的 `request_id`。
2. 运行中任务的 `request_id` 永远不能重复。
3. 已完成记录 1 小时没有新数据后自动清理。
4. 清理时不得删除运行中记录。
5. 收到重复 `request_id` 时不重新执行，直接返回 `duplicate_request_id`。
6. 同一任务的接受应答、进度上报和最终应答使用同一个 `request_id`。

互斥任务记录字段：

| 字段 | 说明 |
| --- | --- |
| `running_method` | 当前方法名 |
| `running_request_id` | 当前请求 ID |
| `task_status` | 当前任务状态 |
| `started_at` | 开始时间，UTC 不可信时填 0 |
| `last_progress` | 最近进度 |
| `cancelable` | 后续如支持取消时使用 |

## 15. MQTT 触发 HTTP 操作

凡是由 MQTT 指令触发且设备需要再执行 HTTP/HTTPS 的操作，都必须遵守统一规则：

1. URL 由平台下发，设备根据 `http://` 或 `https://` 自动选择协议。
2. 连接超时默认 10 秒。
3. 应答间隔超时默认 3 秒。
4. 不定义总超时。
5. 下载和上传默认最多重试 3 次。
6. 重试间隔默认 3 秒、10 秒、30 秒。
7. 成功或失败都必须通过 MQTT 使用同一个 `request_id` 返回最终结果。
8. HTTP POST 上传根对象必须包含 `device_id`、`request_id`、`sha256`。
9. HTTP POST 上传以服务端返回 JSON 中 `code=200` 作为成功。

适用场景：

| 场景 | HTTP 操作 |
| --- | --- |
| 配置更新 | 下载 `manifest.jsonl` 和配置包文件 |
| OTA | 下载固件 |
| 日志查询 | 查询结果超过 8192 字节时 HTTP POST 上传 |

不适用场景：

| 场景 | 说明 |
| --- | --- |
| 主动授时 | 只更新本地时间状态，不按平台请求应答 |

## 16. 与脚本线程协同

线程 1 不阻塞脚本：

1. 联网失败不阻塞脚本。
2. MQTT 未配置或连接失败不阻塞脚本。
3. MQTT 连接失败不阻塞脚本。
4. 配置检查失败不阻塞脚本。
5. 日志写入失败不阻塞脚本。

线程 1 必须协调脚本的场景：

| 场景 | 处理 |
| --- | --- |
| 配置更新 | 目标配置区完整校验通过后发送 `CONFIG_UPDATING`，要求脚本停止或释放资源 |
| 配置切换成功 | 发送 `CONFIG_CHANGED`，随后设备重启 |
| OTA | 发送 `OTA_UPDATING`，要求脚本停止 |
| 设备重启 | 发送停止请求，最多等待 5 秒 |
| 恢复出厂 | 停止脚本并清理用户数据 |
| 脚本异常 | 接收 `SCRIPT_EXCEPTION`，上报异常并按策略处理 |

脚本停止规则：

1. 优雅停止最长等待 5 秒。
2. 超时仍未退出时记录异常。
3. OTA 和恢复出厂可以继续进入后续流程，但必须记录脚本停止超时。
4. 配置更新在切换生效区前如果脚本停止超时，应中止切换并上报失败，保留旧配置。
5. 脚本异常不应导致设备管理平面崩溃。

## 17. 重启与恢复出厂

重启由线程 1 统一执行。

重启前置动作：

1. 如 UTC 可信，写入 `last_trusted_utc`。
2. 上报 `task_status=rebooting`。
3. 请求脚本停止。
4. 刷新关键 NVS 状态。
5. 投递最后一条本地日志。
6. 执行系统重启。

恢复出厂要求：

1. MQTT 请求必须携带 `confirm=true` 和非空 `reason`。
2. 保留硬件 MAC、当前 `device_id`、`product_id` 和出厂必要参数。
3. 清除 MQTT 信息、运行参数、配置双区、`datafs`、`logfs`、OTA 临时状态、运行统计和 `last_trusted_utc`。
4. 恢复出厂过程为互斥任务。
5. 成功或失败都必须使用同一个 `request_id` 应答。
6. 成功后重启。

## 18. 异常和降级策略

| 异常 | 设备管理处理 |
| --- | --- |
| 4G 联网失败 | 保持网络重试，上报 `network_status=disconnected` 或 `connecting` |
| MQTT 信息缺失 | `mqtt_status=not_configured`，不发起 HTTP 注册 |
| MQTT 鉴权失败 | 保留 MQTT 信息，等待后台修正或维护重写 |
| MQTT 断开 | 进入重连，不缓存离线上报 |
| `cfgfs` 异常 | 受限运行，等待配置修复 |
| `datafs` 异常 | 脚本文件 API 失败，设备管理继续 |
| `logfs` 异常 | 降级本地日志，设备管理继续 |
| UTC 不可信 | 定时任务等待授时，立即任务可执行 |
| 配置更新失败 | 保留旧配置运行，上报失败 |
| OTA 失败 | 保留当前固件运行，上报失败 |
| 脚本异常 | 上报异常，按脚本策略处理 |
| `dev_mgr_task` 栈低于 4 KB | 记录 warn 并上报状态 |

## 20. 定时器建议

| 定时器 | 默认值 | 说明 |
| --- | ---: | --- |
| `heartbeat_timer` | 60 秒 | 状态心跳上报 |
| `time_sync_timer` | 按配置 | 周期授时 |
| `mqtt_reconnect_timer` | 10 到 120 秒退避 | MQTT 重连 |
| `request_id_gc_timer` | 60 秒 | 清理超过 1 小时的已完成请求记录 |
| `stack_check_timer` | 60 秒 | 检查核心任务栈高水位 |
| `ota_schedule_timer` | 按平台时间 | UTC 可信后检查定时 OTA |

定时器约束：

1. 定时器回调只投递事件，不直接执行长耗时操作。
2. 定时器时间使用系统 tick；平台调度时间使用可信 UTC。
3. UTC 不可信时，不启动绝对时间类调度，只记录等待原因。

## 21. 实现顺序

1. 实现 `gw_state`，先打通状态聚合和状态上报数据结构。
2. 实现 `gw_supervisor` 主事件队列和状态机。
3. 接入 `net_worker`，完成默认 4G 联网和网络状态。
4. 接入出厂 MQTT 信息读取和 `not_configured` 状态。
5. 接入 `gw_mqtt_client` 通用封装，并让 `dev_mqtt` 基于该封装完成连接、订阅、上线状态上报和心跳。
6. 接入 `request_id` 去重和互斥任务。
7. 接入查询类方法：状态、任务、属性。
8. 接入配置更新和 OTA 编排。
9. 接入授时和定时 OTA。
10. 接入脚本异常、脚本停止协调和恢复出厂。
