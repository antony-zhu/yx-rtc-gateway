## 1. 文档定位

> **当前实现基线（2026-09-01）**：本文件包含早期设计章节。当前嵌入式 C 固件以

## 3. Flash 分区与文件系统

设备固定使用 16 MB Flash，固件工程位于 `embedded/`，自定义分区表文件为 `embedded/partitions.csv`。应用层文件系统固定使用 LittleFS，不使用 SPIFFS 作为业务文件系统。

分区表在参考 `D:\codex\yx-gateway_last\embeded\reference\catv2\partitions.csv` 的基础上，将业务文件系统拆分为配置、用户数据和日志三个 LittleFS 分区。本项目同时提供可直接使用的 `docs/02-ESP32S3R8N16_partitions.csv`：

```csv
# Name,      Type,  SubType,  Offset,     Size,       Flags
nvs,         data,  nvs,      0x9000,     0x20000,
otadata,     data,  ota,      0x29000,    0x2000,
phy_init,    data,  phy,      0x2B000,    0x1000,
factory,     app,   factory,  0x30000,    0x300000,
ota_0,       app,   ota_0,    0x330000,   0x300000,
ota_1,       app,   ota_1,    0x630000,   0x300000,
cfgfs,       data,  littlefs, 0x930000,   0x400000,
datafs,      data,  littlefs, 0xD30000,   0x140000,
logfs,       data,  littlefs, 0xE70000,   0x180000,
```

分区说明：

| 分区 | 大小 | 用途 |
| --- | --- | --- |
| `nvs` | 128 KB | 保存设备出厂参数、运行参数、MQTT 信息、OTA 状态、运行统计和加密副本 |
| `otadata` | 8 KB | ESP-IDF OTA 启动状态 |
| `phy_init` | 4 KB | PHY 初始化数据 |
| `factory` | 3 MB | 出厂固件 |
| `ota_0` | 3 MB | OTA 固件分区 0 |
| `ota_1` | 3 MB | OTA 固件分区 1 |
| `cfgfs` | 4096 KB | 配置双区、`manifest.jsonl`、`config.json`、`main.py` |
| `datafs` | 1280 KB | 用户脚本数据分区，直接使用分区根目录，默认可用限额 1 MB |
| `logfs` | 1536 KB | 运行日志分区，直接使用分区根目录，满足默认 `1 MB + 256 KB` 日志浮动 |
| 未分配尾部空间 | 64 KB | 预留给后续分区微调，不挂载 |

LittleFS 使用要求：

1. LittleFS 分区标签固定为 `cfgfs`、`datafs`、`logfs`。
2. `cfgfs` 只保存配置双区和 Python 固定入口脚本，不保存用户运行数据和日志。
3. `datafs` 只作为用户脚本数据区，直接使用分区根目录，不再在该分区下创建固定子目录。
4. `logfs` 只作为运行日志区，直接使用分区根目录，不再在该分区下创建固定子目录。
5. 配置文件采用双区方式保存，校验通过后再切换当前生效配置区。
6. OTA 固件包不长期保存在 LittleFS；如需临时下载到文件系统，应使用专门的 OTA 临时策略，不得挤占 `datafs` 和 `logfs` 的保留空间。
7. `cfgfs`、`datafs`、`logfs` 挂载失败时，正常运行启动先重试 3 次；仍失败则格式化对应分区并重新挂载一次。
8. `cfgfs` 格式化后配置双区为空，设备视为无本地配置，仅保留设备管理、MQTT、状态上报和整包配置修复能力。
9. `datafs` 和 `logfs` 属于非核心分区，挂载失败、写满或文件损坏均不得导致系统崩溃，不得影响联网、MQTT、OTA、配置更新和心跳上报。
10. `datafs` 格式化后脚本用户数据被清空；如果格式化或重新挂载仍失败，脚本文件操作返回失败，线程 1 继续运行，线程 2 按脚本异常策略处理。
11. `logfs` 格式化后历史日志被清空；如果格式化或重新挂载仍失败，设备关闭或降级本地持久化日志，仅保留内存计数和最近错误摘要。
12. 出厂流程允许通过维护/产测入口显式清空并重建 `cfgfs`、`datafs`、`logfs`，不受正常运行启动的数据保护限制。

### 3.1 LittleFS 分区路径结构

设备同时使用 `cfgfs`、`datafs`、`logfs` 三个 LittleFS 分区。文档中的文件路径统一采用 `分区名:/分区内路径` 表示，避免把三个分区误解为同一个文件系统根目录。

```text
cfgfs:/
  cfg_a/
    manifest.jsonl
    config.json
    main.py
  cfg_b/
    manifest.jsonl
    config.json
    main.py

datafs:/
  <用户脚本创建的文件和目录>

logfs:/
  log_000001.jsonl
  log_000002.jsonl
  index.json
```

目录说明：

| 路径 | 说明 |
| --- | --- |
| `cfgfs:/cfg_a` | 配置 A 区 |
| `cfgfs:/cfg_b` | 配置 B 区 |
| `cfgfs:/cfg_a/manifest.jsonl` | 配置 A 区描述文件 |
| `cfgfs:/cfg_b/manifest.jsonl` | 配置 B 区描述文件 |
| `cfgfs:/cfg_a/config.json`、`cfgfs:/cfg_b/config.json` | 用户配置文件，由当前生效配置区决定 |
| `cfgfs:/cfg_a/main.py`、`cfgfs:/cfg_b/main.py` | Python 脚本入口文件，脚本固定为一个入口文件 |
| `datafs:/` | 脚本数据分区根目录；脚本如果需要文件读写，只允许使用该分区，默认容量限额 1 MB |
| `logfs:/` | 运行日志分区根目录；保存设备运行日志和脚本异常相关日志 |

配置双区规则：

1. `cfgfs:/cfg_a` 和 `cfgfs:/cfg_b` 一次只有一个为当前生效区。
2. 当前生效区、配置流水号和 `manifest_sha256` 属于设备参数，保存在 NVS。
3. 配置更新时，线程 1 写入非生效区。
4. 非生效区所有文件和 `manifest.jsonl` 校验通过后，才更新 NVS 中的当前生效区。
5. 如果两个配置区都有效且 `seq_id` 相同，默认选择 `cfgfs:/cfg_a`。
6. 如果两个配置区都无效，设备视为无本地配置，使用出厂默认逻辑运行并等待整包配置更新。
7. 平台下发的新配置 `seq_id` 必须大于当前 `seq_id`；小于或等于当前值时设备必须拒绝，并上报拒绝原因。
8. `datafs:/` 不属于配置双区，配置更新不得清空 `datafs`。
9. `logfs:/` 不属于配置双区，配置更新不得清空 `logfs`。
10. 单个配置区最大使用量为 1.8 MB，包含 `manifest.jsonl`、`config.json`、`main.py` 和所有子目录文件；超过时拒绝该配置包。

NVS 配置状态示例：

```json
{
  "active_slot": "cfg_a",
  "seq_id": 123,
  "manifest_sha256": "xxxxx",
  "updated_at": 1703424234214
}
```

### 3.2 manifest.jsonl 格式

每个配置区必须包含 `manifest.jsonl`。该文件采用 JSON Lines 格式，一行一个 JSON 对象。

第一行必须为描述行：

```jsonl
{"type":"desc","seq_id":123,"min_product_version":"1.2.1","file_count":2,"created_at":1703424234214}
```

后续每一行为文件描述：

```jsonl
{"type":"file","name":"config.json","size":8192,"sha256":"xxxxx"}
{"type":"file","name":"main.py","size":8192,"sha256":"xxxxx"}
```

字段说明：

| 字段 | 所属行 | 说明 |
| --- | --- | --- |
| `type` | 全部 | `desc` 表示配置包描述；`file` 表示文件描述 |
| `seq_id` | `desc` | 配置流水号，数值越大表示配置越新 |
| `min_product_version` | `desc` | 最低固件版本要求，低于该版本时不得应用该配置 |
| `file_count` | `desc` | 配置包文件数量，不包含 `manifest.jsonl` |
| `created_at` | `desc` | 配置包生成时间，毫秒时间戳 |
| `name` | `file` | 文件相对配置区根目录的路径 |
| `size` | `file` | 文件大小，单位字节 |
| `sha256` | `file` | 文件 SHA-256，小写十六进制字符串 |

`manifest.jsonl` 中的文件路径允许包含子目录和 `../`，但设备必须在使用前做路径规范化，规范化后的最终路径不得逃出当前配置区。当前版本固定要求包含 `config.json` 和 `main.py`，其中 `manifest.jsonl`、`config.json`、`main.py` 作为一个整体配置包下载、校验和切换，不做单文件局部更新；`config.json` 不要求提供 JSON Schema，由用户脚本自行解释。

开机后，线程 1 必须读取 NVS 中的配置状态，找到当前生效配置区，然后同步并校验该区 `manifest.jsonl`。如果发现描述文件缺失、JSONL 格式错误、文件缺失、大小不一致、SHA-256 不一致、配置流水号异常或固件版本不满足要求，应认为当前配置异常，并进入整包配置更新流程。

### 3.3 运行日志分区

设备运行日志固定存放在 `logfs` 分区根目录。

日志文件不按日期命名。设备可能长期未联网或未完成授时，因此日志文件按递增段号命名，并使用 JSON Lines 格式保存。段文件只是设备内部存储实现，平台查询日志时不感知段文件。

```text
logfs:/
  log_000001.jsonl
  log_000002.jsonl
  index.json
```

单行日志示例：

```jsonl
{"seq":1024,"boot_id":"boot-0001","uptime_ms":120345,"ts":1703424234214,"time_synced":true,"level":"info","module":"mqtt","msg":"connected","code":0}
```

日志保留策略：

| 项目 | 策略 |
| --- | --- |
| 保存位置 | `logfs:/` |
| 文件格式 | JSON Lines，一行一条日志 |
| 文件命名 | `log_<segment_id>.jsonl`，`segment_id` 单调递增，不依赖日期 |
| 单个段文件大小 | 128 KB，固定值，不做运行时配置 |
| 单条日志最大长度 | 4096 字节，固定值，不做运行时配置；超过截断并标记 `truncated=true` |
| 默认持久化等级 | `info`、`warn`、`error` |
| 默认不持久化等级 | `debug`，除非平台临时开启 |
| 时间保留目标 | 默认 30 天，可通过配置修改 |
| 日志容量目标 | 默认 1 MB，可通过配置修改 |
| 容量浮动 | 默认允许约 256 KB 浮动，用于当前段文件、索引和扫描间隔内的自然增长 |
| 高水位触发 | `logfs` 使用率超过 80% 或日志写入返回空间不足时触发清理 |
| 清理目标 | 清理到 `logfs` 使用率不高于 50% |
| 扫描周期 | 默认 1 天，可通过配置修改 |
| 默认最大段数 | 10 个，按 `(1 MB + 256 KB) / 128 KB` 计算 |
| 清理策略 | 后台删除最旧段文件；优先按容量目标和使用率控制，时间保留只作为辅助条件 |
| 清理执行线程 | `log_task` 后台异步执行，不得阻塞线程 1 或线程 2 |

注意：当设备日志量较大时，容量目标和 `logfs` 使用率优先，因此不能保证完整保留 30 天内的所有日志。如果设备时间未同步，30 天保留策略不可用，此时只按 `segment_id` 删除最旧日志。

`logfs:/index.json` 用于加速查询和减少扫描，可记录当前段号、总大小、最小/最大 `seq`、每个段文件的大小、行数和时间范围。索引损坏时可扫描 `logfs:/log_*.jsonl` 重建。

写入与清理规则：

1. 线程 1 和线程 2 只向日志队列投递日志，不直接扫描、删除或整理 `logfs:/`。
2. 日志队列满时，低优先级日志可直接丢弃并增加 `dropped_count`；不得阻塞调用方等待 Flash 写入。
3. `log_task` 负责写入段文件、切换段文件、刷新 `index.json` 和清理旧日志。
4. 平时写日志不扫描整个 `logfs:/`。
5. 当前段文件写满 128 KB 后，由 `log_task` 切换到下一个段文件。
6. 设备开机挂载 `logfs` 后由 `log_task` 扫描一次 `logfs:/`，用于重建或校正 `index.json`。
7. 设备运行期间按 `log.scan_interval_sec` 周期扫描一次，默认 1 天。
8. 周期扫描时，如果设备时间已同步，优先删除超过 `log.retention_days` 的日志。
9. 周期扫描或写入触发清理时，如果 `logfs:/log_*.jsonl` 总大小超过 `log.max_size`，或 `logfs` 使用率超过 80%，继续删除最旧段文件，直到 `logfs` 使用率不高于 50%。
10. 如果 `logfs` 写满导致当前写入失败，`log_task` 应先丢弃当前低优先级日志并触发后台清理；清理失败时暂停持久化日志，不影响其他系统能力。
11. `1 MB + 256 KB` 是默认情况下的预估浮动范围，不作为精确硬限制；实际实现以固定段大小、后台清理和周期扫描共同控制，避免日志无限增长。

日志敏感信息规则：

1. Release 版本禁止打印 MQTT 密码、HTTP URL 中的 token、出厂凭据、派生密钥、Wi-Fi 密码、用户配置中的密钥类字段。
2. Debug 版本如需打印敏感字段，必须显式使用脱敏函数，至少保留前 3 位和后 3 位，中间使用 `***` 替代。
3. 任何版本都不得将 NVS 加密密钥、中间派生密钥或明文密码写入 `logfs`。

## 4. 出厂预置内容

设备出厂时必须预置以下信息：

| 项目 | 说明 |
| --- | --- |
| `product_id` | 产品 ID，出厂写入 NVS；当前默认值为 `yx_gw` |
| `group_id` | MQTT Topic 组 ID，出厂写入 NVS；当前联调阶段暂时使用 `yx_gw` |
| `device_id` | 设备业务标识，默认等于 MAC 十六进制大写字符串；后续允许通过接口修改 |
| `mac` | 设备 MAC 地址 |
| MQTT 连接信息 | `host`、`port`、`username`、`password`、`client_id`，出厂写入加密 NVS |
| 默认网络配置 | 默认联网方式先固定为 4G；该配置与产品形态有关，理论上应在出厂时写入 |
| 默认 4G APN | 空字符串，表示使用模组或运营商默认 APN |
| 默认心跳配置 | 默认启用心跳，默认心跳间隔由固件设定 |
| 默认脚本异常策略 | `restart_by_watchdog` |
| 默认配置流水号 | `0` |
| 默认配置 SHA-256 | 默认配置区 `manifest.jsonl` 的 SHA-256 或空字符串 |

出厂后设备首次启动时，若未获取到平台下发配置，应使用出厂默认配置运行。

## 5. 本地持久化数据

设备应将以下数据持久化保存，断电重启后继续使用：

| 数据 | 存储位置 | 说明 |
| --- | --- | --- |
| 设备基础信息 | NVS | `product_id`、`group_id`、`device_id`、`mac`、固件版本；`product_id` 当前默认 `yx_gw`；`group_id` 当前联调阶段暂时使用 `yx_gw`；`device_id` 默认等于 MAC 十六进制大写字符串，但允许修改 |
| MQTT 连接信息 | NVS | `host`、`port`、`username`、`password`、`client_id`、`tls`、`keep_alive_sec` |
| 设备运行参数 | NVS | 当前生效配置区、`seq_id`、`manifest_sha256`、心跳、授时、`last_trusted_utc`、HTTP 超时、MQTT 重连等设备参数 |
| 用户配置 | `cfgfs:/cfg_a/config.json`、`cfgfs:/cfg_b/config.json` | 用户自己的参数，随配置双区切换 |
| 用户脚本 | `cfgfs:/cfg_a/main.py`、`cfgfs:/cfg_b/main.py` | Python 固定入口脚本 |
| OTA 状态 | NVS | 当前 OTA 阶段、目标版本、下载文件校验信息 |
| 脚本数据 | `datafs:/` | 用户脚本创建和读写的文件，默认容量限额 1 MB |
| 运行日志 | `logfs:/` | 最近运行日志、脚本异常日志、MQTT 详细日志 |
| 运行统计 | NVS | 重启次数、最近一次重启原因、MQTT 重连次数 |

设备参数均保存在 NVS。用户自己的参数保存在当前生效配置区的 `config.json`，用户脚本运行时创建的文件保存在 `datafs:/`。持久化数据写入时应采用临时文件或双区方式，避免断电导致配置损坏。启动时如果发现配置校验失败，应按配置双区规则选择有效配置区；如果两区都无效，则视为无本地配置并等待整包配置更新。

### 5.1 NVS 系统参数加密

NVS 中的系统参数必须加密后存储，用户脚本数据、`config.json`、`main.py` 和运行日志不纳入该加密范围。

加密规则：

1. `mac_upper` 为设备 MAC 十六进制大写字符串，不包含冒号，例如 `80B54EE92148`。
2. 主密钥派生：`master_key = SHA256("yx_gateway_nvs_aes_v1:" + mac_upper)`。
3. 每个 NVS 字段派生独立字段密钥：`field_key = SHA256(master_key + ":" + namespace + ":" + key_name)`。
4. 加密算法固定为 `AES-256-CTR`，使用 `field_key` 作为 256 位 AES 密钥。
5. 不使用随机 IV；计数器初值由 `SHA256("yx_gateway_nvs_ctr_v1:" + mac_upper + ":" + namespace + ":" + key_name)` 的前 16 字节确定。
6. 加密前明文应加入固定魔数、版本号、长度和 CRC32；解密后校验失败时认为该字段损坏。
7. 关键系统参数应保存主副两份，读取时优先使用序号较新的有效副本；新副本写入和校验成功后再更新当前序号。

该加密策略的目标是避免 Flash 或 NVS 直接读出明文，在性能、实现复杂度和可靠性之间取平衡。由于密钥由 MAC 派生，MAC 本身不是秘密，因此该策略不用于对抗已完全掌握设备和固件的强物理破解。

### 5.2 恢复出厂策略

恢复出厂时必须保留设备身份类信息，至少包括 `mac`、当前 `device_id`、`product_id` 和 `group_id`。`device_id` 即使曾被修改，也不得被恢复出厂流程清除或重置回 MAC。

恢复出厂时应清除可运行时重建或用户产生的数据，包括 MQTT 连接信息、心跳/授时/HTTP 超时/MQTT 重连等运行参数、`cfgfs` 配置双区内容、`datafs` 用户数据、`logfs` 运行日志、OTA 临时状态和运行统计。清除 MQTT 连接信息后，设备必须由出厂/维护工具重新写入 MQTT 参数才能上线。

平台允许通过 MQTT 方法 `device.factory_reset` 远程触发恢复出厂，但请求必须携带 `confirm=true` 和非空 `reason`。设备应先通过 MQTT 应答 accepted，再执行清理和重启。未指定重启延迟时，默认 3 秒后重启。

## 6. 启动初始化流程

设备上电后按以下顺序初始化：

1. 初始化硬件、Flash 和 NVS。
2. 初始化日志模块和看门狗。
3. 挂载 `cfgfs`、`datafs`、`logfs` 三个 LittleFS 分区。
4. 读取出厂参数和本地持久化配置。
5. 读取 NVS 中的配置状态，确定当前生效配置区。
6. 校验当前生效配置区的 `manifest.jsonl` 和配置文件完整性。
7. 校验 OTA 状态，判断上次升级是否完成。
8. 初始化网络模块，默认联网方式为 4G。
9. 创建线程 1：设备管理线程。
10. 创建线程 2：Python 脚本线程。
11. 线程 1 和线程 2 并行运行，线程 1 的联网、MQTT 连接和配置检查不得阻塞线程 2 启动。

启动阶段如果当前配置区异常，设备应记录异常原因。线程 1 使用默认配置进入联网和 MQTT 连接流程，并在联网后触发整包配置更新；线程 2 使用上一份有效脚本配置或出厂默认脚本配置运行。

## 7. 线程模型

设备运行时至少包含两个核心线程。本文中的“线程 1”表示设备管理主线程和其拉起的管理平面辅助任务集合；实现上允许线程 1 拉起网络、MQTT、HTTP/OTA、日志清理等辅助任务，但这些辅助任务不得阻塞 Python 脚本线程。

任务栈和内存来源固定如下：

| 任务 | 栈大小 | 栈内存来源 | 说明 |
| --- | ---: | --- | --- |
| `dev_mgr_task` | 24 KB | 内部 RAM | 线程 1 主任务，负责设备管理主流程和辅助任务调度 |
| `script_task` | 64 KB | 内部 RAM | 线程 2，运行唯一 Python 脚本入口 `main.py` |
| `log_task` | 8 KB | 内部 RAM | 低优先级日志写入和日志清理任务 |

栈大小单位固定为字节，按 ESP-IDF `xTaskCreate()` 的栈大小参数解释，不得再按 `StackType_t` 字数二次换算。所有系统任务栈均使用内部 RAM，不允许放入 PSRAM。

脚本应用内存与系统内部 RAM 隔离：Python VM heap、Python 对象、脚本模块动态分配、脚本文件读写大缓冲区和脚本扩展模块业务内存均必须从 PSRAM 分配。脚本申请 PSRAM 失败时，只能导致脚本侧分配失败或脚本异常退出，不允许回退占用内部 RAM。

设备应周期性检查核心任务栈高水位：`dev_mgr_task` 剩余栈低于 4 KB 时记录 warn 并上报状态；`script_task` 剩余栈低于 8 KB 时记录 warn 并上报脚本风险状态。发生 FreeRTOS 栈溢出时视为系统级故障，应记录 `fault_task` 后受控重启。

### 7.1 线程 1：设备管理线程

线程 1 负责设备联网、连接 `dev_mqtt`、同步时间、检查配置/OTA、处理平台指令，以及维护设备状态。

线程 1 是设备主控流程，负责决定设备是否需要重启、升级、更新配置或通知脚本线程停止/重启。

线程 1 可以创建管理平面辅助任务，但这些任务仍属于设备管理侧。辅助任务之间应通过队列、事件或状态机协作，不应让网络、MQTT、HTTP、OTA 或日志清理中的任一阻塞点拖住 `script_task`。

### 7.2 线程 2：Python 脚本线程

线程 2 负责运行用户 Python 脚本。

线程 2 不依赖线程 1 完成联网或 `dev_mqtt` 连接。脚本可能完全不需要联网，因此线程 2 应基于本地有效脚本配置独立启动。

线程 2 不直接处理 OTA、配置下载和 `dev_mqtt` 连接。脚本如需访问设备配置或上报数据，应通过设备内部接口与线程 1 通信；如果线程 1 当前离线，内部接口应返回离线状态，设备管理侧不缓存离线 MQTT 上报。

### 7.3 线程间通信

建议线程间使用事件标志、消息队列或内部 RPC 通信。

| 事件/消息 | 方向 | 说明 |
| --- | --- | --- |
| `CONFIG_CHANGED` | 线程 1 -> 线程 2 | 配置已更新，脚本可按需重新加载 |
| `CONFIG_UPDATING` | 线程 1 -> 线程 2 | 即将更新配置，脚本应停止写配置或释放资源 |
| `OTA_UPDATING` | 线程 1 -> 线程 2 | 即将 OTA，脚本应停止运行 |
| `TIME_SYNCED` | 线程 1 -> 线程 2 | 系统时间已同步 |
| `SCRIPT_EXCEPTION` | 线程 2 -> 线程 1 | 脚本运行异常 |
| `SCRIPT_EXITED` | 线程 2 -> 线程 1 | 脚本主动退出或异常退出 |

配置更新、OTA 和重启操作应由线程 1 统一执行，线程 2 不应自行触发系统级重启。

线程 1 不得因为联网失败、MQTT 未配置、MQTT 连接失败、订阅失败或配置检查失败而阻塞线程 2 的启动和运行。只有配置更新、OTA、服务器重启指令、脚本异常策略或系统级故障需要重启时，线程 1 才能要求线程 2 暂停或停止。

### 8.1 联网流程

联网流程要求：

1. 按本地配置选择联网方式；如果配置不存在或未指定联网方式，默认使用 4G。
2. 优先使用当前配置中指定的联网参数。当前阶段默认联网方式先固定为 4G，后续可按产品形态在出厂参数中写入。
3. 4G APN 默认空字符串，表示使用模组或运营商默认 APN；平台下发非空 APN 后按平台配置使用。
4. 联网失败时按退避策略重试。
5. 联网成功后记录网络类型、IP、信号质量等运行状态。
6. 网络断开后，线程 1 负责重连网络和 `dev_mqtt`。

建议重试策略：

| 场景 | 策略 |
| --- | --- |
| 首次联网失败 | 立即重试 3 次 |
| 连续失败 | 按 5 秒、15 秒、30 秒、60 秒退避 |
| 长时间失败 | 保持低频重试，并定期喂狗 |
| 配置中网络参数无效 | 保留当前配置，等待平台或本地维护方式修复 |

### 8.2 设备时间同步

线程 1 在以下时机同步设备时间：

1. 网络连接成功后。
2. MQTT 连接成功后。
3. 配置或平台指令要求立即同步时间时。
4. 到达 NTP/授时配置中的同步周期时。

设备带电池 RTC，RTC 可以作为可信 UTC 来源，但必须通过校验后才能使用。时间可信来源包括 RTC、NTP/SNTP、MQTT 授时、4G 网络时间和可完成证书时间校验的 HTTPS 时间。

UTC 可信判断规则：

1. 设备所有调度时间统一按 UTC 解释。
2. 时间年份必须在 2026 到 2046 年之间；超出范围一律视为不可信。
3. 设备从 NVS 读取 `last_trusted_utc` 作为历史可信时间基准，字段使用毫秒 Unix 时间戳长期保存，不设置过期时间。
4. 开机读取 RTC 后，如果 RTC 年份在 2026 到 2046 年之间，且 RTC 时间不早于 `last_trusted_utc - 300000` 毫秒，则可标记 `time_synced=true`、`time_trusted=true`、`time_source=rtc`。
5. 如果 RTC 早于 `last_trusted_utc - 300000` 毫秒，认为 RTC 不可信，协议报文时间戳和日志 `ts` 填 `0`，日志标记 `time_synced=false`。
6. 一旦通过 NTP/SNTP、MQTT 授时、4G 网络时间或 HTTPS 获取到可信 UTC，设备应同步系统时间、写入 RTC，并按写入策略更新 NVS 中的 `last_trusted_utc`。
7. 没有可信 UTC 时，设备仍可连接 MQTT、运行脚本和处理立即执行类指令；但不得执行服务器设定时间点的 OTA 或配置更新，只能等待授时或上报等待原因。

`last_trusted_utc` 写入策略：

1. 首次获得可信 UTC 时立即写入 NVS。
2. 当前可信 UTC 比 NVS 中 `last_trusted_utc` 大超过 24 小时时写入。
3. OTA、配置切换或正常重启前，如当前 UTC 可信，应写入一次；恢复出厂流程按规则清除该字段。
4. 普通心跳和周期授时成功不每次写入，避免频繁擦写 NVS。
5. 当前可信 UTC 小于等于 NVS 中 `last_trusted_utc` 时不写入，并记录时间倒退异常。
6. 恢复出厂时清除 `last_trusted_utc`。

时间同步成功后，后续日志、状态、属性和 OTA 进度均使用可信 UTC 的毫秒时间戳。

### 8.3 MQTT 信息检查

设备启动后先检查本地是否已有有效 MQTT 信息：

- 如果没有 MQTT 信息，进入 `mqtt_status=not_configured`，不得自动 HTTP 注册。
- 如果 MQTT 信息存在，则直接尝试连接 `dev_mqtt`。
- 如果 `dev_mqtt` 鉴权失败，应保留本地 MQTT 信息，等待后台修正账号或维护工具重写。
- 如果 MQTT 信息解密失败，视为 `not_configured`，不得清除 `device_id`。

MQTT 连接信息由出厂/产测流程写入加密 NVS。固件运行时只读取和使用，不通过 HTTP 接口自动补齐。

### 8.4 dev_mqtt 连接流程

连接 `dev_mqtt` 时应设置：

| 项目 | 要求 |
| --- | --- |
| Client ID | 使用出厂写入的 `client_id` |
| Username | 使用出厂写入的 `username` |
| Password | 使用出厂写入的 `password` |
| Keep Alive | 默认 60 秒，可通过设备参数配置 |
| 连接超时 | 默认 10 秒，可通过设备参数配置 |
| QoS | 默认 1，可通过设备参数配置 |
| Clean Session | 默认 1，可通过设备参数配置 |
| Retain | 默认 0，可通过设备参数配置 |
| Last Will | 默认不启用，可通过设备参数配置；启用时发布离线状态到 `up_raw` |
| 离线缓存 | 默认不缓存离线 MQTT 上报 |
| 单条 Payload | 最大 8192 字节 |

连接成功后，设备应订阅以下下行主题：

1. `down_raw`

订阅成功后，设备立即上报：

1. 在线状态。
2. 基础属性。
3. 配置流水号和配置 SHA-256。
4. 内存与存储状态。

### 8.5 配置与 OTA 检查流程

设备上线后，线程 1 需要检查最新配置和 OTA。

检查原则：

1. 设备上报当前固件版本、当前配置区、配置流水号和 `manifest_sha256`。
2. 平台根据设备状态决定是否下发 OTA 或配置更新。
3. 如果同时存在 OTA 和配置更新，优先执行 OTA。
4. OTA 或配置更新成功后，设备应重启。
5. 重启后设备重新上线，并再次上报当前版本和配置状态。

如果配置更新失败，设备应继续使用旧配置运行，不应进入不可恢复状态。

如果 OTA 失败，设备应继续运行当前固件，并上报失败原因。

### 8.6 运行循环

线程 1 进入运行循环后持续执行：

1. 维护网络连接。
2. 维护 `dev_mqtt` 连接。
3. 按心跳间隔上报设备状态。
4. 按配置周期同步设备时间。
5. 处理服务器下发指令。
6. 到达服务器设定的升级检查时间时，检查升级；平台下发的升级时间统一按 UTC 时间解释，且仅在 UTC 可信时执行。
7. 监听线程 2 的脚本异常。
8. 向 `log_task` 投递本地运行日志，由 `log_task` 维护 `logfs` 轮转。
9. 在需要重启、OTA 或配置更新时，协调线程 2 停止脚本。

### 8.7 平台指令并发规则

设备管理侧同一时间只允许一个会改变设备状态的操作运行。正在执行 OTA、配置更新、重启、恢复出厂、属性设置或脚本异常策略配置时，如果收到新的非查询类指令，设备应拒绝并通过 MQTT 应答 `device_busy`。

查询类指令允许并行执行，包括状态查询、属性查询、日志查询和 Schema 查询。查询类指令不得阻塞正在执行的 OTA 或配置更新流程。

设备侧保存最近 32 个平台下发请求的 `request_id`。运行中任务的 `request_id` 永远不能重复；已完成记录 1 小时没有新数据后自动清理。收到重复 `request_id` 时，不重新执行指令，直接应答 `duplicate_request_id`。设备对同一请求的分片应答、进度上报和最终应答可以复用同一个 `request_id`。去重记录至少包含 `request_id`、首次收到时间、最近更新时间、方法名、运行状态和最终结果摘要。记录满 32 个时，优先清理最旧的已完成记录，不得挤掉运行中任务。

## 9. 线程 2 核心流程

线程 2 只负责 Python 脚本生命周期。

```text
Python 脚本线程启动
  |
  v
加载脚本配置
  |
  v
启动 Python 运行环境
  |
  v
运行用户脚本
  |
  v
脚本退出或异常？
  |-- 正常退出 --> 上报 SCRIPT_EXITED，按配置决定是否重启脚本
  |-- 异常退出 --> 上报 SCRIPT_EXCEPTION，按异常策略处理
```

线程 2 运行要求：

1. 不等待线程 1 完成联网、`dev_mqtt` 连接或配置检查。
2. 脚本运行期间不得直接修改系统配置文件。
3. 脚本异常时必须向线程 1 上报异常摘要。
4. 线程 1 发出 `CONFIG_UPDATING` 或 `OTA_UPDATING` 后，线程 2 应停止脚本并释放资源。
5. 脚本优雅停止最长等待 5 秒；超过 5 秒仍未退出时，线程 1 记录超时原因，并按脚本异常策略处理。
6. 如果脚本需要联网能力，应自行通过内部接口查询网络状态；网络未就绪时脚本按自身业务逻辑降级运行或等待。
7. 脚本文件操作只能访问用户数据区。脚本侧访问 `/a` 时，设备映射为 `datafs:/a`。
8. 脚本路径允许出现 `../`，但设备必须先做路径规范化；规范化后的最终路径不得逃出 `datafs:/`，否则拒绝访问并返回路径非法。
9. `datafs` 达到 1 MB 限额或剩余空间不足时，脚本写操作返回失败；设备记录 warn/error 日志，并上报脚本异常摘要，但不主动重启设备，除非脚本自身崩溃或触发已配置的异常策略。

## 10. 配置更新策略

配置更新由线程 1 统一执行。

配置更新流程：

1. 收到平台配置更新指令。
2. 先检查平台下发的 `seq_id`；只有 `seq_id > 当前 seq_id` 才允许继续。
3. 如果 `seq_id` 小于或等于当前值，拒绝更新，保留旧配置，并通过 MQTT 使用同一 `request_id` 上报拒绝原因。
4. 判断当前生效配置区，选择另一个配置区作为写入目标。例如当前为 `cfgfs:/cfg_a`，则写入 `cfgfs:/cfg_b`。
5. 下载新的 `manifest.jsonl`。
6. 根据 `manifest.jsonl` 下载配置包内全部文件；当前配置包固定包含 `config.json` 和 `main.py`。
7. 校验所有文件大小和 SHA-256。
8. 校验 `manifest.jsonl` 中的 `seq_id`、`min_product_version`、`file_count` 等描述信息。
9. 目标配置区完整校验通过后，通知线程 2 即将切换配置，线程 2 应停止脚本并释放相关资源。
10. 将目标配置区标记为可切换状态。
11. 更新 NVS 中的当前生效区、`seq_id` 和 `manifest_sha256`。
12. 上报配置更新结果。
13. 重启设备。

开机同步策略：

1. 开机后读取当前生效区的 `manifest.jsonl`。
2. 将当前 `seq_id`、`manifest_sha256` 和固件版本上报给平台。
3. 平台判断配置是否最新。
4. 如果平台判断配置不是最新，或设备本地校验发现任何异常，设备进入整包配置更新流程。
5. 整包配置更新必须下载并校验 `manifest.jsonl` 中列出的全部文件，不做单文件补丁更新。

配置更新失败策略：

| 阶段 | 失败处理 |
| --- | --- |
| `manifest.jsonl` 下载失败 | 保留旧配置，稍后重试或等待平台再次下发 |
| 文件下载失败 | 删除目标配置区临时文件，保留旧配置，上报失败 |
| SHA-256 校验失败 | 删除目标配置区临时文件，保留旧配置，上报失败 |
| 描述信息校验失败 | 删除目标配置区临时文件，保留旧配置，上报失败 |
| `seq_id` 小于或等于当前值 | 拒绝更新，保留旧配置，上报拒绝原因 |
| 切换生效区前脚本停止超时 | 不切换生效区，保留旧配置，上报 `script_stop_timeout` |
| NVS 生效区切换失败 | 保留旧配置，上报失败 |
| 重启后校验失败 | 按配置双区规则选择有效配置区；如果两区都无效，则视为无本地配置并重新进入整包配置更新流程 |

## 11. OTA 策略

OTA 由线程 1 统一执行。OTA 过程中线程 2 必须停止脚本。

服务器设定的升级时间统一使用 UTC。协议字段使用毫秒 Unix 时间戳时，本身按 UTC 解释；如果后续扩展 ISO 8601 字符串，必须使用 `Z` 后缀或明确 UTC 偏移。设备只有在 UTC 可信时才允许执行定时 OTA；如果未取得可信 UTC，应保持任务等待状态并上报等待授时原因。立即执行类 OTA 指令不受 UTC 可信限制。

OTA 流程：

1. 收到平台 OTA 指令或到达服务器设定的升级检查时间。
2. 判断目标版本是否高于当前版本；目标版本小于或等于当前版本时必须拒绝，并通过 MQTT 使用同一 `request_id` 上报拒绝原因。
3. 通知线程 2 停止脚本。
4. 下载固件。
5. 校验文件大小和 SHA-256。
6. 写入 OTA 分区。
7. 设置下次启动分区。
8. 上报 OTA 进度。
9. 重启设备。
10. 重启后确认当前固件版本。
11. 上报 OTA 成功或失败。

OTA 失败策略：

| 阶段 | 失败处理 |
| --- | --- |
| 下载失败 | 保持当前固件运行，上报失败 |
| 校验失败 | 删除下载文件，保持当前固件运行 |
| 写入失败 | 保持当前固件运行，上报失败 |
| 目标版本小于或等于当前版本 | 拒绝升级，保持当前固件运行，上报拒绝原因 |
| 新固件启动失败 | 由 OTA 安全机制回到上一可启动固件并上报失败；该动作仅用于启动失败恢复，不作为平台可下发的版本回滚策略 |
| 新固件启动成功但版本不匹配 | 上报异常，等待平台处理 |

## 12. 异常处理策略

### 12.1 网络异常

| 异常 | 处理策略 |
| --- | --- |
| 联网失败 | 按退避策略重试 |
| 网络断开 | 重新联网，恢复后重连 `dev_mqtt` |
| DNS 解析失败 | 退避重试，可切换备用 DNS |
| 长时间无法联网 | 保持脚本策略按配置执行，并持续尝试恢复网络 |

### 12.2 MQTT 异常

| 异常 | 处理策略 |
| --- | --- |
| 连接失败 | 按退避策略重连 |
| 鉴权失败 | 保留 MQTT 信息，等待后台修正账号或维护工具重写 |
| 订阅失败 | 重试订阅；下行主题订阅成功前，设备管理通道不进入在线状态，但不影响线程 2 运行 |
| 连接断开 | 默认不依赖 Last Will；设备恢复网络后重新上线。若平台配置启用 Last Will，则 Broker 可代发离线状态 |

### 12.3 配置异常

| 异常 | 处理策略 |
| --- | --- |
| 本地配置不存在 | 使用出厂默认配置 |
| NVS 配置状态不存在或损坏 | 尝试扫描 `cfgfs:/cfg_a`、`cfgfs:/cfg_b`，选择校验通过且 `seq_id` 最新的配置区；如果两个区 `seq_id` 相同，选择 `cfgfs:/cfg_a` |
| 当前配置区 `manifest.jsonl` 校验失败 | 按配置双区规则选择有效配置区，并触发整包配置更新 |
| 新配置下载失败 | 保留旧配置区 |
| 新配置应用失败 | 不切换生效区，保留旧配置区并上报失败 |

### 12.4 OTA 异常

| 异常 | 处理策略 |
| --- | --- |
| OTA 包下载失败 | 保持当前固件运行 |
| OTA 包校验失败 | 删除 OTA 包并上报失败 |
| OTA 写入失败 | 保持当前固件运行 |
| OTA 目标版本小于或等于当前版本 | 拒绝升级并上报拒绝原因 |
| OTA 后启动失败 | 由 OTA 安全机制回到上一可启动固件并上报失败；该动作仅用于启动失败恢复 |

### 12.5 datafs/logfs 异常

| 异常 | 处理策略 |
| --- | --- |
| `datafs` 挂载失败 | 正常运行启动重试 3 次后格式化并重新挂载一次；仍失败则脚本文件操作返回失败，线程 1 继续运行并上报存储异常 |
| `datafs` 达到 1 MB 限额或空间不足 | 脚本写操作返回失败，不自动删除用户文件，不重启设备 |
| `logfs` 挂载失败 | 正常运行启动重试 3 次后格式化并重新挂载一次；仍失败则关闭或降级本地持久化日志，仅保留内存计数和最近错误摘要 |
| `logfs` 写满 | `log_task` 异步删除最旧段文件，直到使用率不高于 50%；删除期间不得阻塞线程 1 和线程 2 |
| `logfs` 清理失败 | 暂停持久化日志并增加丢弃计数，管理平面和脚本线程继续运行 |

### 12.6 Python 脚本异常

脚本异常默认策略为 `restart_by_watchdog`。

| 策略 | 说明 |
| --- | --- |
| `restart_immediately` | 线程 1 收到脚本异常后立即重启设备 |
| `restart_by_watchdog` | 停止喂脚本相关看门狗，由看门狗触发重启 |
| `ignore` | 不重启设备，仅上报异常并按配置决定是否重启脚本 |

脚本异常上报内容应包含脚本名称、异常摘要、堆栈信息和是否截断。

### 12.7 看门狗策略

设备应至少监控以下对象：

| 对象 | 策略 |
| --- | --- |
| 线程 1 | 必须定期喂狗，卡死时重启设备 |
| 线程 2 | 由线程 1 监控脚本运行状态 |
| 网络恢复流程 | 不应因长时间网络失败导致系统卡死 |
| OTA/配置更新 | 长时间无进展时中止流程并上报失败 |

## 13. 重启策略

以下场景允许重启设备：

1. OTA 成功并需要切换固件。
2. 配置更新成功并需要重新加载系统配置。
3. 服务器下发重启指令。
4. 脚本异常策略要求重启。
5. 关键系统线程卡死。
6. 配置双区均损坏且无法继续运行。

设备重启前应尽量完成：

1. 上报重启原因。
2. 保存运行统计。
3. 停止 Python 脚本。
4. 关闭或断开 `dev_mqtt`。
5. 刷新运行日志和文件系统缓存。

## 14. 运行状态判定

设备运行状态分为主状态和分状态。主状态字段为 `status`，用于平台快速判断设备当前最重要的状态；分状态字段包括 `network_status`、`mqtt_status`、`script_status`、`task_status`，用于避免网络在线、脚本运行、配置更新等状态互相覆盖。线程 2 的脚本运行状态不得依赖设备管理在线状态。

设备通过 `up_raw` 中的 `status.report` 上报的主状态枚举固定如下：

| 状态 | 说明 |
| --- | --- |
| `booting` | 设备启动中 |
| `offline` | 设备管理通道离线 |
| `online` | 设备管理通道在线 |
| `config_checking` | 正在检查配置 |
| `config_updating` | 正在更新配置 |
| `ota_checking` | 正在检查 OTA |
| `ota_upgrading` | 正在 OTA 升级 |
| `script_starting` | Python 脚本启动中 |
| `script_running` | Python 脚本运行中 |
| `script_stopped` | Python 脚本已停止 |
| `script_error` | Python 脚本异常 |
| `busy` | 设备正在执行互斥操作 |
| `factory_resetting` | 正在恢复出厂 |
| `rebooting` | 即将重启或正在重启 |

分状态枚举固定如下：

| 字段 | 取值 |
| --- | --- |
| `network_status` | `disconnected`、`connecting`、`connected`、`degraded` |
| `mqtt_status` | `disconnected`、`not_configured`、`connecting`、`connected`、`reconnecting`、`auth_failed` |
| `script_status` | `disabled`、`starting`、`running`、`stopped`、`error` |
| `task_status` | `idle`、`busy`、`config_checking`、`config_updating`、`ota_checking`、`ota_upgrading`、`log_uploading`、`factory_resetting`、`rebooting` |

### 14.1 脚本运行状态

设备满足以下条件后，认为脚本已进入运行状态：

1. 本地脚本配置已加载。
2. Python 运行环境已启动。
3. 用户脚本已启动，或配置明确禁用脚本。

### 14.2 设备管理在线状态

设备满足以下条件后，认为设备管理通道已进入在线状态：

1. 网络已连接。
2. 系统时间已完成至少一次同步，或已进入允许无准确时间运行的降级状态。
3. `dev_mqtt` 已连接。
4. 下行主题已订阅成功。
5. 已上报在线状态。
6. 已上报基础属性和配置状态。
7. 未发现必须立即执行的 OTA 或配置更新。

## 15. 待确认事项

以下事项需要在实现前确认：

1. 后续产品形态是否需要支持 Wi-Fi、4G、以太网自动切换；当前版本默认 4G。
2. 设备是否需要本地维护入口，例如串口、蓝牙或本地 Web 配网。
3. 后续如果需要维护工具在线重写 MQTT 信息，应单独定义出厂/维护接口和权限边界。
