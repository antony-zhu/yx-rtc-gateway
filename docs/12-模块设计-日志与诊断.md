## 2. 设计目标

1. 日志模块用于排查设备运行、脚本异常、MQTT 细节、配置更新、OTA 和网络问题。
2. 日志持久化固定使用 `logfs:/` 分区根目录，不创建 `/log` 子目录。
3. `logfs` 是非核心分区，挂载失败、写满、索引损坏或清理失败不得影响线程 1 和线程 2。
4. 线程 1 和线程 2 只投递日志，不直接写 Flash、不扫描 `logfs:/`、不删除日志文件。
5. `log_task` 低优先级异步写入日志、维护索引和执行清理。
6. 日志文件按单调递增段号命名，不按日期命名。
7. 服务器查询日志时不感知段文件，只按条数、时间、等级、模块等条件查询。
8. 本地日志容量目标默认 1 MB，保留时间目标默认 30 天，扫描周期默认 1 天。
9. `logfs` 使用率超过 80% 或写入空间不足时触发后台清理，清理到不高于 50%。
10. MQTT 日志直传完整 Payload 最大 8192 字节，超过必须 HTTP POST。
11. Release 版本不得输出敏感信息。

## 3. 模块边界

建议目录：

```text
main/
  log/
    gw_log.c
    gw_log_queue.c
    gw_log_writer.c
    gw_log_index.c
    gw_log_cleaner.c
    gw_log_query.c
    gw_log_upload.c
    gw_diag.c
```

职责拆分：

| 模块 | 职责 |
| --- | --- |
| `gw_log` | 对外日志入口、等级过滤、脱敏、统一格式化 |
| `gw_log_queue` | 非阻塞日志队列、丢弃计数、队列状态 |
| `gw_log_writer` | 段文件追加、段文件切换、当前写入状态 |
| `gw_log_index` | `logfs:/index.json` 维护、重建和查询辅助 |
| `gw_log_cleaner` | 周期扫描、容量清理、写满恢复 |
| `gw_log_query` | `log.query` 过滤、结果估算、MQTT 直传数据构造 |
| `gw_log_upload` | 大日志查询 HTTP POST 上传和最终 MQTT 应答 |
| `gw_diag` | 诊断计数、最近错误摘要、运行统计聚合 |

不负责：

1. 不决定设备是否重启。
2. 不执行配置更新或 OTA。
3. 不保存系统 NVS 加密参数。
4. 不替 MQTT 做离线缓存。
5. 不直接进入 Python VM。
6. 不清理 `datafs:/` 用户文件。

## 4. 任务和内存

固定任务：

| 任务 | 栈大小 | 内存来源 | 说明 |
| --- | ---: | --- | --- |
| `log_task` | 8 KB | 内部 RAM | 低优先级日志写入、索引和清理任务 |

辅助 worker：

| 任务 | 归属 | 说明 |
| --- | --- | --- |
| `log_upload_worker` | 线程 1 管理平面 | 大日志 HTTP POST 上传，可与 `log_task` 分离实现 |

内存规则：

1. `log_task` 栈使用内部 RAM。
2. 日志队列元数据应使用内部 RAM 或静态内存。
3. 单条日志正文和上传缓冲可使用 PSRAM；PSRAM 不足时丢弃该条日志或拒绝本次查询。
4. 日志队列必须非阻塞，调用方不得等待 Flash 写入。
5. 日志查询构造大对象时应分批读取，不一次性把全部日志复制到内部 RAM。

队列建议：

| 项目 | 建议值 | 说明 |
| --- | ---: | --- |
| 队列最大条数 | 64 | 防止短时间日志突增拖垮内存 |
| 队列正文总字节 | 64 KB | 超过后新日志按等级丢弃 |
| 投递超时 | 0 | 非阻塞投递 |

队列满处理：

1. `debug` 和 `info` 可以直接丢弃并增加计数。
2. `warn` 和 `error` 尽量保留；如果队列已满仍然不得阻塞调用方。
3. 丢弃日志时记录 `dropped_debug`、`dropped_info`、`dropped_warn`、`dropped_error`。
4. 丢弃计数应进入诊断状态和后续日志摘要。

## 5. 日志文件结构

`logfs` 目录结构：

```text
logfs:/
  index.json
  log_000001.jsonl
  log_000002.jsonl
  log_000003.jsonl
```

固定规则：

| 项目 | 规则 |
| --- | --- |
| 文件系统 | LittleFS |
| 分区路径 | `logfs:/` |
| 固定子目录 | 无 |
| 段文件名 | `log_<segment_id>.jsonl` |
| `segment_id` | 单调递增，不依赖 UTC |
| 段文件大小 | 128 KB，固定值，不做运行时配置 |
| 单条日志最大长度 | 4096 字节，固定值，不做运行时配置 |
| 文件格式 | JSON Lines，一行一条 |
| 索引文件 | `logfs:/index.json` |

段文件规则：

1. 当前段达到 128 KB 后切换到下一个段。
2. 日志行超过 4096 字节时截断，并设置 `truncated=true`。
3. 普通日志追加不使用临时文件和原子替换。
4. `index.json` 使用临时文件和原子替换。
5. 段文件是设备内部实现，平台查询时不得暴露为主要概念。

## 6. 日志记录格式

单行日志建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `seq` | integer | 设备本地日志序号，单调递增 |
| `boot_id` | string | 本次启动 ID |
| `uptime_ms` | integer | 本次启动后的运行时间 |
| `ts` | integer | UTC 毫秒时间戳；UTC 不可信时填 0 |
| `time_synced` | boolean | 写入该条日志时 UTC 是否可信 |
| `level` | string | `debug`、`info`、`warn`、`error` |
| `module` | string | 模块名，例如 `mqtt`、`network`、`script`、`ota` |
| `event` | string | 可选，事件名 |
| `msg` | string | 日志摘要 |
| `code` | integer | 可选，错误码或业务码 |
| `request_id` | string | 可选，关联平台请求 |
| `reason_code` | string | 可选，细分失败原因 |
| `truncated` | boolean | 是否被截断 |
| `data` | object | 可选，少量结构化上下文 |

记录示例：

```jsonl
{"seq":1024,"boot_id":"boot-0001","uptime_ms":120345,"ts":1703424234214,"time_synced":true,"level":"info","module":"mqtt","event":"connected","msg":"connected","code":0}
```

字段规则：

1. `seq` 在设备本地递增，重启后可继续递增，也可由 `boot_id + seq` 唯一区分。
2. UTC 不可信时，`ts=0` 且 `time_synced=false`。
3. `module` 使用小写单词或下划线。
4. `msg` 应简短，不放大块正文。
5. `data` 只放必要上下文，避免把大 Payload 写入日志。
6. `request_id` 用于串联 MQTT 指令、HTTP 下载、日志上传等流程。

## 7. 日志来源

日志来源：

| 来源 | 例子 |
| --- | --- |
| 启动与硬件 | 启动原因、看门狗、栈水位 |
| 存储 | NVS 读写、LittleFS 挂载、`cfgfs`/`datafs`/`logfs` 异常 |
| 网络 | 4G 注册、IP 获取、断线、重连 |
| 出厂 MQTT 信息 | 连接信息缺失、解密失败、鉴权失败等诊断 |
| `dev_mqtt` | 连接、订阅、断开、鉴权失败、重连 |
| 协议 | `request_id` 去重、参数校验、互斥拒绝 |
| 配置 | manifest 下载、校验、双区切换 |
| OTA | 下载、校验、写入、重启 |
| 脚本 | 脚本启动、退出、异常、停止超时 |
| 脚本 MQTT/HTTP | 用户业务网络状态摘要 |
| 本地诊断 | 队列丢弃、日志清理、上传结果 |

等级建议：

| 等级 | 用途 | 默认持久化 |
| --- | --- | --- |
| `debug` | 临时调试细节 | 否 |
| `info` | 正常关键流程 | 是 |
| `warn` | 可恢复异常或降级 | 是 |
| `error` | 操作失败或不可恢复局部异常 | 是 |

规则：

1. `debug` 默认不持久化，只有平台临时开启后才写入 `logfs`。
2. MQTT 详细收发日志默认关闭，避免占用 Flash 和带宽。
3. 配置、OTA、恢复出厂等关键流程至少写入 `info` 和失败 `error`。
4. 脚本异常必须写入本地日志，同时按协议通过 `up_raw` 上报 `script.exception`。

## 8. 写入流程

普通日志写入流程：

```text
调用方
  -> gw_log_write()
  -> 等级过滤和脱敏
  -> 非阻塞投递 log_queue
  -> log_task 取出
  -> 追加到当前 log_*.jsonl
  -> 更新内存索引
  -> 必要时切段或异步刷新 index.json
```

写入规则：

1. 调用方不直接打开 `logfs:/log_*.jsonl`。
2. 调用方不扫描 `logfs:/`。
3. 调用方不删除日志段。
4. `log_task` 追加写入当前段文件。
5. 当前段满 128 KB 后切换新段。
6. 平时写日志不扫描整个 `logfs:/`。
7. `index.json` 可按段切换、定时或清理后刷新，不要求每条日志同步刷新。

写入失败处理：

1. 如果 `logfs` 未挂载，日志不持久化，只增加内存计数。
2. 如果追加写入返回空间不足，丢弃当前低优先级日志并触发后台清理。
3. 如果当前日志为 `error`，可尝试在清理完成后写入一条摘要，但不得阻塞调用方。
4. 清理失败时进入 `log_persist_paused`，暂停持久化日志。
5. 进入暂停状态后继续累计丢弃计数和最近错误摘要。

## 9. 索引文件

`logfs:/index.json` 用于加速查询，不作为唯一可信数据。

建议内容：

| 字段 | 说明 |
| --- | --- |
| `version` | 索引格式版本 |
| `current_segment_id` | 当前写入段号 |
| `next_seq` | 下一条日志序号 |
| `total_size` | 段文件总大小 |
| `total_count` | 日志总条数 |
| `oldest_seq` | 最小日志序号 |
| `newest_seq` | 最大日志序号 |
| `segments` | 段文件摘要数组 |

段摘要字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 段号 |
| `file` | 文件名，例如 `log_000001.jsonl` |
| `size` | 文件大小 |
| `line_count` | 日志条数 |
| `min_seq` | 段内最小 `seq` |
| `max_seq` | 段内最大 `seq` |
| `min_ts` | 段内最小可信 UTC，未知为 0 |
| `max_ts` | 段内最大可信 UTC，未知为 0 |

索引维护规则：

1. 开机挂载 `logfs` 后，`log_task` 扫描 `logfs:/log_*.jsonl` 重建或校正索引。
2. `index.json` 损坏、缺失或版本不匹配时删除并重建。
3. `index.json` 写入使用临时文件和原子替换。
4. 查询以索引作为加速路径，但读取日志行时仍应容忍段文件被删除或损坏。
5. 清理删除段文件后必须刷新索引。

## 10. 清理策略

可配置参数：

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| `log.retention_days` | 30 | 本地日志保留目标，单位天 |
| `log.max_size` | 1048576 | 本地日志容量目标，单位字节 |
| `log.scan_interval_sec` | 86400 | 本地日志扫描清理周期 |
| `log.clean_high_watermark_percent` | 80 | `logfs` 使用率达到该值时触发清理 |
| `log.clean_target_percent` | 50 | 后台清理目标使用率 |

固定参数：

| 参数 | 固定值 |
| --- | ---: |
| 段文件大小 | 128 KB |
| 单条日志最大长度 | 4096 字节 |
| MQTT 直传最大 Payload | 8192 字节 |

清理触发条件：

1. 开机重建索引后发现超出容量或时间目标。
2. 周期扫描时间到达，默认 1 天。
3. `logfs` 使用率超过 80%。
4. 日志写入返回空间不足。
5. 平台或控制台显式请求日志清理。

清理流程：

```text
log_clean_async(reason)
  -> log_task 设置 clean_running
  -> 读取索引或重建索引
  -> 如果 UTC 可信，优先删除超过 retention_days 的旧段
  -> 如果总大小超过 log.max_size，删除最旧段
  -> 如果 logfs 使用率仍高于 50%，继续删除最旧段
  -> 刷新 index.json
  -> 恢复或保持持久化状态
```

规则：

1. 清理由 `log_task` 后台执行，不阻塞线程 1 和线程 2。
2. 删除顺序按最旧 `segment_id` 优先。
3. 如果设备未授时，时间保留目标不可用，只按 `segment_id` 和容量清理。
4. 清理目标优先保证 `logfs` 使用率不高于 50%。
5. `1 MB + 256 KB` 是默认预估浮动，不作为精确硬限制。
6. 清理失败时暂停持久化日志，不重启设备。
7. `logfs` 写满不能导致系统崩溃。

## 11. 查询流程

平台通过 `log.query` 查询本地日志。`log.query` 是查询类指令，不占用全局非查询互斥任务。

支持过滤：

| 字段 | 说明 |
| --- | --- |
| `mode` | `recent` 或 `all` |
| `limit` | `mode=recent` 时返回最近 N 条；默认 100 |
| `start_time` | 可选，起始 UTC 毫秒时间戳 |
| `end_time` | 可选，结束 UTC 毫秒时间戳 |
| `level` | 可选等级数组，空数组表示不过滤 |
| `module` | 可选模块数组，空数组表示不过滤 |
| `upload_url` | 大结果 HTTP POST 上传地址 |

查询规则：

1. 服务器不感知段文件。
2. 查询时先基于索引筛选候选段，再逐行过滤。
3. `mode=recent` 未指定 `limit` 时默认 100。
4. `mode=all` 可能产生大结果，建议服务器始终提供 `upload_url`。
5. 设备未授时时，按 `seq` 和写入顺序查询可靠；按时间过滤只对 `time_synced=true` 的日志可靠。
6. 当前版本不使用 MQTT 分片。
7. MQTT 直接返回时 `chunk_index=1`、`chunk_count=1`。
8. 完整 `log.query.reply` MQTT Payload 预计超过 8192 字节时，必须使用 HTTP POST。
9. 超过 8192 字节且未提供 `upload_url` 时，应答 `413`。

查询并发：

1. 小结果 MQTT 直传查询可并行处理。
2. 大结果 HTTP POST 上传最多同时执行 1 个。
3. 已有日志上传任务运行时，新的大日志上传请求返回 `423 log_upload_busy`。
4. 大日志上传运行期间，状态查询、属性查询和小日志查询仍可执行。
5. 日志查询不得长时间持有写入锁；应基于段文件快照读取。

## 12. MQTT 直传

当完整 MQTT 应答 Payload 不超过 8192 字节时，设备可直接返回日志内容。

返回内容建议：

| 字段 | 说明 |
| --- | --- |
| `delivery` | 固定 `mqtt` |
| `chunk_index` | 固定 1 |
| `chunk_count` | 固定 1 |
| `total_count` | 返回日志条数 |
| `total_size` | 日志内容大小 |
| `logs` | 日志数组 |

规则：

1. 8192 字节按完整 MQTT Payload 计算，不只计算 `logs` 数组。
2. 设备应先估算 Payload 大小，必要时减少返回条数或要求 HTTP POST。
3. 如果 `mode=recent` 的指定 `limit` 导致结果超过 8192 字节，且未提供 `upload_url`，返回 `413`，不自动截断成不完整结果。
4. MQTT 断开时不缓存日志查询应答。

## 13. HTTP POST 上传

当日志查询结果超过 8192 字节时，服务器必须提供 `upload_url`，设备通过 HTTP POST 上传。

上传根对象固定包含：

| 字段 | 说明 |
| --- | --- |
| `device_id` | 设备业务标识 |
| `request_id` | 原始 MQTT 请求 ID |
| `sha256` | 上传内容 SHA-256 |
| `file_type` | 固定 `log` |
| `timestamp` | UTC 毫秒时间戳，UTC 不可信时填 0 |
| `payload` | 日志查询结果 |

`payload` 建议字段：

| 字段 | 说明 |
| --- | --- |
| `mode` | 查询模式 |
| `total_count` | 日志条数 |
| `total_size` | 日志内容大小 |
| `logs` | 日志数组 |
| `filter` | 实际使用的过滤条件 |

HTTP 规则：

| 参数 | 默认值 |
| --- | --- |
| URL 协议 | 由 `upload_url` 的 `http://` 或 `https://` 决定 |
| 连接超时 | 10 秒 |
| 应答间隔超时 | 3 秒 |
| 总超时 | 不定义 |
| 重试次数 | 最多 3 次 |
| 重试间隔 | 3 秒、10 秒、30 秒 |
| Content-Type | `application/json` |
| 成功判定 | 服务端返回 JSON 中 `code=200` |

应答规则：

1. 上传耗时较长时，设备可以先通过 `log.query.reply` 返回 `accepted`。
2. HTTP POST 完成后必须使用同一个 `request_id` 返回最终 MQTT 应答。
3. HTTP 失败时最终应答包含 `http_status`、`server_code` 和 `reason_code`。
4. 未收到 HTTP 响应时 `http_status=0`。
5. 服务端 `code != 200` 视为失败。
6. 上传期间 `task_status` 可临时显示为 `log_uploading`，但不占用全局非查询互斥任务。

## 14. 实时日志上报

实时日志通过 `/yx_gw/YxzhNode${device_id}/thing/model/up_raw` 上报，默认关闭。

启用场景：

1. 调试版本临时排查问题。
2. 平台临时开启故障排查。
3. 紧急场景需要实时观察设备状态。

规则：

1. `log.enabled=false` 时不实时上报日志。
2. 实时上报不替代本地 `logfs:/` 持久化。
3. MQTT 断开时不缓存实时日志。
4. 实时日志 Payload 不得超过 8192 字节。
5. 实时上报仍必须执行敏感信息脱敏。
6. Release 版本默认禁止输出 `debug` 细节和敏感字段。

## 15. 故障摘要和诊断状态

由于 `logfs` 可能不可用，关键故障摘要不得只依赖本地日志。

最小故障摘要建议保存在 NVS 或 RAM：

| 字段 | 说明 |
| --- | --- |
| `last_fault_module` | 最近故障模块 |
| `last_fault_reason` | 最近故障原因 |
| `last_fault_uptime_ms` | 最近故障发生时运行时间 |
| `last_reset_reason` | 最近重启原因 |
| `fault_count` | 故障计数 |

日志诊断状态建议：

| 字段 | 说明 |
| --- | --- |
| `log.mounted` | `logfs` 是否已挂载 |
| `log.persist_enabled` | 本地持久化是否启用 |
| `log.persist_paused` | 是否因写入/清理失败暂停持久化 |
| `log.segment_count` | 当前段文件数量 |
| `log.total_size` | 当前日志段总大小 |
| `log.current_segment_id` | 当前写入段号 |
| `log.queue_depth` | 当前队列深度 |
| `log.dropped_count` | 总丢弃条数 |
| `log.clean_running` | 是否正在后台清理 |
| `log.last_clean_result` | 最近一次清理结果 |
| `log.last_write_error` | 最近一次写入错误 |
| `log.upload_running` | 是否正在上传日志 |

上报原则：

1. 基础日志参数作为属性上报。
2. 运行态诊断可放入状态查询或属性查询结果。
3. `logfs` 异常应通过状态或属性暴露给平台。
4. 故障摘要不得包含密码、token、密钥和用户敏感字段。

## 16. 敏感信息规则

Release 版本禁止写入本地日志或 MQTT 日志：

1. MQTT 密码。
2. 设备管理 MQTT 出厂密码。
3. HTTP URL 中的 token、签名、密钥类 query。
4. 出厂凭据或产测密钥。
5. NVS 加密密钥和中间派生密钥。
6. Wi-Fi 密码。
7. 用户配置中的密钥类字段。
8. 用户业务明文大 Payload。

脱敏规则：

1. 需要打印标识符时，最多保留前 3 位和后 3 位，中间用 `***`。
2. URL 日志默认只保留 scheme、host、path，不保留 query。
3. JSON 中常见字段 `password`、`token`、`secret`、`key`、`authorization` 必须脱敏。
4. Debug 版本如需输出敏感上下文，也必须显式调用脱敏函数。
5. `gw_log_write()` 是日志总入口，必须对 `message` 和 `result.detail` 做最终脱敏兜底；如果脱敏缓冲分配失败，应写入固定占位，不得回退输出原文。

## 17. 异常策略

| 异常 | 处理 |
| --- | --- |
| `logfs` 挂载失败 | 重试 3 次后格式化并重新挂载；仍失败则关闭本地持久化，保留内存计数和最近错误摘要 |
| `index.json` 损坏 | 删除索引并后台重建 |
| 段文件损坏 | 跳过损坏行，记录损坏计数 |
| 队列满 | 丢弃低优先级日志并计数，不阻塞调用方 |
| 单条日志超过 4096 字节 | 截断并标记 `truncated=true` |
| `logfs` 写满 | 触发后台清理，必要时暂停持久化 |
| 清理失败 | 暂停持久化，不影响设备管理和脚本 |
| HTTP 上传失败 | 使用同一个 `request_id` 通过 MQTT 返回失败 |
| MQTT 断开 | 不缓存实时日志或查询应答 |
| UTC 不可信 | `ts=0`，时间过滤只对已可信日志可靠 |

## 19. 测试建议

写入测试：

1. `log_task` 未运行时，调用方写日志不阻塞。
2. `logfs` 重试和格式化后仍挂载失败时，线程 1 和脚本仍可运行。
3. 单条日志超过 4096 字节时被截断。
4. 段文件达到 128 KB 后切换新段。
5. `debug` 默认不持久化。
6. 队列满时丢弃计数增加。

清理测试：

1. 开机能扫描 `logfs:/log_*.jsonl` 重建索引。
2. `index.json` 损坏时能删除并重建。
3. `logfs` 使用率超过 80% 后触发清理。
4. 清理后使用率不高于 50%。
5. UTC 不可信时按段号删除最旧日志。
6. 清理失败后进入 `persist_paused`，系统不重启。

查询测试：

1. `mode=recent` 默认返回最近 100 条。
2. `level` 和 `module` 过滤正确。
3. UTC 不可信日志不参与可靠时间过滤。
4. MQTT 直传 Payload 不超过 8192 字节。
5. 超过 8192 且无 `upload_url` 返回 413。
6. 超过 8192 且有 `upload_url` 时执行 HTTP POST。
7. HTTP POST 返回 `code=200` 才算成功。
8. HTTP POST 失败后通过同一 `request_id` 返回失败。

安全测试：

1. Release 日志不包含 MQTT 密码。
2. URL query 中的 token 不进入日志。
3. NVS 加密密钥和派生材料不会写入 `logfs`。
4. 用户配置中的密钥类字段被脱敏。
