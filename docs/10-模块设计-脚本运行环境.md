## 2. 设计目标

1. 脚本运行环境只负责本地 Python 脚本生命周期和用户业务执行。
2. `script_task` 不等待联网、出厂 MQTT 参数检查、`dev_mqtt` 连接或配置检查完成。
3. 系统只有一个 MicroPython VM，只有 `script_task` 允许进入 VM。
4. Python VM heap、Python 对象、大缓冲和脚本模块动态内存必须使用 PSRAM。
5. 任务栈使用内部 RAM，`script_task` 栈固定 64 KB。
6. 脚本固定入口为当前生效配置区中的 `main.py`。
7. 脚本只能读写 `datafs:/`，不得直接写 `cfgfs`、`logfs` 或系统 NVS。
8. 脚本与 C 模块交互必须遵守状态快照、消息队列和 waker 模型。
9. 脚本 MQTT、HTTP、WS、外设输入等事件不得从 C 回调直接执行 Python。
10. 脚本异常不得拖垮设备管理平面。

## 3. 模块边界

建议目录：

```text
main/
  py_runtime/
    py_runtime.c
    gw_py_queue.c
  mpy/
    micropython_embed.c
    mod_runtime.c
    mod_system.c
    mod_net.c
    mod_mqtt.c
    mod_http.c
    mod_fs.c
    mod_board.c
    mod_ws.c
  script_api/
    <固件内置 Python 包装层>
```

职责划分：

| 模块 | 职责 |
| --- | --- |
| `py_runtime` | MicroPython VM 初始化、heap、脚本任务、运行入口、异常捕获 |
| `mpy` | MicroPython port、native module 绑定、`mpconfigport`、mphal |
| `script_api` | 公开 Python API 包装层，隐藏内部 `_xxx` 模块 |
| `gw_script_manager` | 线程 1 侧脚本状态监控、停止请求、异常接收 |
| `gw_py_queue` | C/Python 消息队列、waker、generation 校验辅助 |

不负责：

1. 不申请、获取或改写设备管理 MQTT 凭据。
2. 不连接或维护 `dev_mqtt`。
3. 不下载配置包或 OTA 固件。
4. 不直接修改系统 NVS 参数。
5. 不决定设备是否重启。

## 4. 任务和内存

任务要求：

| 项目 | 要求 |
| --- | --- |
| 任务名 | `script_task` |
| 栈大小 | 64 KB |
| 栈内存 | 内部 RAM |
| VM 数量 | 1 个 MicroPython VM |
| 进入 VM 的任务 | 仅 `script_task` |
| 栈高水位告警 | 剩余栈低于 8 KB 时记录 warn 并上报 |

内存要求：

| 内存 | 来源 |
| --- | --- |
| Python VM heap | PSRAM |
| Python 对象 | PSRAM |
| 脚本模块动态内存 | PSRAM |
| 脚本 MQTT/HTTP/WS 大缓冲 | PSRAM |
| 文件读写大缓冲 | PSRAM |
| 系统任务栈 | 内部 RAM |
| C 管理平面关键小对象 | 内部 RAM |

PSRAM 规则：

1. 脚本应用只能使用 PSRAM 作为主要 heap。
2. PSRAM 分配失败时，脚本 API 返回异常或脚本进入异常流程。
3. 不允许因为脚本 PSRAM 不足而回退占用内部 RAM 大块内存。
4. PSRAM 不足只影响脚本运行，不应影响设备管理平面。

## 5. 启动流程

脚本运行环境启动流程：

```text
script_task start
  -> 等待 py_runtime 初始化参数
  -> 读取当前生效配置区
  -> 加载 config.json
  -> 设置 Python sys.path
  -> 初始化公开 Python API 包装层
  -> 初始化 MicroPython VM heap
  -> 执行 main.py
  -> 进入 asyncio 事件循环
  -> 监听停止、异常、退出
```

启动约束：

1. 不等待线程 1 完成联网。
2. 不等待出厂 MQTT 参数检查完成。
3. 不等待 `dev_mqtt` 连接完成。
4. 不等待配置检查完成。
5. 当前生效配置区无效时，按运行设计文档选择上一份有效脚本或出厂默认脚本；没有可运行脚本时上报 `script_status=error` 或 `stopped`。

当前固件实现状态：

1. 已接入最小 MicroPython VM，`script_task` 会从当前 active 配置区执行 `cfgfs:/<active_slot>/main.py`。
2. Python VM heap 和脚本读取缓冲使用 PSRAM；任务栈仍使用内部 RAM。
3. 脚本正常返回后 `script_status=stopped`，不再用占位循环伪装为 `running`。
4. 已内置 `runtime` 模块，当前提供 `runtime.should_stop()`、`runtime.status()`、`runtime.stats()` 和 `runtime.log()`。
5. 已内置 `system` 模块，当前提供 `system.info()`、`system.time_status()`、`system.status()`、`system.net_status()` 和 `system.stats()`，仅暴露只读诊断信息，不暴露 MQTT 密码、NVS 加密材料和内部 handle。
6. 已内置 `fs` 模块，当前提供 `fs.read()`、`fs.write()`、`fs.listdir()`、`fs.exists()`、`fs.stat()`、`fs.mkdir()`、`fs.remove()`、`fs.rmdir()` 和 `fs.info()`，只访问 `datafs:/`。
7. 已内置 `config` 模块，当前提供 `config.info()` 和 `config.read()`，只读当前生效配置区的 `config.json`。
8. 已提供受限 `open()`：脚本侧 `/xxx` 映射到 `datafs:/xxx`；`cfgfs`、`logfs` 物理路径会被拒绝；路径穿透会被拒绝；写入 `datafs` 时按默认 1 MB 限额拦截。
9. 当前开放 `runtime.sleep_ms()`、`runtime.ticks_ms()`、`runtime.uptime_ms()` 等单调时间能力；UTC 可信状态通过 `system.time_status()` 读取，暂未开放 `time.time()` 和 UTC 日历时间 API。
10. 已支持同步 `def main()` 入口：顶层代码执行结束后，如果全局存在可调用的 `main`，框架会调用 `main()`；没有 `main()` 时保持顶层脚本兼容。
11. 已内置 `net` 模块，当前提供 `net.status()`、`net.is_connected()` 和 `net.wait_connected()`，只读查询网络状态，不允许脚本启动、停止或重置设备管理网络。
12. 已内置 `mqtt` 模块的基础多客户端 API，当前提供 `mqtt.create()`、`mqtt.configure()`、`mqtt.start()`、`mqtt.stop()`、`mqtt.destroy()`、`mqtt.connect()`、`mqtt.disconnect()`、`mqtt.publish()`、`mqtt.subscribe()`、`mqtt.unsubscribe()`、`mqtt.recv()`、`mqtt.poll()`、`mqtt.on()`、`mqtt.off()` 和 `mqtt.status()`；MQTT DATA 分片在 C 层组为完整 payload 后才进入 Python，`mqtt.Client` 类和 asyncio 包装层后续再封装。
13. 已内置 `http` 模块的异步提交和轮询 API，当前提供 `http.request()`、`http.get()`、`http.post()`、`http.poll()` 和 `http.status()`；`request/get/post` 返回本地 `request_id`，底层通过脚本专用 HTTP worker 执行，完成后由 `http.poll()` 读取结果，不直接在 Python VM 上下文调用 `gw_http_perform()`。
14. 已内置 `board` 模块，当前提供 `board.info()`、`board.pins()`、`board.reset_reason()`、LED 控制、RS485 读写和受控 CH374/CH37X 基础访问能力；这些接口只开放板级白名单能力，不暴露任意 GPIO 或底层驱动 handle。
15. 已内置 `ch37x` 模块，并注册 `ch34x` 作为同一模块别名，提供 `configure()`、`start()`、`stop()`、`destroy()`、`disconnect()`、`is_ready()`、`pending()`、`read()`、`write()` 和 `info()`；读缓冲使用 PSRAM，业务协议拆包放在 Python 侧。
16. `embedded/main/script_api/ymzl.py` 提供 YMZL/GS200 帧构建、校验、流式解析和 CH37X 组合封装，需随配置包下发后由脚本导入；流式解析器已按 MicroPython `bytearray` 行为处理分片缓存，固件不会把该业务协议写死到 C 层。
17. YMZL/GS200 应用层脚本 `ymzl_app.py` 已移除，正式固件关闭脚本自动启动；`ymzl.py` 仅作为协议/硬件模块保留，后续 dongle 业务由 C 服务接管。
18. 脚本异常摘要和 `runtime.log()` 消息已接入敏感字段脱敏，覆盖 `password`、`token`、`secret`、`key`、`authorization` 等常见字段和 URL query。
19. `async def main()`、WS、asyncio 包装层仍按后续模块计划逐步接入。

## 6. 配置和路径

脚本来源：

| 文件 | 来源 |
| --- | --- |
| `main.py` | 当前生效配置区 `cfgfs:/cfg_a/main.py` 或 `cfgfs:/cfg_b/main.py` |
| `config.json` | 当前生效配置区 `cfgfs:/cfg_a/config.json` 或 `cfgfs:/cfg_b/config.json` |
| 其他配置文件 | 当前生效配置区 `manifest.jsonl` 描述的文件 |
| 用户数据 | `datafs:/` |

规则：

1. 脚本入口固定为 `main.py`。
2. 配置包固定包含 `manifest.jsonl`、`config.json` 和 `main.py`。
3. 脚本运行期间不得修改当前配置区文件。
4. 配置更新不得清空 `datafs:/`。
5. 恢复出厂会清空 `datafs:/`。

脚本文件 API 路径映射：

| Python 路径 | 实际路径 |
| --- | --- |
| `/a` | `datafs:/a` |
| `/dir/file.txt` | `datafs:/dir/file.txt` |
| `/dir/../a` | `datafs:/a` |
| `/../../cfg_a/main.py` | 拒绝 |

路径规则：

1. 脚本只能访问 `datafs:/`。
2. 路径允许出现 `../`，但规范化后不得逃出 `datafs:/`。
3. 脚本 API 不接受 `cfgfs:/`、`logfs:/`、`/cfgfs/...`、`/logfs/...`、Windows 盘符或反斜杠路径作为用户文件路径。
4. `datafs` 默认限额 1 MB；达到限额时写操作返回失败。
5. `datafs` 写满不自动删除用户文件，不重启设备。

导入规则：

1. 用户模块只允许从当前 active 配置区导入，例如 `cfgfs:/cfg_a` 生效时只能从该目录及其子目录导入。
2. 脚本即使修改 `sys.path`，也不得导入其他配置区、`datafs:/` 或 `logfs:/` 中的文件。
3. `import` 只用于加载配置包中的代码文件；用户数据文件仍必须通过 `open()` 或 `fs` API 访问 `datafs:/`。

## 7. Python 入口规则

当前版本固定执行 `main.py`。

推荐入口：

```python
async def main():
    ...
```

兼容入口：

```python
def main():
    ...
```

执行规则：

1. 如果存在同步 `def main()`，框架调用该函数；函数返回表示脚本正常退出。
2. 如果存在 `async def main()`，目标设计是框架创建 asyncio 事件循环并运行该协程；当前实现尚未接入 asyncio 包装层，暂不作为可用入口。
3. 如果不存在 `main()`，执行 `main.py` 顶层代码；顶层代码返回表示脚本正常退出。
4. `main.py` 顶层异常或 `main()` 异常均进入脚本异常流程。
5. 正常退出时上报 `SCRIPT_EXITED`，默认不触发设备重启。
6. 用户脚本不需要再写 `if __name__ == "__main__": main()`；否则 `main()` 可能被用户代码和框架各调用一次。

建议用户脚本形态：

```python
import asyncio
import runtime

async def main():
    while not runtime.should_stop():
        await asyncio.sleep_ms(1000)
```

## 9. C 到 Python 事件桥接

所有 C 到 Python 的事件必须遵守：

```text
C callback / worker
  -> 更新 C 状态快照或写入 C 消息队列
  -> 调度轻量 waker
  -> script_task 被唤醒
  -> Python event task 调用 status()/poll()
```

规则：

1. waker 只负责唤醒，不承载业务数据。
2. MQTT payload、HTTP body、WS frame、外设数据必须先复制到 C 队列。
3. Python 判断状态必须调用 `status()`。
4. Python 读取消息必须调用 `poll()`。
5. 单轮 drain 消息默认 `max_batch=5`。
6. 队列满必须计数并暴露到 `stats()` 或 `status()`。

通用公开 API 形态：

```python
status = client.status()
evt = client.poll()
stats = client.stats()
```

## 10. 脚本 MQTT

脚本 MQTT 通过 `mqtt` 公开模块使用，底层必须走 `gw_mqtt_client` 和 `script_mqtt_adapter`。

事件路径：

```text
esp-mqtt callback
  -> gw_mqtt_client
  -> script_mqtt_adapter
  -> script_mqtt C queue
  -> waker
  -> script_task
  -> mqtt.recv()/poll() 或 Python mqtt callback
```

规则：

1. 脚本 MQTT 不使用 `dev_mqtt`。
2. 脚本不能读取或复用 `dev_mqtt` 凭据。
3. 脚本不能获得 `dev_mqtt` handle。
4. 当前版本脚本侧最多 4 个 MQTT client。
5. 脚本 MQTT 的 Topic、账号和业务协议由脚本自行管理。
6. 脚本 MQTT 与 `dev_mqtt` 凭据、连接和 handle 隔离，不额外按 Topic 禁止 `/yx_gw/YxzhNode${device_id}/thing/model/...`；系统 Topic 的安全边界由独立凭据和 Broker ACL 保证。
7. 脚本 MQTT 单条 Payload 最大 8192 字节。
8. 脚本 MQTT 大缓冲使用 PSRAM。
9. 脚本退出时自动断开并销毁所有脚本 MQTT client。
10. `mqtt.on()` 注册的 callback 只在 MicroPython VM 上下文执行；ESP-MQTT callback 只负责写 C 队列和唤醒脚本。

建议 API：

```python
h = mqtt.connect({
    "broker": "mqtt://example.com:1883",
    "client_id": "app-client",
    "username": "user",
    "password": "pass"
})

mqtt.subscribe(h, "a/b")
mqtt.publish(h, "a/b", b"hello")

evt = mqtt.recv(h, 100)
```

callback 形态：

```python
def on_data(evt):
    topic = evt["topic"]
    payload = evt["payload"]

mqtt.on(h, "data", on_data)
```

事件对象建议：

```python
{
    "handle": 1,
    "name": "business",
    "type": "data",
    "topic": "a/b",
    "payload": b"...",
    "payload_len": 3,
    "msg_id": 12,
    "timestamp_ms": 0,
    "reason": ""
}
```

## 11. 脚本 HTTP

脚本 HTTP 只服务用户业务，不用于设备注册、配置更新或 OTA。

规则：

1. 脚本 HTTP 请求必须有 timeout。
2. 默认 HTTP 连接超时和响应间隔超时可参考设备参数，但脚本 API 应允许调用方显式传入。
3. `http.request()`、`http.get()`、`http.post()` 只提交请求并返回本地 `request_id`，不等待网络完成。
4. 完成事件进入 C 层固定队列，脚本通过 `http.poll(timeout_ms=0)` 读取；无事件返回 `None`。
5. HTTP 响应 body 返回 Python 前必须受大小限制。
6. 大文件下载不得直接返回为 Python bytes。
7. 脚本 HTTP 失败只影响脚本业务。
8. 脚本退出时递增 HTTP generation，未执行的请求和未 poll 的完成事件会被清理；正在执行的旧请求完成后丢弃结果。

当前 C 模块第一版 API 为异步小响应接口：

```python
rid = http.get("https://example.com/api", max_bytes=8192)
rid = http.post(
    "https://example.com/api",
    b"{\"a\":1}",
    content_type="application/json",
    connect_timeout_sec=10,
    response_interval_timeout_sec=3,
    max_bytes=8192,
)
evt = http.poll(100)
```

`http.poll()` 返回对象包含 `type=done`、`request_id`、`ok`、`status_code`、`code`、`reason`、`esp_err`、`truncated`、`body_len`、`timestamp_ms` 和 `body`。HTTP 非 2xx、未收到响应、DNS/连接/读取失败都会作为完成事件返回并设置 `ok=false`；提交阶段的网络不可用、参数非法、队列满或资源不足会抛出 Python 异常。

## 12. 脚本文件系统

脚本文件 API 只允许访问 `datafs:/`。

建议 API：

```python
fs.write("/a.txt", b"hello")
data = fs.read("/a.txt")
items = fs.listdir("/")
meta = fs.stat("/a.txt")
```

规则：

1. 普通小文件读写可以同步。
2. 大文件读写必须分块，限制单次阻塞时间。
3. 写入前检查 `datafs` 限额和剩余空间。
4. 写失败应转换成 Python 异常。
5. 路径穿透返回 `EACCES` 或 `ValueError`。
6. `datafs` 写满返回 `ENOSPC`。
7. `datafs` 重试和格式化后仍挂载失败返回 `ENODEV`。
8. `fs.read()` 默认最多读取 64 KB，调用方可显式传入 `max_bytes`，但不得超过 `datafs` 默认限额。
9. `fs.write()` 默认覆盖写入，第三个参数为真时追加写入。

## 13. 网络和系统状态

脚本可查询网络和系统状态，但不得控制设备管理主流程。

允许：

1. 查询网络是否可用。
2. 查询 IP、4G 信号、SIM 状态等只读信息。
3. 查询 UTC 是否可信。
4. 查询设备基础信息和资源状态。
5. 查询当前脚本状态和停止标志。

不允许：

1. 直接修改 `dev_mqtt` 参数。
2. 直接触发 OTA。
3. 直接触发配置更新。
4. 直接写系统 NVS 参数。
5. 直接重启设备。

如后续需要允许脚本请求系统重启或配置刷新，必须设计为受控请求，由线程 1 决策。

## 14. 与线程 1 协同

线程 1 到脚本的事件：

| 事件 | 处理 |
| --- | --- |
| `CONFIG_UPDATING` | 脚本应停止写资源并准备退出 |
| `CONFIG_CHANGED` | 设备即将重启，脚本无需自行 reload |
| `OTA_UPDATING` | 脚本必须停止 |
| `TIME_SYNCED` | 更新时间状态，脚本可重新读取时间 |
| `REBOOTING` | 脚本应尽快退出 |
| `FACTORY_RESETTING` | 脚本应退出，用户数据将被清理 |

脚本到线程 1 的事件：

| 事件 | 说明 |
| --- | --- |
| `SCRIPT_RUNNING` | 脚本进入运行状态 |
| `SCRIPT_EXITED` | 脚本正常退出 |
| `SCRIPT_EXCEPTION` | 脚本异常 |
| `SCRIPT_STOP_TIMEOUT` | 脚本未在规定时间内停止 |

停止流程：

1. 线程 1 设置脚本停止请求。
2. runtime waker 唤醒 Python。
3. `runtime.should_stop()` 返回 true。
4. Python 框架取消或等待用户 task 退出。
5. 最长等待 5 秒。
6. 退出后清理脚本资源并上报结果。

## 15. 异常处理

脚本异常来源：

1. `main.py` 顶层异常。
2. `main()` 异常。
3. asyncio task 未捕获异常。
4. native module 返回致命错误。
5. PSRAM 分配失败。
6. C/Python 桥接对象生命周期错误。

异常上报内容：

| 字段 | 说明 |
| --- | --- |
| `script_name` | 固定 `main.py` |
| `exception` | 异常摘要 |
| `stack` | 堆栈摘要，超长截断 |
| `truncated` | 是否截断 |
| `uptime_ms` | 本次启动运行时间 |

异常策略：

| 策略 | 说明 |
| --- | --- |
| `restart_immediately` | 线程 1 收到异常后立即重启设备 |
| `restart_by_watchdog` | 默认策略，等待看门狗触发重启 |
| `ignore` | 不重启设备，仅上报异常 |

规则：

1. 脚本异常不得导致设备管理平面崩溃。
2. 用户 callback 异常必须被捕获并上报。
3. 公开 API 应尽量把 C 错误映射成 Python 可理解的异常。
4. Release 版本不得在异常堆栈中输出 MQTT 密码、token、NVS 加密材料等敏感信息。

## 16. 脚本资源清理

脚本退出或重启前必须清理：

1. 脚本 MQTT client。
2. WebSocket client。
3. HTTP 异步请求。
4. 外设订阅。
5. C/Python 消息队列。
6. waker 绑定。
7. Python callback 引用。
8. 临时 PSRAM buffer。

清理规则：

1. 先停止 C service 或取消订阅。
2. 再解绑 waker。
3. 再清空消息队列。
4. 最后释放 C 资源。
5. 已经进入 scheduler 的旧 waker 通过 generation 校验 no-op。

## 17. 看门狗和健康检查

建议检查项：

| 项目 | 策略 |
| --- | --- |
| `script_task` 栈高水位 | 低于 8 KB 上报 warn |
| Python heap 剩余 | 低于阈值上报脚本风险 |
| event loop 卡住 | 由脚本 watchdog 或心跳检测 |
| 消息队列溢出 | 增加 dropped/overflow 计数 |
| 脚本停止超时 | 上报 `SCRIPT_STOP_TIMEOUT` |

规则：

1. 看门狗不应由用户脚本直接控制。
2. Python 框架可周期性向 C runtime 喂脚本健康状态。
3. 用户业务长耗时操作必须 `await`，避免卡住 event loop。

## 18. 安全和权限

禁止脚本访问：

1. `dev_mqtt` 密码、handle 和订阅。
2. 设备管理 MQTT 出厂密码。
3. NVS 加密密钥和派生材料。
4. 系统 NVS 参数写接口。
5. `cfgfs:/` 配置区写接口。
6. `logfs:/` 日志区写接口。
7. ESP-IDF 私有 handle。

允许脚本访问：

1. `datafs:/` 用户数据。
2. 公开网络状态。
3. 公开设备状态。
4. 用户业务 MQTT。
5. 用户业务 HTTP。
6. 受控外设能力。

## 20. 测试建议

基础测试：

1. `script_task` 不等待出厂 MQTT 参数检查或 `dev_mqtt` 连接即可启动。
2. `main.py` 缺失时进入脚本错误状态。
3. 同步 `def main()` 能正常执行。
4. `async def main()` 接入 asyncio 包装层后再测试。
5. 顶层异常能上报 `SCRIPT_EXCEPTION`。

C/Python 桥接测试：

1. MQTT 回调不直接执行 Python。
2. MQTT payload 入队前已复制。
3. waker 重复触发不会重复制造消息。
4. 队列满后 dropped 计数增加。
5. destroy 后旧 waker generation 不匹配时 no-op。

资源测试：

1. 脚本 MQTT 断开不影响 `dev_mqtt`。
2. 脚本退出后 `script_mqtt` 自动销毁。
3. `datafs` 写满返回 `ENOSPC`。
4. PSRAM 分配失败进入脚本异常流程。
5. 脚本停止超过 5 秒，上报停止超时。

安全测试：

1. 用户脚本不能导入 `_mqtt`。
2. 用户脚本不能读取 `dev_mqtt` 密码。
3. 用户脚本不能访问 `cfgfs:/`。
4. 用户脚本不能访问 `logfs:/`。
5. 用户脚本不能通过修改 `sys.path` 导入非当前配置区文件。
6. 异常日志中敏感字段被脱敏。

## 21. 实现顺序

1. 完成 `script_task`、MicroPython VM heap 和 PSRAM 分配策略。
2. 完成 `main.py` 入口加载和异常捕获。
3. 完成公开 Python API 框架和禁止 `_xxx` 导入策略。
4. 完成 runtime 停止标志、waker、状态快照和消息队列模板。
5. 接入 `fs`，确保只访问 `datafs:/`。
6. 接入 `mqtt`，使用 `gw_mqtt_client` 和 `script_mqtt_adapter`。
7. 接入 `net`、`system`、`config` 只读状态。
8. 接入 `http`、`ws`、`board` 等能力。
9. 接入线程 1 的配置更新、OTA、恢复出厂停止流程。
10. 补充异常、队列满、PSRAM 不足和脚本停止超时测试。
