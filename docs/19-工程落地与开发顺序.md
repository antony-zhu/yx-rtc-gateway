## 2. 落地目标

工程落地按“先跑骨架，再接网络，再接协议，再接升级，再接脚本”的顺序推进。

目标：

1. 先把工程能稳定编译、启动、挂载分区、创建核心任务。
2. 先实现公共类型、事件队列、日志和状态快照，避免后续模块各写一套。
3. 先让 `dev_mgr_task` 能事件驱动运行，再接 4G、出厂 MQTT 参数读取、MQTT 和 HTTP。
4. 先完成设备管理闭环，再扩展脚本运行环境和脚本 API。
5. 每个阶段都有可验证输出，不依赖“一口气写完再调”。

非目标：

1. 不在第一阶段集成完整 MicroPython。
2. 不在 MQTT 连接前实现全部平台方法。
3. 不在配置 OTA 前实现复杂脚本业务能力。
4. 不提前做多脚本、多 MQTT client、多配置补丁、MQTT 分片等扩展。
5. 不为了临时调试破坏系统参数加密、路径隔离和 C/Python 边界。

## 3. 工程目录最终建议

建议目录：

```text
embedded/
  CMakeLists.txt
  partitions.csv
  sdkconfig.defaults
  main/
    CMakeLists.txt
    Kconfig.projbuild
    app_main.c
    include/
      gw_defaults.h
      gw_version.h
      gw_result.h
      gw_event.h
      gw_time.h
      gw_state.h
      gw_param.h
    board/
    common/
    storage/
    fs/
    time/
    log/
    supervisor/
    net/
    http/
    mqtt/
    protocol/
    gw/
    config/
    ota/
    py_runtime/
    mpy/
    script_api/
    drivers/
    ch37x/
    console/
  components/
  managed_components/
  third_party/
  disabled/
```

目录职责：

| 目录 | 职责 |
| --- | --- |
| `include/` | 跨模块公共头文件，只放稳定公共类型和接口 |
| `board/` | 板级初始化、MAC、芯片和模组基础信息 |
| `common/` | 通用工具、CRC、SHA-256、AES、字符串和安全脱敏 |
| `storage/` | NVS 系统参数、加密读写、主副本和出厂参数 |
| `fs/` | `cfgfs`、`datafs`、`logfs` 挂载和路径规范化 |
| `time/` | RTC、UTC 可信、授时和调度 |
| `log/` | 日志队列、写入、索引、查询、清理和上传 |
| `supervisor/` | 健康监控、看门狗、故障摘要、重启管理 |
| `net/` | 默认 4G、网络状态和重连 |
| `http/` | 通用 HTTP、下载和上传 |
| `mqtt/` | `gw_mqtt_client` 通用封装 |
| `protocol/` | MQTT 平台协议校验、分发和应答 |
| `gw/` | 设备管理主流程和业务编排 |
| `config/` | 配置包、manifest、双区更新 |
| `ota/` | OTA 下载、校验和 ESP-IDF OTA 调用 |
| `py_runtime/` | MicroPython VM 生命周期、C/Python 队列和 waker |
| `disabled/` | 已迁移但当前不加入编译的预留模块，例如 Python 框架层 cron |
| `mpy/` | MicroPython port 和 native module |
| `script_api/` | 固件内置 Python 包装层 |
| `drivers/`、`ch37x/` | 外设驱动和业务外设适配 |
| `console/` | 本地调试命令，发布版本默认关闭或受控开启 |

命名规范：

1. 项目自有 C 代码统一使用 `gw_` / `GW_` 前缀，包括通用基础能力和设备管理编排层。
2. 允许保留芯片、总线或外部协议对象自身的明确前缀，例如 `ch37x_`；这类前缀只用于对应驱动边界内。
3. 旧参考工程中的 `cat_` 前缀不得继续用于当前工程 C 模块；迁移旧代码时必须同步改名。
4. MQTT 基础封装固定命名为 `gw_mqtt_client`，设备管理 MQTT 业务层固定命名为 `gw_mqtt_manager`。

## 4. 公共头文件先行

公共头文件必须先定，避免后续模块互相包含私有头。

第一批必须落地：

| 头文件 | 内容 |
| --- | --- |
| `gw_defaults.h` | 固件默认值、固定限制、队列容量、栈大小、Payload 限制 |
| `gw_version.h` | 固件版本号，使用 3 字节 `major.minor.patch` |
| `gw_result.h` | `gw_result_t`、统一错误转换和 reason_code 常量 |
| `gw_event.h` | `GW_EVT_*`、事件包、事件优先级和 payload 所有权 |
| `gw_time.h` | `gw_time_point_t`、UTC 可信状态、uptime 接口 |
| `gw_state.h` | 主状态、网络状态、MQTT 状态、脚本状态和任务状态 |
| `gw_param.h` | 系统参数 key、参数来源、恢复出厂策略 |

第二批随模块落地：

| 头文件 | 内容 |
| --- | --- |
| `gw_storage.h` | NVS 加密读写、出厂参数、主副本接口 |
| `gw_fs.h` | LittleFS 挂载、分区信息、路径规范化 |
| `gw_log.h` | 日志投递、查询、诊断计数 |
| `gw_health.h` | 健康心跳、故障摘要、重启请求 |
| `gw_http.h` | HTTP 请求、下载、上传、取消、结果 |
| `gw_mqtt_client.h` | 通用 MQTT client 接口 |
| `gw_protocol.h` | MQTT 下行入口、应答、互斥任务、`request_id` |
| `gw_update.h` | 配置更新和 OTA 统一请求接口 |
| `py_runtime.h` | 脚本启动、停止、状态和 C/Python 事件接口 |

头文件要求：

1. 所有对外结构体、枚举、宏和函数必须有中文注释。
2. 公共头不得包含 ESP-IDF 私有业务 handle，除非该模块本身就是 ESP-IDF 适配层。
3. 公共头不得包含 Python `mp_obj_t`，Python 相关对象留在 `py_runtime` 或 `mpy` 私有头。
4. 模块私有状态机和内部结构体放在模块私有头或 `.c` 文件中。
5. 公共头之间避免循环包含，公共基础类型从 `gw_result.h`、`gw_event.h`、`gw_time.h` 单向依赖。

## 5. 默认值落点

默认值分三类落地：

| 类型 | 落点 | 示例 |
| --- | --- | --- |
| 固件固定限制 | `gw_defaults.h` | MQTT Payload 8192、日志行 4096、日志段 128 KB |
| 可配置参数默认值 | `gw_defaults.h` + NVS 参数表 | 心跳、MQTT 重连、HTTP 超时、日志容量 |
| 出厂参数 | 出厂 NVS 或默认生成 | `product_id=yx_gw`、`group_id=yx_gw`（当前联调阶段暂时使用）、`device_id=MAC_HEX` |

规则：

1. `16-设备参数与默认值清单.md` 是默认值来源，不允许代码里散落魔法数字。
2. 固定限制可作为宏或 `static const`。
3. 可配置参数启动时从 NVS 读取，无值时使用默认值。
4. 恢复出厂时按 `16` 的策略保留或清除。
5. 发布版本禁止通过日志输出敏感参数明文。

## 6. 构建配置

第一版工程配置建议：

| 项目 | 要求 |
| --- | --- |
| 分区表 | 工程构建使用 `embedded/partitions.csv`，协议文档同步保留 `02-ESP32S3R8N16_partitions.csv` |
| 文件系统 | `cfgfs`、`datafs`、`logfs` 均为 LittleFS |
| PSRAM | 必须启用，脚本 heap 和大缓冲使用 PSRAM |
| NVS | 系统参数使用加密封装读写 |
| MQTT | 使用 ESP-IDF MQTT，外层统一 `gw_mqtt_client` |
| HTTP | 使用 ESP-IDF HTTP client，外层统一 `gw_http_client` |
| JSON | 使用统一 JSON 库，不在各模块手写 JSON 字符串 |
| 日志 | 先接内部 `gw_log`，Release 版本限制敏感输出 |
| MicroPython | 后置集成，先保留 `script_task` 桩实现 |

`Kconfig.projbuild` 建议只放构建开关和调试开关，不放运行参数默认值的唯一来源。

当前实现记录：

1. CH37X 驱动已从参考工程迁移到 `embedded/main/ch37x/`，包含 `ch37x_host.c`、`ch37x_port.c`、`ch37x_port_spi.c` 和配套头文件。
2. CH37X 的 SPI 依赖已迁移为 `embedded/main/drivers/gw_spi_driver.*`，接口使用 `gw_spi_*` 命名。
3. 当前阶段已迁移并编译 CH37X 驱动能力，脚本侧可通过 `board.ch374_*` 兼容入口或独立 `ch37x`/`ch34x` 模块访问受控基础能力；固件不会自动启动 CH37X host 线程。
4. 通用 MQTT 封装已统一命名为 `gw_mqtt_client.*`；`gw_mqtt_manager`、脚本 MQTT adapter 和 `mod_mqtt` 均使用该封装。
5. 板级能力已接入 `gw_board.*`，当前覆盖 LED、RS485 和基础板级信息；脚本侧通过 `mod_board` 访问受控能力。
6. crypto 基础能力已接入 `gw_crypto.*` 和 `mod_crypto`，用于脚本侧 SHA-256、MD5、CRC32 等摘要能力。
7. 外部硬件看门狗已接入 `gw_hardware_watchdog.*`，默认启动独立喂狗任务。
8. 旧工程 cron 约定已迁移到 `embedded/disabled/cron/`，当前不加入编译、不安装到脚本环境。
9. YMZL/GS200 的 `embedded/main/script_api/ymzl.py` 仅保留为协议/硬件模块；应用层 `ymzl_app.py` 已移除，正式固件不再自动执行配置区脚本，dongle 业务将由 C 服务接管。
10. YMZL/GS200 硬件读取测试包位于 `tests/device-joint/package-sources/ymzl-hw-read/`；在 `ESP32S3R8N16` + CH37X 硬件上已验证 `ch37x` 可枚举到 `VID=0x1A86, PID=0x5523`，可持续读取 `55AA` 帧并解析为 `cmd=0x12`、`ext=cmd12`，低噪声版本默认仅周期记录状态和抽样帧。
11. 真设备远端配置包发布脚本已改为读取 `manifest.jsonl` 并上传其中描述的全部文件，避免只上传 `manifest.jsonl`、`config.json`、`main.py` 时导致扩展脚本文件 404。
12. OTA 管理器已接入 `ota.upgrade`，支持 accepted 后异步下载、版本递增校验、`scheduled_at` 等待、SHA-256 校验、ESP-IDF OTA 写入、进度上报和成功后受控重启。

## 7. 开发阶段

### P0 工程骨架

目标：工程能编译、能启动、能使用固定分区表。

实现内容：

1. 建立 `embedded/` 工程目录结构、`CMakeLists.txt`、`Kconfig.projbuild`。
2. 接入 `embedded/partitions.csv`。
3. 创建 `app_main.c`。
4. 创建第一批公共头文件空壳和最小实现。
5. 打通串口日志和启动 banner。
6. 输出固件版本 `major.minor.patch`。

验收标准：

1. 固件可编译。
2. 设备启动后能打印芯片型号、MAC、固件版本和分区表摘要。
3. 不创建业务任务，不连接网络。

### P1 基础公共能力

目标：公共类型、结果、事件、时间、日志和健康基础先可用。

实现内容：

1. `gw_result_t` 和 reason_code 常量。
2. `GW_EVT_*` 枚举和事件包。
3. `dev_mgr_event_queue` 基础封装。
4. 单调时间和 UTC 占位状态。
5. `gw_log_write()` 非阻塞投递，早期可先输出到串口。
6. `gw_health_report_heartbeat()` 基础心跳。

验收标准：

1. 可模拟投递 `GW_EVT_BOOT_READY`、`GW_EVT_NET_READY`、`GW_EVT_SCRIPT_EXCEPTION`。
2. 队列满时有返回值和计数。
3. 日志调用方不阻塞。
4. 所有公共头中文注释完整。

### P2 存储和文件系统

目标：NVS、LittleFS 三分区、路径隔离和默认参数可用。

实现内容：

1. 初始化 NVS。
2. 实现系统参数加密读写封装。
3. 读取或生成 `device_id`，默认等于 MAC 大写 hex。
4. 读取或生成 `product_id`，默认 `yx_gw`。
5. 挂载 `cfgfs`、`datafs`、`logfs`。
6. 实现 `datafs:/` 路径规范化，拒绝目录穿透。
7. 初步扫描 `cfgfs:/cfg_a`、`cfgfs:/cfg_b`。

验收标准：

1. 三个 LittleFS 分区挂载状态可查询。
2. `datafs:/a`、`datafs:/dir/../a` 能正确解析。
3. `/../../cfg_a/main.py` 被拒绝。
4. `datafs` 或 `logfs` 挂载失败不阻止后续主流程启动。
5. 恢复出厂保留 `device_id` 和 `product_id`。

### P3 任务骨架和状态快照

目标：两个核心任务并行，线程 1 不阻塞线程 2。

实现内容：

1. 创建 `dev_mgr_task`，栈 24 KB，内部 RAM。
2. 创建 `script_task` 桩任务，栈 64 KB，内部 RAM。
3. 创建 `log_task`，栈 8 KB，内部 RAM。
4. `dev_mgr_task` 使用事件驱动主循环。
5. 实现 `gw_state` 状态快照。
6. 实现心跳状态和基础属性构造。
7. `script_task` 桩不等待网络，启动后定期上报健康。

验收标准：

1. `dev_mgr_task`、`script_task`、`log_task` 都能独立运行。
2. 模拟网络失败不会阻塞 `script_task`。
3. 状态快照能输出 `status`、`network_status`、`mqtt_status`、`script_status`、`task_status`。
4. 栈高水位能被健康模块读取。

### P4 日志和诊断

目标：本地日志可持久化，写满保护不影响主流程。

实现内容：

1. `log_queue` 非阻塞队列，默认 64 条。
2. `logfs:/index.json` 初步维护。
3. `logfs:/log_*.jsonl` 段文件写入。
4. 单条日志 4096 字节截断。
5. 段文件 128 KB 切换。
6. 使用率超过 80% 后异步清理到 50%。
7. 日志诊断计数进入状态或属性。

验收标准：

1. 突发日志不会阻塞 `dev_mgr_task` 和 `script_task`。
2. `logfs` 写满后不会导致系统崩溃。
3. 清理动作由 `log_task` 执行，不在应用线程中扫描。
4. 日志查询可先支持最近 N 条。

### P5 网络和 HTTP 基础

目标：默认 4G 联网和 HTTP 通用请求可用。

实现内容：

1. 迁移旧工程验证过的 4G USB ECM 组件和启动流程。
2. 固定 4G USB VID `0x2ECC`、PID `0x3012`、AT interface `2` 和板级 4G GPIO。
3. 保持 public profile 为 `4g`，不把 ECM 暴露给平台或脚本。
4. 实现默认 4G 启动状态机，包含 GPIO 上电、USB Host、CDC、ECM、AT 查询、APN、ECM 数据模式和 IP 获取。
5. APN 默认空字符串。
6. 网络事件投递 `GW_EVT_NET_READY`、`GW_EVT_NET_LOST`、`GW_EVT_NET_FAILED`。
7. 实现 `gw_http_client`。
8. 实现连接超时 10 秒、应答间隔超时 3 秒。
9. 实现 HTTP 下载、上传和取消基础能力。
10. 实现出厂 MQTT 参数读取后的 `dev_mqtt` 连接前置检查。

验收标准：

1. 网络失败不阻塞脚本桩任务。
2. 4G USB ECM 能完成枚举、AT 检查、ECM 拨号并获取 IP。
3. USB 断开或 IP 获取失败能转换为网络事件并释放本轮资源。
4. 出厂 MQTT 连接信息完整时能直接连接 `dev_mqtt`。
5. MQTT 信息缺失时进入 `mqtt_status=not_configured`，不尝试 HTTP 注册。
6. HTTP URL 中敏感 query 不完整打印。

### P6 MQTT 基础封装

目标：`dev_mqtt` 和脚本 MQTT 共享 `gw_mqtt_client` 封装。

实现内容：

1. 实现 `gw_mqtt_client_create()`、`connect()`、`disconnect()`、`publish()`、`subscribe()`。
2. 实现 `GW_MQTT_CLIENT_EVENT_*` 到系统事件的转换。
3. 实现 `dev_mqtt` client。
4. 实现 MQTT 默认参数：QoS1、clean_session=1、retain=0、无 Last Will、无离线缓存。
5. Payload 最大 8192 字节。
6. 鉴权失败时保留出厂 MQTT 信息并进入 `auth_failed` 状态。

验收标准：

1. `dev_mqtt` 能连接，并且 `/yx_gw/YxzhNode${device_id}/thing/model/down_raw` 收到 Broker `SUBACK` 后才视为上线。
2. MQTT 回调只投递事件，不执行业务。
3. Payload 超限能拒绝并记录 reason_code。
4. `gw_mqtt_client` 支持后续脚本 MQTT 单独实例。
5. 如果 CONNECT 成功但订阅被 Broker 断开，应保留诊断日志并判定服务端 Topic/ACL 未满足协议要求，不自动切换旧 Topic。

### P7 协议处理和状态上报

目标：设备管理 MQTT 协议闭环。

实现内容：

1. Topic 校验 `/yx_gw/YxzhNode${device_id}/thing/model/down_raw`。
2. JSON 解析和通用字段校验。
3. 最近 32 个 `request_id` 去重。
4. 非查询类互斥任务。
5. `up_raw` 中的状态上报和属性上报。
6. `device.status.get`、`property.get`、`task.current.get`。
7. `property.set` 白名单参数写入。
8. 统一应答生成和错误映射。

验收标准：

1. 非法 Topic 被拒绝且不触发业务。
2. 重复 `request_id` 返回 `duplicate_request_id`。
3. 忙时非查询类方法返回 `device_busy`。
4. UTC 不可信时 `timestamp=0`。
5. 应答 Payload 不超过 8192 字节。

### P8 时间和调度

目标：UTC 可信、RTC 和定时任务可用。

实现内容：

1. 开机读取带电池 RTC。
2. 校验年份 2026 到 2046。
3. 校验不早于 `last_trusted_utc - 300000` 毫秒。
4. 网络授时入口。
5. `last_trusted_utc` 写入策略。
6. 基于 tick 的周期任务。
7. 基于可信 UTC 的定时 OTA 触发。

验收标准：

1. RTC 可信时开机直接 `time.utc_trusted=true`。
2. RTC 不可信时协议时间戳填 0。
3. 定时 OTA 在 UTC 不可信时等待，不提前执行。
4. `last_trusted_utc` 不高频写 NVS。

### P9 配置更新和 OTA

目标：配置整包更新和 OTA 能通过 MQTT 指令执行。

实现内容：

1. 配置 manifest 下载、SHA-256 校验和 JSONL 解析。
2. `manifest.jsonl`、`config.json`、`main.py` 三文件整体校验。
3. 配置写入非生效区，校验通过后切换 NVS。
4. 配置 `seq_id` 只允许递增。
5. OTA 目标固件版本只允许递增。
6. OTA 下载流直接写 ESP-IDF OTA 分区。
7. 配置和 OTA 进度上报。
8. 成功后进入受控重启。

验收标准：

1. `seq_id` 未递增时拒绝，不下载文件。
2. SHA-256 不匹配时保留旧配置或旧固件。
3. 配置三个核心文件缺任一文件都拒绝。
4. MQTT 触发 HTTP 操作用同一个 `request_id` 返回最终结果。
5. 成功前旧配置仍可用。

### P10 脚本运行环境

目标：MicroPython VM 和脚本 API 正式接入。

实现内容：

1. 集成 MicroPython port。
2. `script_task` 初始化 VM，任务栈 64 KB 内部 RAM。
3. Python VM heap、对象和大缓冲使用 PSRAM。
4. 固定执行当前生效配置区 `main.py`。
5. 实现 `runtime`、`system`、`fs`、`config` 基础 API。
6. 实现 C/Python 队列、waker 和 generation 校验。
7. 实现脚本停止流程，最长等待 5 秒。

验收标准：

1. 脚本不等待联网即可运行。
2. 脚本只能访问 `datafs:/`。
3. 脚本不能导入内部 `_xxx` 模块。
4. 非 `script_task` 上下文不能进入 VM。
5. 脚本异常能上报并按策略处理。

### P11 脚本网络能力

目标：脚本 MQTT、HTTP、WS 和外设事件按统一桥接规则进入 Python。

实现内容：

1. 脚本 MQTT 使用 `gw_mqtt_client` 独立 client，当前最多 4 个。
2. 脚本 MQTT 事件进入 C 队列，Python 用 `recv()` / `poll()` 获取，或由 `mqtt.on()` 在 VM 上下文分发 callback。
3. 脚本 HTTP 只服务用户业务。
4. 脚本大响应和大缓冲使用 PSRAM。
5. 外设输入先入 C 队列，再由 Python 消费。
6. 用户 callback 异常捕获并上报。

验收标准：

1. 脚本 MQTT 不影响 `dev_mqtt`。
2. 脚本不能获得或复用 `dev_mqtt` 的凭据、handle 和连接；脚本 MQTT 不额外按 Topic 字符串封禁系统 Topic，隔离依赖独立凭据和 Broker ACL。
3. MQTT DATA 分片由 C 层组包后再给 Python。
4. 队列满有 dropped/overflow 计数。

### P12 集成压测和发布收口

目标：把异常、资源、日志、恢复和安全策略收口。

实现内容：

1. 网络断开、MQTT 信息缺失、MQTT 鉴权失败压测。
2. 日志突发、`logfs` 写满、`datafs` 写满压测。
3. 配置更新断电点测试。
4. OTA 失败和成功重启测试。
5. 脚本异常重启风暴测试。
6. 栈高水位和 heap/PSRAM 低水位测试。
7. Release 日志敏感信息扫描。

验收标准：

1. `datafs`、`logfs` 故障不影响联网、MQTT、配置和 OTA。
2. `dev_mgr_task` 卡死能触发受控重启或看门狗兜底。
3. Release 版本不输出密码、token、密钥和完整敏感 URL。
4. 所有 MQTT 方法有成功、失败、超时、忙、重复请求测试。

## 8. 最小可运行版本

第一版最小可运行版本建议定义为：

1. 固定分区表生效。
2. NVS 可读写，`device_id`、`product_id` 可生成或读取。
3. `cfgfs`、`datafs`、`logfs` 可挂载。
4. `dev_mgr_task`、`script_task`、`log_task` 可并行启动。
5. `script_task` 不等待网络。
6. 日志可写入 `logfs:/`，写满不崩溃。
7. 默认 4G 联网可启动。
8. 出厂 MQTT 信息可读取并用于连接 `dev_mqtt`。
9. `dev_mqtt` 可连接并订阅平台 Topic。
10. 可通过 `up_raw` 上报 `status.report` 并响应 `device.status.get`。

这版不要求：

1. 不要求完整配置更新。
2. 不要求完整 OTA。
3. 不要求 MicroPython 正式运行用户脚本。
4. 不要求脚本 MQTT 和脚本 HTTP。

## 9. 测试组织

测试按层级组织：

| 层级 | 测试内容 |
| --- | --- |
| 单元测试 | JSON 校验、路径规范化、request_id 去重、版本比较、SHA-256 |
| 模块测试 | NVS、LittleFS、日志队列、HTTP 超时、MQTT Payload 限制 |
| 任务测试 | `dev_mgr_task` 事件驱动、脚本桩并行、log_task 清理 |
| 协议测试 | Topic、方法、应答、状态、属性、错误码 |
| 故障测试 | 断网、写满、鉴权失败、HTTP 超时、配置校验失败、脚本异常 |
| 长稳测试 | 24 小时联网、日志写入、心跳、重连、heap 和栈水位 |

必须优先自动化的用例：

1. 路径穿透拒绝。
2. `request_id` 32 条缓存和 1 小时清理。
3. Payload 超过 8192 字节拒绝。
4. 配置 `seq_id` 不递增拒绝。
5. OTA 版本不递增拒绝。
6. UTC 不可信时 `timestamp=0`。
7. 日志查询超过 8192 字节且无 `upload_url` 返回 413。
8. 队列满不阻塞调用方。

PC 侧 MQTT 测试工具：

1. `tools/dev_mqtt_cli.py config-package` 用于生成普通配置包目录和 `manifest.jsonl`。
2. `tools/dev_mqtt_cli.py script-api-smoke-package` 用于生成脚本 API 烟测配置包，默认包含 `config.json` 和 `main.py`。
3. `tools/dev_mqtt_cli.py config-update` 用于按正式 `config.update` 协议下发配置更新。
4. 配置包的 `base_url` 必须是设备 4G 网络可访问的 HTTP/HTTPS 地址；本机 `localhost` 或仅 PC 可访问的内网地址不能用于真实设备下载。
5. 工具只负责生成包和发送 MQTT 指令，不绕过固件配置更新状态机。

## 10. 调试和发布开关

建议保留以下调试开关：

| 开关 | 默认 | 说明 |
| --- | --- | --- |
| `GW_DEBUG_CONSOLE` | 关闭 | 本地 console |
| `GW_DEBUG_MQTT_TRACE` | 关闭 | MQTT 详细收发日志 |
| `GW_DEBUG_HTTP_TRACE` | 关闭 | HTTP 详细日志 |
| `GW_DEBUG_SCRIPT_TRACE` | 关闭 | 脚本 runtime 详细日志 |
| `GW_FAULT_INJECT` | 关闭 | 故障注入测试 |

发布规则：

1. Release 版本默认关闭详细 trace。
2. Release 版本禁止打印 MQTT 密码、设备管理 MQTT 出厂密码、URL token、NVS 加密材料。
3. 如平台临时开启详细日志，应有持续时间或重启后失效策略。
4. 故障注入开关不得进入正式发布默认启用状态。

## 11. 不应提前实现的内容

当前版本不做：

1. 多个用户脚本并行运行。
2. 多个脚本 MQTT client。
3. MQTT 离线缓存。
4. MQTT 分片传输日志。
5. 配置单文件补丁更新。
6. 配置或 OTA 回滚到低版本。
7. 脚本直接控制设备管理 OTA、配置更新或重启。
8. 脚本访问系统 NVS 或 `dev_mqtt` 凭据。
9. 平台感知日志内部段文件。
10. 复杂的日志写前扫描或每条日志容量扫描。
