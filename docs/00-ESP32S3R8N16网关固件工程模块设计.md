## 2. 总体分层

固件按“系统基础层、设备管理平面、脚本运行平面”三层组织。

```text
app_main
  |
  v
系统基础层
  board / storage / fs / time / net / http / log
  |
  v
设备管理平面
  dev_mgr / mqtt / protocol / config / ota
  |
  v
脚本运行平面
  script_runtime / script_api / datafs
```

依赖原则：

1. 下层模块不得依赖上层业务模块。
2. 设备管理平面可以调用系统基础层，但不得直接进入 Python VM。
3. 脚本运行平面只能通过受控 `script_api` 访问网络、文件、状态和设备能力。
4. `datafs` 和 `logfs` 是非核心能力，异常不得影响 MQTT、OTA、配置更新和状态上报。
5. 模块间长耗时操作必须通过任务、队列或状态机异步执行，不得在 MQTT 回调或脚本调用栈中阻塞。

## 3. 建议目录结构

后续固件工程建议按以下目录落地：

```text
main/
  app_main.c
  board/
  drivers/
  ch37x/
  common/
  console/
  storage/
  fs/
  time/
  net/
  http/
  mqtt/
  gw/
  protocol/
  config/
  ota/
  log/
  mpy/
  py_runtime/
  script_api/
  ws/
  ymzl/
  supervisor/
```

目录可以按 ESP-IDF component 进一步拆分，但当前工程内部 C 模块统一使用 `gw_` / `GW_` 前缀，不再沿用参考工程中的 `cat_` 命名。芯片或外部协议驱动可以保留明确的对象前缀，例如 `ch37x_`；ESP-IDF、MicroPython 和第三方库保留原始命名。

命名约定：

1. 项目自有 C 接口、结构体、枚举、宏统一使用 `gw_` / `GW_`。
2. 通用 MQTT client 封装命名为 `gw_mqtt_client`；设备管理业务层命名为 `gw_mqtt_manager`。
3. CH37X 是芯片驱动层，公共接口保留 `ch37x_`，其 SPI 适配依赖项目统一的 `gw_spi_driver`。
4. 新增模块不得再引入 `cat_` 前缀；如从参考工程迁移代码，必须在迁移时完成命名整理。

与参考工程目录的建议映射：

| 参考目录 | 建议归属 | 说明 |
| --- | --- | --- |
| `board/` | 启动与硬件抽象 | 板级初始化、GPIO、电源和硬件识别 |
| `drivers/`、`ch37x/` | 外设驱动层 | SPI、USB Host、外设芯片驱动；只暴露驱动能力，不承载业务协议 |
| `common/`、`utils/` | 基础公共能力 | 看门狗、运行统计、通用加解密、通用工具函数 |
| `storage/`、`fs/` | 存储与文件系统 | NVS 加密、LittleFS 挂载、路径隔离、文件存储 |
| `net/`、`http/`、`mqtt/`、`ota/` | 通信基础能力 | 提供通用网络、HTTP、MQTT、OTA 原语 |
| `gw/` | 设备管理编排层 | 组合 MQTT、协议、配置、状态、脚本和 OTA 流程 |
| `mpy/`、`py_runtime/` | 脚本运行层 | MicroPython 移植、VM、脚本任务、脚本模块绑定 |
| `ws/` | 可选通信能力 | WebSocket 基础能力，只有被脚本或业务明确使用时启用 |
| `ymzl/` | 业务协议适配 | 业务外设或透传协议解析，不应反向依赖设备管理协议 |
| `console/` | 本地调试能力 | 调试命令和诊断输出，发布版本默认关闭或受控开启 |

## 4. 模块细化

### 4.1 启动与硬件抽象模块

建议目录：`board/`、`drivers/`、`ch37x/`、`common/`

健康监控、看门狗、故障摘要和重启保护见：`15-模块设计-健康监控与异常恢复.md`。

职责：

1. 初始化板级硬件、GPIO、电源控制、4G 模组控制、外设基础状态。
2. 初始化内部看门狗和外部硬件看门狗。
3. 提供 MAC、芯片型号、PSRAM/Flash 基础信息查询。
4. 提供统一重启原因、启动次数、崩溃原因记录接口。
5. 管理 SPI、USB Host、外设芯片等驱动初始化顺序。

不负责：

1. 不保存业务配置。
2. 不解析 MQTT 协议。
3. 不直接启动 Python 脚本业务。
4. 不在底层驱动里直接拼接平台 MQTT 报文。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `board_init()` | 初始化板级硬件 |
| `board_get_mac()` | 获取硬件 MAC |
| `watchdog_start()` | 启动看门狗 |
| `watchdog_feed(source)` | 按来源喂狗 |
| `runtime_stats_record_fault(task, reason)` | 记录故障任务和原因 |

异常策略：

1. 硬件初始化失败时，进入受限运行或重启。
2. 看门狗任务自身异常属于系统级故障。
3. 记录故障信息时不得依赖 `logfs` 必须可写，应优先写入 NVS 中的最小故障摘要。

### 4.2 存储与文件系统模块

建议目录：`storage/`、`fs/`

细化设计见：`06-模块设计-存储与文件系统.md`。

职责：

1. 初始化 NVS、NVS 系统参数加密和三块 LittleFS 分区。
2. 管理 `cfgfs`、`datafs`、`logfs` 的挂载、路径解析和容量查询。
3. 提供配置双区、用户数据区、日志区的路径隔离能力。
4. 提供 NVS 主副副本、CRC 校验、加密读写接口。
5. 提供分区级状态给属性上报模块。

固定分区：

| 分区 | 用途 |
| --- | --- |
| `cfgfs` | 配置双区、`manifest.jsonl`、`config.json`、`main.py` |
| `datafs` | 用户脚本数据区，直接使用分区根目录 |
| `logfs` | 运行日志区，直接使用分区根目录 |

路径规则：

1. 文档和内部诊断统一使用 `cfgfs:/...`、`datafs:/...`、`logfs:/...` 表示分区路径。
2. 脚本访问 `/a` 时映射为 `datafs:/a`。
3. 路径可以出现 `../`，但规范化后的最终路径不得逃出所属分区。
4. `datafs` 写满时不自动删除用户文件；挂载失败恢复按文件系统策略执行。
5. `logfs` 可以自动删除旧日志。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `storage_init()` | 初始化 NVS 和加密存储 |
| `fs_mount_all()` | 挂载 `cfgfs`、`datafs`、`logfs` |
| `fs_get_info(partition)` | 查询分区容量和使用情况 |
| `nvs_secure_get/set(namespace, key)` | 加密读写 NVS 系统参数 |
| `fs_resolve_script_path(path)` | 脚本路径映射到 `datafs` |

异常策略：

1. `cfgfs` 失败会影响配置和脚本，应进入受限运行并等待配置修复。
2. `datafs` 失败只影响脚本文件读写，不影响设备管理平面。
3. `logfs` 失败只影响本地日志持久化，不影响设备管理平面。
4. 不允许因为 `datafs` 或 `logfs` 写满导致系统崩溃。

### 4.3 网络模块

建议目录：`net/`

网络与 HTTP 细化设计见：`14-模块设计-网络与HTTP.md`。

职责：

1. 按配置启动联网方式，当前默认 4G。
2. 管理 4G APN、网络注册、IP 获取、断线检测和重连。
3. 提供网络状态、IP、4G 信号、SIM 状态等属性。
4. 提供网络可用事件给 MQTT、时间同步和 OTA。

不负责：

1. 不保存 MQTT 账号密码。
2. 不解析平台协议。
3. 不替脚本缓存离线数据。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `net_start(profile)` | 启动指定网络 |
| `net_stop()` | 停止网络 |
| `net_get_status()` | 查询网络状态 |
| `net_wait_ready(timeout)` | 等待网络可用 |

默认策略：

1. 默认联网方式为 4G。
2. APN 默认空字符串，表示使用模组或运营商默认 APN。
3. 网络失败按退避重试。
4. 网络模块不得阻塞 `script_task` 启动和运行。

### 4.4 出厂 MQTT 参数

写入规则见：`03-出厂MQTT连接信息写入说明.md`。
NVS 加密存储见：`06-模块设计-存储与文件系统.md`。

职责：

1. 出厂/产测流程写入 `product_id`、`group_id`、`device_id` 和 MQTT 连接信息。
2. 固件启动后只从 NVS 读取 `host`、`port`、`username`、`password`、`client_id`。
3. 固件根据本地参数创建 `dev_mqtt`，不通过 HTTP 注册接口自动获取账号密码。
4. 缺少或损坏 MQTT 信息时进入 `mqtt_status=not_configured`。

不负责：

1. 不在固件中实现 HTTP 注册。
2. 不在 MQTT 鉴权失败后自动清除 MQTT 信息。
3. 不通过 MQTT 应答出厂写入失败，因为写入发生在固件运行流程之外。

异常策略：

1. MQTT 信息缺失或解密失败时保持 `status=offline`，`mqtt_status=not_configured`。
2. MQTT 鉴权失败时保持本地 MQTT 信息，等待维护工具重新写入或后台修正账号。
3. 恢复出厂可以清除 MQTT 信息；清除后必须重新出厂写入才能上线。

### 4.5 MQTT 管理模块

建议目录：`mqtt/`

通用 MQTT 基础封装细化设计见：`07-模块设计-MQTT基础封装.md`。

职责：

1. 封装通用 MQTT client 能力，包括连接、断开、订阅、发布、事件、重连和状态查询。
2. 支持 `dev_mqtt` 和脚本 MQTT 复用同一套底层封装。
3. 维护设备管理 MQTT 连接，以下简称 `dev_mqtt`。
4. 订阅 `/yx_gw/YxzhNode${device_id}/thing/model/down_raw` 下行主题。
5. 发布属性、状态、配置结果、服务应答、OTA 进度、日志和脚本异常。
6. 管理 MQTT 重连、QoS、clean session、retain、Last Will 配置。
7. 限制单条 MQTT Payload 最大 8192 字节。

不负责：

1. 不直接处理业务命令。
2. 不执行 HTTP 下载/上传。
3. 不缓存离线 MQTT 上报。
4. 不向脚本暴露 `dev_mqtt` 凭据和句柄。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `gw_mqtt_client_create(config, cb, ctx)` | 创建通用 MQTT client |
| `gw_mqtt_client_connect(handle)` | 连接 Broker |
| `gw_mqtt_client_publish(handle, topic, payload, qos, retain)` | 发布消息 |
| `gw_mqtt_client_subscribe(handle, topic, qos)` | 订阅主题 |
| `gw_mqtt_client_get_status(handle)` | 查询连接状态 |
| `gw_mqtt_start_dev_client()` | 基于 `gw_mqtt_client` 启动 `dev_mqtt` |
| `script_mqtt_connect(config)` | 脚本侧基于 `gw_mqtt_client` 创建 MQTT 连接 |

默认参数：

| 参数 | 默认值 |
| --- | --- |
| QoS | 1 |
| Clean Session | 1 |
| Retain | 0 |
| Last Will | 不启用 |
| 离线缓存 | 不启用 |
| 单条 Payload | 8192 字节 |

### 4.6 设备协议模块

建议目录：`protocol/`、`gw/`

设备管理主流程细化设计见：`09-模块设计-设备管理主流程.md`。
MQTT 协议处理细化设计见：`08-模块设计-MQTT协议处理.md`。

职责：

1. 校验 MQTT 下行 Topic、JSON 格式、`version`、`method`、`request_id`。
2. 维护最近 32 个平台下发 `request_id` 去重记录。
3. 将平台方法分发给配置、OTA、日志、属性、状态、脚本异常策略等模块。
4. 统一生成 MQTT 应答和错误码。
5. 处理 MQTT 触发 HTTP 操作的最终应答码、HTTP 状态码和失败原因。
6. 维护设备状态机和属性上报所需的统一数据视图。

不负责：

1. 不直接写 Flash 大文件。
2. 不直接执行 Python 代码。
3. 不在 MQTT 回调里执行长耗时任务。

并发规则：

1. 同一时间只允许一个非查询类任务运行。
2. 查询类指令允许并行，包括状态查询、属性查询、日志查询和 Schema 查询。
3. 非查询类任务冲突时，应答 `device_busy`。
4. 重复 `request_id` 不重新执行，直接应答重复请求。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `protocol_handle_down(topic, payload)` | 下行统一入口 |
| `protocol_reply(request_id, code, message, data)` | 通用应答 |
| `protocol_task_begin(request_id, method)` | 互斥任务占用 |
| `protocol_task_end(request_id, result)` | 互斥任务结束 |

### 4.7 配置管理模块

建议目录：`config/`

配置与 OTA 细化设计见：`11-模块设计-配置与OTA.md`。

职责：

1. 管理 `cfgfs:/cfg_a` 和 `cfgfs:/cfg_b` 配置双区。
2. 下载并校验 `manifest.jsonl`。
3. 按 `manifest.jsonl` 下载 `config.json`、`main.py` 和其他配置文件。
4. 校验文件大小、SHA-256、`seq_id`、`min_product_version`。
5. 在校验全部通过后切换 NVS 中的当前生效区。

固定规则：

1. 配置包固定以 `manifest.jsonl`、`config.json`、`main.py` 为整体。
2. 不做单文件局部更新。
3. `seq_id` 只允许递增。
4. 两个配置区都有效且 `seq_id` 相同，默认选择 `cfgfs:/cfg_a`。
5. 两个配置区都无效，视为无本地配置，等待整包配置更新。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `config_scan_slots()` | 扫描双区有效性 |
| `config_get_active_slot()` | 获取当前生效区 |
| `config_update_package(manifest_url, request_id)` | 整包配置更新 |
| `config_validate_manifest(slot)` | 校验描述文件和包内文件 |
| `config_switch_active(slot)` | 切换生效区 |

异常策略：

1. 下载或校验失败时保留旧配置。
2. 切换失败时不上电新配置。
3. 配置更新成功后重启设备。

### 4.8 脚本运行模块

建议目录：`py_runtime/`、`mpy/`、`script_api/`

C/Python 交互和脚本事件桥接规则见：`05-模块设计-C与Python交互规则.md`。
脚本运行环境细化设计见：`10-模块设计-脚本运行环境.md`。

职责：

1. 创建并维护 `script_task`。
2. 初始化 Python VM。
3. 固定运行当前生效配置区中的 `main.py`。
4. 管理脚本异常、退出、停止、重启和状态上报。
5. 提供脚本侧受控 API，包括文件、网络状态、MQTT 透传和设备状态查询。
6. 管理 MicroPython 模块绑定，例如 `mod_fs`、`mod_net`、`mod_http`、`mod_mqtt`、`mod_system`。

任务和内存：

| 项目 | 要求 |
| --- | --- |
| `script_task` 栈 | 64 KB，内部 RAM |
| Python VM heap | PSRAM |
| Python 对象和大缓冲 | PSRAM |
| PSRAM 分配失败 | 脚本异常或分配失败，不回退内部 RAM |

脚本文件规则：

1. 入口固定为 `main.py`。
2. 脚本只能访问 `datafs:/`。
3. 脚本访问 `/a` 时映射为 `datafs:/a`。
4. 路径规范化后不得逃出 `datafs:/`。
5. `datafs` 写满时，脚本写操作失败，不删除用户文件。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `script_start()` | 启动脚本 |
| `script_stop(timeout_ms)` | 请求停止脚本 |
| `script_restart(reason)` | 重启脚本 |
| `script_get_status()` | 查询脚本状态 |
| `script_report_exception(summary, stack)` | 上报脚本异常 |

脚本 API 边界：

1. 脚本 API 只能暴露经过封装的能力，不允许直接调用 NVS 系统参数接口。
2. 脚本侧文件 API 统一映射到 `datafs:/`。
3. 脚本侧网络、HTTP、MQTT API 应有独立超时和错误返回，不得阻塞设备管理平面。
4. 脚本侧 MQTT 必须通过 `gw_mqtt_client` 通用封装层，不允许直接调用 ESP-IDF MQTT。
5. 脚本侧接口不得返回 `dev_mqtt` 密码、NVS 加密材料等系统敏感信息。

### 4.9 日志模块

建议目录：`log/`

日志与诊断细化设计见：`12-模块设计-日志与诊断.md`。

职责：

1. 创建低优先级 `log_task`。
2. 接收系统日志、脚本异常日志和 MQTT 详细日志。
3. 将日志写入 `logfs:/log_*.jsonl`。
4. 维护 `logfs:/index.json`。
5. 按容量、使用率和时间保留策略删除旧日志。
6. 支持 `log.query` 查询和 HTTP POST 上传。

固定规则：

1. `log_task` 栈 8 KB，内部 RAM。
2. 线程 1 和线程 2 只投递日志，不直接写 Flash。
3. 日志队列满时允许丢弃低优先级日志并计数。
4. `logfs` 使用率超过 80% 或写入空间不足时触发清理。
5. 清理目标是 `logfs` 使用率不高于 50%。
6. 清理失败时暂停持久化日志，不影响其他模块。
7. 日志 MQTT 直传完整 Payload 最大 8192 字节，超过必须 HTTP POST。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `log_init()` | 初始化日志队列和任务 |
| `log_write(level, module, msg)` | 非阻塞投递日志 |
| `log_query(filter, upload_url)` | 查询日志 |
| `log_clean_async(reason)` | 请求后台清理 |
| `log_get_status()` | 查询日志状态和丢弃计数 |

### 4.10 OTA 与时间模块

建议目录：`ota/`、`time/`

配置与 OTA 细化设计见：`11-模块设计-配置与OTA.md`。
时间与调度细化设计见：`13-模块设计-时间与调度.md`。

OTA 职责：

1. 接收平台 OTA 指令。
2. 校验目标版本必须高于当前版本。
3. 执行 HTTP/HTTPS 下载、大小校验、SHA-256 校验。
4. 写入 ESP-IDF OTA 分区。
5. 上报进度和最终结果。
6. 成功后重启设备。

OTA 固定规则：

1. OTA 过程中必须停止脚本。
2. 不允许平台下发版本回滚。
3. ESP-IDF 启动失败回退只作为启动失败恢复机制。
4. `scheduled_at` 按 UTC 解释，只有 UTC 可信时才执行定时 OTA。
5. 立即执行类 OTA 指令不受 UTC 可信限制。

时间职责：

1. 管理系统 UTC、RTC、NTP/SNTP、MQTT 授时、4G 网络时间和 HTTPS 时间校验。
2. 判断 UTC 是否可信。
3. 更新 RTC 和 `last_trusted_utc`。
4. 为日志、状态、属性和 OTA 调度提供时间状态。

UTC 可信规则：

1. 年份必须在 2026 到 2046 年之间。
2. RTC 可作为可信来源，但必须不早于 `last_trusted_utc - 300000` 毫秒。
3. `last_trusted_utc` 长期保存在加密 NVS，不设置过期时间。
4. 首次可信 UTC 立即写入；之后默认当前可信 UTC 比 NVS 值大超过 24 小时才写入。
5. OTA、配置切换或正常重启前，如 UTC 可信，应写入一次。
6. 没有可信 UTC 时，协议时间戳填 `0`，定时 OTA 和定时配置更新等待授时。

关键接口建议：

| 接口 | 说明 |
| --- | --- |
| `ota_start(request)` | 启动 OTA |
| `ota_get_status()` | 查询 OTA 状态 |
| `time_init()` | 初始化 RTC 和时间状态 |
| `time_is_trusted()` | 查询 UTC 是否可信 |
| `time_update(source, utc_ms)` | 使用可信来源更新时间 |
| `time_get_status()` | 查询时间来源和 `last_trusted_utc` |

### 4.11 本地调试与控制台模块

建议目录：`console/`

职责：

1. 提供本地串口调试命令。
2. 查看基础状态、分区状态、任务状态、时间状态和最近故障。
3. 支持有限的本地维护操作，例如重启、打印状态、触发日志清理。

固定规则：

1. 发布版本默认关闭高风险写命令。
2. 控制台不得打印 MQTT 密码、NVS 加密密钥和用户脚本敏感数据。
3. 控制台输出只作为本地诊断能力，不作为平台协议的一部分。
4. 控制台异常不得影响设备管理和脚本运行。

### 4.12 业务外设与透传协议模块

建议目录：`ymzl/`、业务协议独立目录

职责：

1. 解析和封装业务外设协议。
2. 对接外设驱动层，例如 SPI、USB Host 或其他总线。
3. 向脚本运行层或设备协议层提供清晰的业务数据接口。
4. 支持原始十六进制透传类数据的输入输出。

边界：

1. 业务协议模块不得直接持有 MQTT 连接。
2. 业务协议模块不得直接访问出厂 MQTT 连接信息。
3. 业务协议异常只影响对应业务功能，不应导致设备管理平面重启。
4. 如需要通过 MQTT 上报，应通过协议模块或脚本 API 转发。

### 4.13 可选通信扩展模块

建议目录：`ws/`

职责：

1. 提供 WebSocket 客户端基础能力。
2. 作为脚本 API 或特定业务模块的可选通信通道。

固定规则：

1. 默认不参与设备注册、配置更新和 OTA。
2. 只有配置或脚本明确启用时才启动。
3. WebSocket 连接失败不得影响 `dev_mqtt`。

## 5. 核心任务模型

固定核心任务：

| 任务 | 栈大小 | 内存来源 | 是否核心 | 说明 |
| --- | ---: | --- | --- | --- |
| `dev_mgr_task` | 24 KB | 内部 RAM | 是 | 设备管理主流程 |
| `script_task` | 64 KB | 内部 RAM | 是 | Python 脚本运行 |
| `log_task` | 8 KB | 内部 RAM | 否 | 日志写入和清理 |

允许的辅助任务：

| 任务 | 归属 | 说明 |
| --- | --- | --- |
| `net_worker` | 线程 1 管理平面 | 网络连接和重连 |
| `mqtt_worker` | 线程 1 管理平面 | MQTT 连接和事件接收 |
| `http_worker` | 线程 1 管理平面 | MQTT 触发的 HTTP 下载/上传 |
| `ota_worker` | 线程 1 管理平面 | OTA 下载和写入 |
| `time_worker` | 线程 1 管理平面 | 授时和 RTC 同步 |

任务约束：

1. 所有任务栈使用内部 RAM。
2. 脚本应用堆和大缓冲使用 PSRAM。
3. `log_task` 不属于核心任务，异常时降级日志能力。
4. 辅助任务不能阻塞 `script_task`。
5. MQTT 回调不能直接执行长耗时任务，应投递到对应 worker。

## 8. 异常隔离矩阵

| 模块异常 | 影响范围 | 不得影响 |
| --- | --- | --- |
| `cfgfs` 损坏 | 配置和脚本启动 | MQTT、状态上报、配置修复 |
| `datafs` 写满 | 脚本文件写入 | 线程 1、MQTT、OTA、配置更新 |
| `logfs` 写满 | 本地持久化日志 | 线程 1、线程 2、MQTT |
| 网络断开 | MQTT、OTA、远程配置 | 本地脚本运行 |
| MQTT 断开 | 平台指令和上报 | 本地脚本运行、网络重连 |
| HTTP 下载失败 | 当前配置/OTA/日志上传任务 | 旧配置、当前固件、脚本运行 |
| Python 异常 | 脚本业务 | 设备管理平面 |
| 脚本异常重启风暴 | 脚本自动运行 | 设备管理平面、联网、MQTT、配置修复 |
| PSRAM 不足 | 脚本运行 | 内部 RAM、设备管理平面 |
| 健康监控发现非核心任务异常 | 对应非核心能力 | 线程 1、线程 2、MQTT |
| UTC 不可信 | 定时 OTA/定时配置 | 立即执行指令、MQTT |

## 9. 建议实现顺序

1. 启动、NVS 加密、三分区挂载、基础状态上报。
2. 健康监控、故障摘要、核心任务心跳和受控重启。
3. `log_task`、非阻塞日志队列、`logfs` 后台清理。
4. 网络、HTTP 通用封装、MQTT 管理连接。
5. 协议分发、`request_id` 去重、状态/属性上报。
6. 配置双区、`manifest.jsonl` 整包更新。
7. Python 运行时、PSRAM heap、`datafs` 文件隔离。
8. OTA、UTC/RTC 可信策略、定时 OTA。
9. 远程日志查询、HTTP POST 上传、诊断状态补齐。
