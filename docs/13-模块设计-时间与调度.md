## 2. 设计目标

1. 设备统一使用 UTC 作为协议时间和平台调度时间。
2. 设备同时维护单调运行时间和 UTC 时间，二者用途必须区分。
3. RTC 带电池，且本次启动未检测到 RTC 故障锁时，校验通过后可作为可信 UTC 来源。
4. 没有可信 UTC 时，设备仍可联网、注册、连接 MQTT、运行脚本和执行立即类指令。
5. 没有可信 UTC 时，协议 `timestamp` 填 0。
6. 所有依赖日历时间的定时任务必须等待 UTC 可信；RTC 缺失或启动校验异常时，只能由网络授时解除执行锁。
7. `last_trusted_utc` 长期保存在加密 NVS，不设置过期时间。
8. 时间同步失败不得阻塞 `script_task`。
9. 时间倒退、RTC 缺失、RTC 掉压/停钟和授时失败必须可诊断并锁存，不能由 BLE 手机时间掩盖。
10. 定时器回调只投递事件，不执行长耗时操作。

## 4. 时间模型

固件使用两类时间：

| 时间 | 来源 | 用途 |
| --- | --- | --- |
| 单调运行时间 | 系统 tick 或高精度计数器 | 超时、重试、周期定时器、运行时长、看门狗 |
| UTC 时间 | RTC、4G、MQTT、HTTPS、SNTP | 协议 `timestamp`、日志 `ts`、定时 OTA、时间属性 |

固定规则：

1. 超时和重试必须使用单调运行时间，不依赖 UTC。
2. MQTT 心跳、HTTP 连接超时、HTTP 应答间隔超时、MQTT 重连等周期任务使用单调运行时间。
3. `scheduled_at` 等平台绝对时间使用可信 UTC。
4. UTC 不可信时，绝对时间任务不得执行，只进入等待状态。
5. UTC 不可信不影响相对超时和重试。

协议时间单位：

| 字段 | 单位 | 说明 |
| --- | --- | --- |
| `timestamp` | 毫秒 Unix 时间戳 | UTC 不可信时填 0 |
| `scheduled_at` | 毫秒 Unix 时间戳 | 按 UTC 解释 |
| `last_trusted_utc` | 毫秒 Unix 时间戳 | 长期保存在 NVS |
| `uptime_ms` | 毫秒 | 单调运行时间，不是 UTC |

## 5. 时间来源

候选时间来源和权限：

| 来源 | 说明 |
| --- | --- |
| RTC | 带电池 RTC；仅在开机校验全部通过且 `recovery_required=false` 时可直接建立可信 UTC |
| BLE 手机时间 | APP 通过 `time.sync` 提交；仅在当前时间已可信且没有 RTC 启动故障锁时用于日常微调，不得解除故障锁 |
| 4G 网络时间 | 模组或运营商网络时间；校验通过后可解除 RTC 启动故障锁 |
| MQTT 授时 | 平台连接后下发或请求返回的服务器时间；校验通过后可解除 RTC 启动故障锁 |
| HTTPS 时间 | HTTPS 注册或平台接口返回的服务器时间；校验通过后可解除 RTC 启动故障锁 |
| SNTP | 网络可用后的标准网络时间；校验通过后可解除 RTC 启动故障锁 |

默认策略：

1. 开机优先读取 RTC。RTC 正常时先用 RTC 建立可信 UTC；RTC 缺失或异常时立即置 `recovery_required=true`，UTC 保持不可信。
2. 首次收到 `NET_READY` 后立即启动 SNTP（默认服务器 `ntp.aliyun.com`），同时允许 HTTPS 注册时间、4G 网络时间或 MQTT 授时；任一经过统一校验的网络来源可建立可信 UTC 并清除故障锁。
3. `ntp.enabled=true` 时允许周期授时。
4. `ntp.sync_interval_sec` 默认 3600 秒；ESP-IDF SNTP 周期也固定为 1 小时，首次网络就绪不等待周期定时器。
5. 已可信且没有故障锁时，BLE 手机时间可按回退保护做日常微调。故障锁存在时，`time.sync` 必须整体拒绝，不修改时区、系统 UTC 或 RTC，并返回 `network_time_required`。
6. 网络授时成功后更新系统 UTC，最佳努力写 RTC，并按策略写 NVS。RTC 不存在或写回失败不影响本次通电期间的网络可信状态；下次启动仍会重新检测并锁定。

来源优先级不是简单的“最后写入者优先”。网络时间是故障恢复授权源，正常 RTC 是离线启动源，BLE 手机时间只是低权限校准源。任何来源仍须通过年份、格式和回退保护。

MQTT 授时落地规则：

1. 设备收到通过 topic、协议版本和方法路由校验的 `down_raw` 请求后，读取根字段 `timestamp`。
2. `timestamp` 为正整数毫秒 Unix 时间戳时，作为 `mqtt` 来源候选时间提交给统一校验。
3. 校验通过后，在处理业务方法和生成应答前更新 UTC，因此当前应答即可使用非 0 `timestamp`。
4. `timestamp` 缺失、为 0、类型非法或年份越界时，只拒绝该时间候选，不拒绝业务请求。MQTT 属于已认证网络授权源，允许纠正错误的未来检查点，但必须记录重基准诊断。

来源状态：

| 状态 | 说明 |
| --- | --- |
| `none` | 无可信 UTC |
| `rtc` | RTC 校验通过 |
| `module_4g` | 4G 网络时间校验通过 |
| `mqtt` | 平台 MQTT 授时校验通过 |
| `https` | HTTPS 时间校验通过 |
| `sntp` | SNTP 校验通过 |
| `ble_phone` | BLE APP 手机时间校验通过 |

## 6. UTC 可信判断

候选 UTC 必须满足：

1. 年份在 2026 到 2046 年之间，包含 2026 和 2046。
2. RTC 和 BLE 候选不得早于 `last_trusted_utc - 300000` 毫秒；已认证的 4G/MQTT/HTTPS/SNTP 网络来源允许纠正错误的未来检查点，并原子重建 NVS 基准。
3. 候选 UTC 的格式和单位必须明确为毫秒 Unix 时间戳。
4. 候选 UTC 为 0、负数或明显越界时拒绝。

判断结果：

| 结果 | 处理 |
| --- | --- |
| 通过 | 更新当前 UTC、`time.utc_trusted=true`、`time.source` |
| 年份越界 | 拒绝，记录 `time_year_out_of_range` |
| RTC/BLE 早于允许回退范围 | 拒绝，记录 `time_rollback_detected` |
| 网络时间早于错误检查点 | 接受服务器时间，记录重基准原因并重建 `last_trusted_utc` 主/备份 |
| 来源格式非法 | 拒绝，记录 `invalid_time_source` |

说明：

1. `300000` 毫秒回退容忍用于处理 RTC 或授时时间的小幅误差。
2. 时间校验拒绝不导致重启。
3. 如果 UTC 已可信，后续更高质量来源可更新当前 UTC。
4. 如果新候选时间小于当前运行 UTC，但没有触发 `last_trusted_utc` 回退限制，应记录 warn 并谨慎更新。
5. “候选 UTC 数值合法”和“允许定时调度”是两层判断。RTC 启动异常后，即使 BLE 手机时间数值合法，`time.utc_trusted` 仍为 `false`，直到网络授时成功。
6. RTC 启动故障锁写入加密 NVS 并跨重启保持。BLE 不得修复或清除此状态；只有网络授时成功且恢复锁主/备记录清除成功后，UTC 和调度才重新可信。

## 7. RTC 策略

本板使用带电池的外部 `YSN8010SJ` RTC，可作为可信 UTC 来源。硬件和总线参数固定如下：

| 项目 | 固定值 | 说明 |
| --- | --- | --- |
| I2C 7 位地址 | `0x32` | 使用 RX8010 兼容寄存器布局 |
| SCL | `GPIO9` | 原理图网络名 `SCL` |
| SDA | `GPIO10` | 原理图网络名 `SDA` |
| I2C 速率 | `100000` Hz | 标准模式 |
| 上拉 | 4.7 kΩ 到 3.3 V | 板上已有，固件不依赖内部上拉 |
| 后备电源 | CR1220 经二极管接入 `VRTC` | 主 3.3 V 断开后只维持 RTC 计时 |

RTC 内保存 UTC，不保存时区偏移或本地墙上时间。`rtc_read()` 在本文中专指通过 I2C 读取外部 `YSN8010SJ`，不是读取 ESP-IDF 的 `gettimeofday()`。

开机 RTC 流程：

```text
app_main
  -> storage_init()
  -> 读取并校验 last_trusted_utc 主/备安全记录
  -> rtc_init(GPIO9/GPIO10, 100 kHz, address=0x32)
  -> rtc_probe()
  -> rtc_read_status_and_calendar()
  -> 检查 VLF、STOP、BCD 和日期完整性
  -> time_validate_candidate(source=rtc)
  -> RTC 通过、安全时间记录有效且不存在历史故障锁：设置系统 UTC，time.utc_trusted=true，time.source=rtc
  -> RTC 缺失/失败、安全时间记录损坏或存在历史故障锁：锁存“需要网络校时”，time.utc_trusted=false，timestamp 填 0
```

RTC 可信条件：

1. 固定地址 `0x32` 可响应，RTC 状态和日期读取成功。
2. `VLF` 掉压/数据无效标志未置位。
3. `STOP` 停钟标志未置位。
4. BCD、星期、年月日和时分秒格式完整且取值合法。
5. RTC 年份在 2026 到 2046 年之间。
6. RTC 不早于 `last_trusted_utc - 300000` 毫秒。
7. 启动时两次读取间隔约 1.1 秒，第二次 UTC 必须合理向前推进；即使 VLF/STOP 均正常，读秒不前进也判为 `rtc_not_advancing`。

RTC 写入策略：

1. 网络授时成功后应把 UTC 写入 RTC；正常可信状态下接受的 BLE 微调也可写入 RTC。
2. 写入流程为设置 `STOP`、写 UTC 日历、按需初始化保留寄存器并清除 `VLF`、清除 `STOP`、读回状态和日期确认。
3. 写 RTC 失败不撤销已经生效的系统 UTC，但下次硬断电后的离线恢复不能视为有保证，并应记录 `rtc_write_failed`。
4. RTC 写入不应高频执行；同一来源连续授时且偏差很小时可跳过。
5. 正常重启前如 UTC 可信，不强制写 RTC，但可以写入一次作为收尾。

离线和掉电语义：

1. MQTT、4G 或互联网离线但设备仍有主电时，调度器使用已可信的系统 UTC 和单调时间继续执行任务。
2. 整机完全断电时，CR1220 只维持 RTC 计时；ESP32、dongle 和灯具控制链路均不工作，因此断电期间不会执行任何任务。
3. 重新上电且 RTC 有效时，固件在调度器启动前恢复可信 UTC。未到期的 `duration` 按原 UTC 截止时间继续；截止时间已在断电期间经过的 `duration` 直接标记为 `missed` 并自动停用，严禁补触发。
4. `daily` 重新上电时只安排严格晚于本次调度器可信起点的下一次计划；当天计划时刻已经经过即视为 `missed`，等待下一自然日，严禁使用补触发窗口。
5. RTC 不存在、`VLF=1`、`STOP=1`、日期非法、触发回退保护，或 `last_trusted_utc`/恢复锁主备安全记录损坏时，UTC 保持不可信并锁定所有定时动作。BLE 手机校时不能解除，只有重新获得并校验通过的网络时间后才可启动调度。
6. `VLF` 只表示 RTC 数据因掉压等原因不可信，不是电池电量计。本板没有把 CR1220 电压接入 ADC，固件不能报告“电池低电量”。

RTC 异常：

| 异常 | 处理 |
| --- | --- |
| 地址 `0x32` 无响应 | `rtc_present=false`，UTC 不可信并锁定调度，等待网络授时 |
| 读取失败 | UTC 不可信并锁定调度，等待网络授时 |
| `VLF=1` | `rtc_vlf_latched=true`、`rtc_valid=false`，锁存故障，等待网络授时重新初始化 RTC |
| `STOP=1` | `rtc_stopped=true`、`rtc_valid=false`，锁存故障，等待网络授时重新写入并启动 RTC |
| BCD 或日期非法 | `rtc_valid=false`，拒绝作为 UTC 来源 |
| 年份越界 | UTC 不可信，记录异常 |
| 早于 `last_trusted_utc - 300000` | UTC 不可信，记录时间倒退 |
| 写入失败 | 保持当前 UTC 可信状态，记录异常 |

RTC 故障锁保存在加密 NVS 主/备记录中。即使 RTC 后续恢复应答、用户重新插入电池或重启设备，也不自动解锁；网络授时校验成功并确认清锁持久化成功后才开放调度。恢复锁记录自身损坏时按 `recovery_state_invalid` 失败关闭，不能因“读不到锁”而放行任务。

## 8. last_trusted_utc 策略

`last_trusted_utc` 是最近可信 UTC 的长期基准，保存在加密 NVS。

固定规则：

1. 不设置过期时间。
2. 恢复出厂时清除。
3. 首次获得可信 UTC 时立即写入。
4. 当前可信 UTC 比 NVS 值大超过 24 小时时写入。
5. OTA 成功待重启前，如 UTC 可信，应写入一次。
6. 配置切换成功待重启前，如 UTC 可信，应写入一次。
7. 正常重启前，如 UTC 可信，应写入一次。
8. 普通心跳成功不触发写入。
9. RTC/BLE 当前可信 UTC 小于等于 NVS 值时不写入，并记录时间倒退或未推进原因。网络授权源解除恢复锁或纠正未来检查点时允许原子重建主/备份。

写入流程：

```text
time_maybe_save_last_trusted_utc(reason)
  -> 检查 time.utc_trusted
  -> 比较 current_utc 与 nvs_last_trusted_utc
  -> 满足首次/超过24小时/关键事件
  -> 写 time.last_trusted_utc_bak
  -> 写 time.last_trusted_utc
```

NVS 主副本：

| Key | 说明 |
| --- | --- |
| `time.last_trusted_utc` | 主记录 |
| `time.last_trusted_utc_bak` | 备份记录 |
| `time.rec_lock` | RTC/时间恢复锁主记录，协议键为 `rec_lock` |
| `time.rec_lock_bak` | 恢复锁备份记录，由安全存储层维护 |

读写规则：

1. 读取时先读主记录，失败则读备份记录。
2. 备份有效时可后台修复主记录。
3. 只有主备键都不存在时，才视为设备从未保存过历史可信时间。
4. 安全存储层必须校验加密包头、CRC 和值类型；`last_trusted_utc` 的类型固定为 `U64`，解密后长度必须严格等于 8 字节，数值还必须落在可信 UTC 年份范围内。
5. 主记录损坏时允许回退到有效备份；主备都因 CRC、包大小、值类型、明文长度或 UTC 范围错误而无效时，按 `recovery_state_invalid` 失败关闭。启动流程继续运行并等待联网，不能把损坏误判成“没有历史记录”，也不能因此形成重启循环。
6. 4G、HTTPS、MQTT 或 SNTP 网络时间校验成功后，可以原子重建 `last_trusted_utc` 主/备记录并解除恢复锁；RTC 和 BLE 手机时间不能修复该状态。
7. 写入使用存储模块的确定性 AES 加密。

## 9. 授时流程

启动后流程：

```text
boot
  -> RTC 校验
  -> RTC 正常且无故障锁：立即允许使用 UTC
  -> RTC 缺失/异常或已有故障锁：UTC 不可信，定时调度锁定
  -> 网络启动
  -> MQTT/4G/SNTP/HTTPS 任一授时成功
  -> 更新时间状态、RTC 和 last_trusted_utc，清除 RTC 故障锁
  -> 以授时成功时刻作为调度恢复点，过期 occurrence 只记 missed、不补触发
  -> 发布 TIME_TRUSTED 事件
```

周期授时：

1. 默认启用。
2. 默认服务器 `ntp.aliyun.com`，默认间隔 3600 秒。
3. 周期定时使用系统 tick。
4. 首次 `NET_READY` 立即发起一次，网络不可用时跳过本轮或等待下一次网络事件。
5. 授时失败只记录状态，不阻塞脚本和设备管理主循环。

授时成功后的动作：

1. 网络来源更新 `time.utc_trusted=true` 并解除调度锁；BLE 仅在原本已可信且无故障锁时允许微调。
2. 更新 `time.source`。
3. 更新当前 UTC。
4. 写 RTC。
5. 按 `last_trusted_utc` 策略写 NVS。
6. 通知等待 UTC 的任务，并按恢复点规则丢弃已经错过的用户定时 occurrence。
7. 后续日志、状态、属性和进度上报使用可信 UTC。

### 9.1 校准优先级和落地顺序

1. 冷启动先用 RTC 尽快建立时间，但要同时通过状态、日历、NVS 回退和约 1.1 秒读秒推进检查。
2. 首次 `NET_READY` 立即请求 `ntp.aliyun.com`；之后每 3600 秒同步一次。HTTPS 注册时间、4G 时间和已认证 MQTT 服务器时间走同一网络授权入口。
3. 网络时间是最高权限校准源：可双向纠正系统时间，并在旧 `last_trusted_utc` 明显错误地位于未来时重建检查点。正常 RTC 和 BLE 均不得突破 5 分钟回退保护。
4. BLE `time.sync` 只在当前已经可信且 `recovery_required=false` 时接受；它不能成为 RTC 故障后的启动授时源。
5. 接受候选后先设置系统 UTC。RTC 与候选相差不超过 2 秒时跳过物理写；否则使用 STOP 保护写入并读回确认。RTC 写失败只影响下次掉电恢复，不撤销本次网络可信 UTC。
6. 正常授时按首次、推进 24 小时或关键重启事件更新 `last_trusted_utc`。网络恢复时如果旧检查点错误，则立即重建主/备记录。
7. 恢复锁存在时，必须先把“已恢复”原子写入加密 NVS 主/备记录，再设置 `recovery_required=false` 和 `scheduler_time_trusted=true`。清锁落盘失败时继续保持不可信并等待下次网络重试。
8. 校准不改变已运行 `duration` 的单调截止点。UTC 或时区重基准若直接跨过 daily 计划点，该次按 missed 处理，不突然补发历史动作。
9. 所有运行期授时入口，包括 SNTP、MQTT、HTTPS、4G 和 BLE，必须成对调用 `gw_scheduler_time_change_begin()` / `gw_scheduler_time_change_finish()`：`begin` 串行化不同授时源并暂停调度轮询，调用方随后更新时区、系统 UTC、RTC 和 NVS，`finish` 完成 daily 边界对账后才恢复轮询。未持有事务的调用方不得直接接受候选 UTC。
10. 首次建立可信时间、UTC 改变量绝对值大于 300000 毫秒，或时区发生变化时，`finish` 必须重置 daily 边界；重基准跨过的到期点记为 `missed`。不超过 300000 毫秒且时区未变化的日常微调保留原边界，避免把本应自然触发的到期点误判为历史任务。
11. 授时事务期间，`gw_scheduler_poll()` 不检查到期任务，配置写操作可暂时返回 `task_busy`。即使边界持久化暂时失败也要解除全局暂停，保留 RAM 对账标志；标志存在时 daily 到期判断继续被拦截，后续轮询先重试持久化和对账，不观察半更新的时间轴。

## 10. 调度模型

调度分为相对调度和绝对调度。

相对调度：

| 任务 | 时间基准 |
| --- | --- |
| MQTT 心跳 | 系统 tick |
| MQTT 重连 | 系统 tick |
| HTTP 连接超时 | 系统 tick |
| HTTP 应答间隔超时 | 系统 tick |
| 注册重试 | 系统 tick |
| 日志扫描周期 | 系统 tick |
| 栈水位检查 | 系统 tick |
| request_id 清理 | 系统 tick |
| 已启用 `duration` 在本次连续开机期间 | 单调 tick；UTC 只保存掉电恢复截止点 |

绝对调度：

| 任务 | 时间基准 |
| --- | --- |
| 定时 OTA `scheduled_at` | 可信 UTC |
| `duration` 重启后的剩余时长恢复 | 可信 UTC 与持久化截止点 |
| `daily` 本地日历计划 | 可信 UTC 加 `tz_offset_min` |
| 后续如启用配置定时更新 | 可信 UTC |
| 按 UTC 的日志时间过滤 | 可信 UTC 日志 |

定时器约束：

1. 定时器回调只投递事件。
2. 不在定时器回调里执行 HTTP、MQTT 发布、文件扫描、OTA 写入等长耗时操作。
3. UTC 不可信时不启动绝对时间执行，只记录等待原因。
4. UTC 恢复可信后，调度器应重新评估等待中的绝对时间任务。

### 10.1 BLE 定时任务的一次性和错过策略

调度器必须区分“本次开机期间已经布防的到期点”和“开机/恢复可信时间之前已经过去的到期点”。禁止用固定的补触发窗口混淆二者。

启动或重新获得网络可信时间时，记录 `scheduler_resume_utc_ms`，然后逐项恢复：

1. `duration.deadline_utc_ms > scheduler_resume_utc_ms`：按原截止时间布防；等于或早于恢复点则记为 `missed`、自动停用，不发送动作。
2. `daily`：只计算严格晚于 `scheduler_resume_utc_ms` 的下一次本地计划；当天时刻已经经过时，从下一自然日开始，不补当天动作。
3. UTC 不可信期间只允许读取和修改配置，不允许创建新的运行中截止时间、投递 `timer.fired` 或发送任何 dongle/GS200 动作。

连续开机期间的一次性保证：

1. `duration` 创建/启用后使用单调 tick 作为本次启动倒计时主基准，同时保存 UTC 截止时间用于掉电恢复。
2. `daily` 不要求命中某个毫秒；在可信时间自然推进期间，只要当前时间已到且当日尚未执行，轮询抖动或任务短时阻塞后仍会投递一次。`duration` 在同次启动使用单调 tick，不受墙钟校准影响。
3. 每次到期先从持久化单调计数器预留唯一 `occurrence_id` 并保存更新后的计数器，再在任务表中推进并保存“已领取”进度：`duration` 自动停用并清除截止点，`daily` 保存 `last_fired_local_day`。这两步都确认落盘后，才允许向唯一动作 worker 入队。
4. 事件队列暂满时，在 RAM 中保留 `dispatch_pending`、同一 `occurrence_id` 和原 `scheduled_utc_ms`，只在本次连续开机内重试；不得重复分配编号，也不得再次推进任务状态。
5. `dispatch_pending` 存在时，禁止覆盖、删除或启停对应任务，并禁止修改全局时区；BLE 返回临时错误 `task_busy`。这样已领取事件使用的任务内容和本地日边界不会被并发替换。
6. 重启时不恢复 RAM 待投递状态。若在“领取进度已落盘、事件尚未入队”窗口断电，重启后仍把该 occurrence 视为已经处理而不重放；这是为避免重复灯控而采用的掉电窗口至多一次语义。
7. 正常连续供电且存储恢复、事件队列最终可用时，已经布防的到期点使用同一编号持续重试并只入队一次；副作用动作开始后无论成功或失败都不自动重放。物理断电期间不承诺执行。

显式 UTC 校时或时区修改是“时间轴重基准”，不等同于自然走时。重基准后若某个 daily 到期点已经位于新时间的过去，按 `missed` 处理而不补触发，避免错误时钟被一次大幅修正时突然执行历史灯控。这里的“连续开机一定触发”是指可信时间连续自然推进并跨过已布防到期点，不包括断电、时间不可信区间或显式重基准直接跳过到期点。

### 10.2 用户业务 cron 预留

旧工程中的 cron/scheduler 约定已迁移为禁用态预留目录 `embedded/disabled/cron/`。当前版本不启用用户业务 cron，不安装 `cron.py` 到配置区，也不由 C 层直接调度用户脚本。

后续如启用，必须满足：

1. cron 配置由配置包携带，例如 `cfgfs:/cfg_a/cron.toml`。
2. cron 只在 Python 框架层运行，C 层只提供可信 UTC、单调 tick、waker 和停止状态。
3. `require_valid_time=true` 的任务必须等待 UTC 可信。
4. cron 任务执行必须遵守 `script_task`、PSRAM、`datafs:/` 路径和脚本停止协同规则。
5. 启用前必须先补充 asyncio 包装层、任务重入策略和脚本退出清理测试。

## 11. 定时 OTA

当前协议明确使用 `scheduled_at` 的场景是 OTA。

规则：

1. `scheduled_at` 可选，单位为毫秒 Unix 时间戳，按 UTC 解释。
2. 未提供 `scheduled_at` 时，OTA 接收后可立即执行。
3. 提供 `scheduled_at` 且 UTC 可信时，时间已到则执行，未到则等待。
4. 提供 `scheduled_at` 且 UTC 不可信时，进入 `waiting_time_sync`。
5. 等待 UTC 或计划时间期间，OTA 任务仍占用非查询互斥任务。
6. 等待期间查询类指令仍可执行。
7. 只有 OTA 在本次连续开机期间已用可信时间进入 `waiting_schedule`，随后跨过 `scheduled_at`，才执行 OTA。启动或网络校时恢复时发现 `scheduled_at` 已到或已过，应标记计划已错过并取消，不补执行。
8. OTA 成功待重启前，如 UTC 可信，应写入 `last_trusted_utc`。

OTA 等待状态：

| 阶段 | 说明 |
| --- | --- |
| `waiting_time_sync` | 等待可信 UTC |
| `waiting_schedule` | UTC 可信，但未到执行时间 |
| `schedule_missed` | 启动或恢复可信时间时计划点已经过去；终止且不补执行 |

## 12. 配置定时扩展

当前 MQTT 协议中的 `config.update` 不启用配置定时更新字段；配置更新收到后按整包更新流程处理。

若后续版本扩展配置 `scheduled_at`，必须遵守：

1. `scheduled_at` 单位为毫秒 Unix 时间戳，按 UTC 解释。
2. 只有 UTC 可信后才允许执行。
3. UTC 不可信时进入等待授时状态。
4. 等待期间查询类指令仍可执行。
5. 只有本次连续开机期间跨过计划时间才进入配置下载和切换流程；启动或网络校时恢复时已过计划时间则取消，不补执行。
6. 该扩展必须先更新 MQTT 协议文档，再进入实现。

## 13. 协议时间戳

设备生成 MQTT 报文时：

| UTC 状态 | `timestamp` |
| --- | --- |
| 可信 | 当前 UTC 毫秒时间戳 |
| 不可信 | 0 |

适用报文：

1. `up_raw` 中的 `status.report`。
2. `up_raw` 中的 `property.report`。
3. `heartbeat.report`。
4. `config.update.reply`。
5. `ota.progress`。
6. `log.query.reply`。
7. `script.exception`。
8. 其他设备主动上报或应答。

日志时间：

1. UTC 可信时，日志 `ts` 填当前 UTC 毫秒时间戳，`time_synced=true`。
2. UTC 不可信时，日志 `ts=0`，`time_synced=false`。
3. 日志仍必须保存 `uptime_ms`，便于无 UTC 时排查先后顺序。
4. 日志按 `start_time/end_time` 过滤只对 `time_synced=true` 的日志可靠。

## 15. 与其他模块关系

| 模块 | 关系 |
| --- | --- |
| `dev_mgr_task` | 接收时间事件，推进主状态机和调度任务 |
| `gw_mqtt_manager` | MQTT 连接后触发平台授时或上报时间属性 |
| `gw_config_manager` | 配置切换前请求保存 `last_trusted_utc` |
| `ota_manager` | 定时 OTA 等待可信 UTC，成功前请求保存时间 |
| `log_task` | 使用 UTC 生成 `ts`，UTC 不可信时依赖 `uptime_ms` |
| `script_task` | 可查询时间状态，但不能直接修改系统 UTC |
| `storage` | 提供加密 NVS 主/备读写 `last_trusted_utc` 和持久化恢复锁 `rec_lock` |

脚本可见能力：

1. 查询 `time.utc_trusted`。
2. 查询当前 UTC 或返回 0。
3. 查询 `time.source`。
4. 查询本次启动 `uptime_ms`。

脚本不可执行：

1. 不得直接写 RTC。
2. 不得直接写 `last_trusted_utc`。
3. 不得绕过线程 1 创建定时 OTA。

## 16. 异常策略

| 异常 | 处理 |
| --- | --- |
| RTC 地址 `0x32` 无响应 | `rtc_present=false`，UTC 不可信并锁定调度，只等待网络授时 |
| RTC 读取失败 | UTC 不可信并锁定调度，只等待网络授时 |
| RTC `VLF=1` 或 `STOP=1` | `rtc_valid=false`，锁存故障，不使用 RTC 日期，只等待网络授时修复 |
| RTC 年份不在 2026 到 2046 | UTC 不可信，记录异常 |
| RTC 早于 `last_trusted_utc - 300000` | UTC 不可信，记录时间倒退 |
| `last_trusted_utc` 主备的 CRC、包大小、值类型、明文长度或数值范围均无法通过校验 | 置 `recovery_state_invalid` 并锁住调度；启动继续联网而不重启循环，只有网络授权时间可重建主/备记录并自愈 |
| 网络授时失败 | 保持当前状态，按周期重试 |
| 当前 UTC 不可信 | 协议 `timestamp=0`，定时任务只等待，不投递动作 |
| 故障锁期间收到 BLE `time.sync` | 返回 `network_time_required`，时区、系统 UTC 和 RTC 均保持不变 |
| 网络校时恢复时任务已经过期 | 标记 `missed`；duration 自动停用，daily 安排下一自然日，不补触发 |
| 当前 UTC 倒退 | 拒绝更新或记录 warn，保持原可信状态 |
| RTC 写入失败 | 保持当前 UTC 可信状态，记录异常 |
| NVS 写入失败 | 保持内存 UTC 状态，记录异常，下次关键事件再尝试 |

## 18. 测试建议

4. RTC 通过校验时开机即可生成非 0 `timestamp`。
5. RTC 写入失败不影响当前 UTC 可信状态。
6. 授时后确认外部 RTC 写入并读回成功，再彻底切断主 3.3 V 供电 10～30 分钟；测试期间必须排除 COM9、USB-UART 或其他接口向主电源反向供电。
7. 保持 4G、MQTT、SNTP 和 BLE 授时不可用后重新上电，首次时间状态必须为 `source=rtc`、`rtc_present=true`、`rtc_valid=true`，且 UTC 推进量与实际断电时长基本一致。
8. 分别验证：`duration` 未到期时按原截止时间继续、已在断电期间到期时启动后标记 missed 并停用；`daily` 的当天计划已过时直接安排下一日，任何情况都不补历史动作。
9. 拔出电池或制造 VLF/STOP/非法日历/读秒不前进/恢复锁损坏后启动，必须持久化锁定；普通重启仍不解锁，BLE `time.sync` 返回 `network_time_required` 且不改变系统 UTC/RTC，只有网络授时成功并清锁落盘才恢复。

NVS 测试：

1. 首次可信 UTC 立即写入 `last_trusted_utc`。
2. 未超过 24 小时时普通授时不频繁写 NVS。
3. OTA 成功待重启前写入一次。
4. 配置切换成功待重启前写入一次。
5. 主记录损坏时可从备份恢复。
6. 分别破坏主/备记录的包 CRC、包大小、值类型和明文长度，确认启动不会反复重启，而是进入 `recovery_state_invalid`、保持调度锁定；网络授时成功后主/备记录可被重建并恢复调度。

调度测试：

1. UTC 不可信时，`scheduled_at` OTA 进入 `waiting_time_sync`。
2. UTC 可信且未到 `scheduled_at` 时进入 `waiting_schedule`。
3. UTC 可信且已到 `scheduled_at` 时立即执行。
4. UTC 不可信不影响 MQTT 重连、HTTP 超时和注册重试。
5. 定时器回调不执行长耗时操作。
6. 连续可信时间自然推进时让轮询跨过到期毫秒、让 worker 短时阻塞，已布防 occurrence 均只领取一次；显式 UTC/时区重基准跨过计划点时必须记 missed、不补发。
7. 并发注入 SNTP、MQTT 和 BLE 授时，确认授时源被串行化、事务期间 poll 不触发任务，并且 APP 配置写入只会暂时得到 `task_busy`；分别验证不超过 5 分钟微调保留边界、大于 5 分钟跳变和时区变化先对账再恢复轮询。
8. 在“唯一 ID 与领取进度落盘前后、事件入队前后、动作发送前后”分别模拟重启；领取进度未落盘时允许本次开机重试，落盘后即使未入队也不得跨重启重放。
9. 制造事件队列暂满，确认 RAM pending 复用同一 `occurrence_id` 并在队列恢复后只入队一次；pending 期间覆盖、删除、启停和修改时区均返回 `task_busy`，掉电后不恢复 pending。

协议测试：

1. UTC 不可信时设备应答 `timestamp=0`。
2. UTC 可信后设备应答 `timestamp` 为当前毫秒时间戳。
3. 日志 UTC 不可信时 `ts=0`、`time_synced=false`。
4. 日志时间过滤只匹配 `time_synced=true` 的可靠时间日志。

## 19. 实现顺序

1. 实现 `gw_time_init()`，读取 `last_trusted_utc` 和 RTC。
2. 实现候选 UTC 校验：年份、回退容忍、格式检查。
3. 实现 `time.utc_trusted`、`time.source` 和协议时间戳接口。
4. 实现 RTC 写入和 `last_trusted_utc` 主副本写入策略。
5. 接入 4G、MQTT、HTTPS、SNTP 授时来源。
6. 实现周期授时定时器和 `TIME_TRUSTED` 事件。
7. 实现 `gw_scheduler` 的相对任务和 UTC 绝对任务。
8. 接入 OTA `scheduled_at` 等待和到时执行。
9. 接入日志、状态、属性和脚本只读查询。
10. 补齐 RTC 异常、时间倒退、NVS 损坏和授时失败测试。
